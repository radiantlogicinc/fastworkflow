# Execution Agent Anti-Patterns

Critical mistakes to avoid when executing workflows, derived from distillation.

1. Only use the environment's accepted cancellation reasons (e.g., "no longer needed", "ordered by mistake") with cancel_pending_order; improvised reasons like "User request" fail with "Invalid reason" and waste a tool call.
2. When the user asks for the total refund, sum every refund due — the full amounts refunded by each cancelled order ($3131.10 + $4777.75) plus the returned item's price ($367.38), totaling $8276.23 — rather than reporting only the returned item's price ($367.38) or a false $0.00.
3. Do not tell the user refunds total $0.00 or are "unprocessed" without verifying; cancel_pending_order refunds immediately, so check refund/payment history across all affected orders before stating any amounts.
4. When the user hasn't specified a refund destination, confirm the payment method with the user or verify the order's original payment method instead of arbitrarily picking one from the user profile.
5. Never fabricate system facts that no tool or policy supports — e.g., inventing a return shipping address, claiming a prepaid return label was emailed to the user, specifying carriers/packaging steps, or promising refund timelines like "2-3 business days"; only relay information actually returned by tool calls or clearly documented policy.
6. Avoid redundant verification calls: do not re-run lookups (e.g., find_user_id_by_email followed by get_user_details) to re-confirm data already retrieved earlier in the session, and do not re-fetch identical order details repeatedly when nothing has changed.
7. When the user asks to cancel all pending orders, inspect the status of every order on the account and cancel each pending one — the student mislabeled #W8665881 as delivered and never cancelled it despite having fetched its details.
8. Do not state order counts or account state to the user (e.g., "You have 1 pending order") until the status of every order has been checked.
9. When the user refers to an item by description rather than order number (e.g., "the watch I just received"), search their orders yourself instead of asking them to supply the order number they likely don't know.
10. After a tool call fails, immediately re-execute the corrected call and verify the success observation before proceeding — never claim an action succeeded (e.g., asserting "order #W5199551 successfully cancelled" and reporting its refund) when the retry was never actually executed.
11. Before telling the user which order contains an item they want to return, verify each candidate order's delivery status and item list from actual order details — a watch the user "just received" must be in a delivered order, never a pending or cancelled one.
12. Match user item descriptions semantically rather than requiring an exact product-name match — the delivered order #W9389413 contained a "Smart Watch" satisfying "return the watch I just received", but the student concluded "no wristwatch exists in delivered orders" and never processed the return.
13. When the user has already explicitly requested "cancel all pending orders" upfront, proceed directly with each cancellation instead of re-asking per-order yes/no confirmations, which wastes turns.
14. Don’t perform irreversible order modifications (item swaps/address updates) until the user confirms the corrected address and the exact replacement variant, especially when multiple variants/payment outcomes exist.
15. When adjusting an order with a price difference/refund, use the user-specified (or order-original) payment method; never arbitrarily pick a credit card when PayPal (or another method) is requested.
16. If the user asks to verify/correct the address on “all my orders,” update every pending order’s shipping address (not just the one being edited for items).
17. Use the workflow’s exact expected argument names and structures (e.g., `item_ids`/`new_item_ids` as JSON arrays; correct address field tags; well-formed command markup); malformed params may silently fail and must not be treated as success.
18. Don’t claim “refund processed to X” unless the tool response explicitly confirms refund destination/amount; replacing an item with a cheaper one does not guarantee a refund to a specific method without confirmation.
19. Don’t perform irreversible order modifications (e.g., swapping items) before explicitly confirming the exact replacement variant/address and payment/refund preference with the user.
20. When a user asks to verify/correct the address on “all my orders,” update the shipping address on every pending order (not just the one being modified for items).
21. Avoid redundant or repeated `modify_user_address` calls; after an address update succeeds once, proceed to the remaining required steps instead of reissuing the same update.
22. Use the workflow’s exact command syntax and parameter names (e.g., `modify_user_address <user_id>... <address1>...`; `modify_pending_order_address` tags like `address1/address2`) to prevent parser misrouting and extraction errors.
23. Don’t call `finish` until all requested operations are successfully executed and confirmed by tool observations.
24. Don’t propagate stray characters in user-provided addresses (e.g., leading “R ”) into `modify_user_address`/order address updates; confirm/normalize the exact corrected address before applying.
25. When a user asks to verify/correct the address on “all my orders,” update the shipping address on every pending order, not just the one being modified for item swaps.
26. Use the workflow’s exact argument names and formats for item swaps (e.g., `item_ids`/`new_item_ids` as JSON arrays) rather than ad-hoc fields like `old_item_ids` to avoid silent failures.
27. Don’t call `finish` until all user-requested actions are completed; avoid “finish” followed by additional tool calls (premature termination).
28. Don’t execute an irreversible order item swap before explicitly confirming the exact replacement variant, address correction, and payment/refund preference with the user.
29. When the user asks to verify/correct the address on “all my orders,” update the shipping address on every pending order (not just the one being edited for item changes).
30. Use the workflow’s exact expected parameter names and formats (e.g., `modify_pending_order_items` with `item_ids`/`new_item_ids` as JSON arrays; `address1/address2` tags; well-formed `<order_id>...</order_id>`), not ad-hoc fields like `old_item_ids` or `first_line`.
31. Don’t call `finish` until all requested actions have been executed and confirmed by tool observations; avoid finishing and then continuing with more tool calls.
32. Don’t execute an irreversible order item swap before explicitly confirming the exact replacement variant, any address correction, and refund/payment preference when the user only expressed uncertainty (“might be too hard”, “may have typed my address incorrectly”).
33. When a user asks to verify/correct the address on their account and “all my orders,” you must ask for the corrected address if none is provided and then update both the account address and every pending order’s shipping address (not just assume it’s fine because values match).
34. Use the workflow’s exact expected argument names/structures for item swaps (e.g., `item_ids`/`new_item_ids` JSON arrays), not ad-hoc fields like `old_item_ids`, to avoid parser mismatch or silent failures.
35. Don’t claim “refund was issued to PayPal/original method” unless the tool response explicitly confirms the refund amount and destination; otherwise phrase as “price difference will be applied/processed via the payment method on file” or verify via a supporting tool response.
36. Don’t assume “address is correct” just because account and orders match—when the user says it “may be incorrect,” ask for the corrected address and then update the user profile plus every pending order’s shipping address.
37. Never attempt an irreversible `modify_pending_order_items` before completing required address updates/confirmations; heed system/tool warnings about one-way modifications and sequence the steps accordingly.
38. Use the workflow’s exact command schema: `modify_pending_order_items` should use `item_ids`/`new_item_ids` as JSON arrays (not ad-hoc `old_item_ids`/bare strings) to avoid parser mismatch or silent failure.
39. Keep tool command markup well-formed (e.g., include `<order_id>...</order_id>` in `modify_pending_order_address`) rather than relying on loosely formatted strings that may fail in stricter parsers.
40. Don’t claim a refund/price-difference was processed “via PayPal” unless the tool output explicitly confirms the refund amount and destination; otherwise state it more cautiously or verify with a supporting query.
41. After a tool explicitly instructs “do not modify yet” / indicates a prerequisite (e.g., address change pending), do not repeat the same blocked call—stop, satisfy the prerequisite (often via ask_user + address update), then retry once.
42. Never proceed as if a change succeeded when the tool observation says it was rejected; update your plan and user-facing statements to reflect the failure before attempting any further irreversible actions.
43. Avoid “thrashing” with multiple `finish` calls and then resuming tool execution; treat `finish` as terminal only after all required tool steps have succeeded (per observations) and no further actions are pending.
44. Don’t ask the user which payment method to “cover the difference” when the replacement item is cheaper; frame it as a refund/credit destination choice (or confirm preferred refund method) instead of implying an extra charge.
45. Use the workflow’s required JSON-array format for `modify_pending_order_items` parameters (`<item_ids>[\"...\"]</item_ids>` and `<new_item_ids>[\"...\"]</new_item_ids>`), not bare string IDs, to avoid parser mismatch or silent failures.
46. When the primary email lookup fails, ask the user for an alternate email address associated with their account before requesting order numbers or escalating to a human agent.
47. Do not transfer to a human agent while viable account-identification methods (e.g., alternate email addresses, name+ZIP lookups) remain unexplored and the user has not exhausted their available identifying information.
48. When a user requests to return a specific item described in singular terms (e.g., "this overpr onzekerheid speaker"), but the order contains multiple similar items with different IDs/prices, do not assume all instances should be returned; identify the specific item based on the user's description (e.g., the higher-priced one) or ask for clarification before executing the return.
49. Never claim an order's shipping address matches the corrected account address without verifying from tool observations; the student falsely stated order #W9583042 already had the updated address (445 Maple Drive) when the fetched details showed it still contained the old address (443 Maple Drive), failing to update it despite the user requesting correction on "all my orders."
50. Verify that a pending order contains the specific items the user wants to modify before requesting cancellation confirmation — the student asked to cancel order #W9892465 (Smart Watch) without checking if it contained the fleece jacket or skateboard, resulting in cancellation of the wrong order.
51. When a user mentions specific items by name, systematically inspect all pending orders to locate which order(s) contain those items rather than assuming an arbitrary pending order is the correct one.
52. Check the product catalog for variant availability (e.g., "maple deck, 34 inches, graphic") before informing the user whether a requested modification is possible.
53. Do not execute irreversible cancellations until the correct order(s) containing the user's requested items have been identified from a complete review of all account orders.
54. Do not attempt to execute `cancel_pending_order` until every order on the account has been retrieved via `get_order_details`; the system blocks write operations until all orders have been read, and premature cancellation attempts result in errors that waste turns.
55. Before requesting cancellation confirmation for a pending order containing a user-mentioned item, inspect all pending orders first to verify whether other mentioned items are in the same order or different orders, and present the complete order structure to the user rather than handling cancellations sequentially in isolation.
56. When asking a user to confirm an order for cancellation or modification, explicitly list the items in that order (e.g., "Order #W9892465 contains: Smart Watch") so the user can verify it matches their intent; the student asked for confirmation on #W9892465 without disclosing it contained only a Smart Watch, causing the user to mistakenly approve cancelling an unrelated order.
57. When a user's requested items are distributed across multiple pending orders, track and process every affected order to completion; the student cancelled the skateboard order #W1242543 but failed to cancel the fleece jacket order #W8367380, leaving the user's request partially unfulfilled.
58. When a user provides account identification (e.g., email) but declines to share new sensitive data in chat, and explicitly indicates the information exists in existing records (e.g., "pull the Washington DC address from my pending order"), authenticate the user and query order history to retrieve that data rather than terminating the conversation.
59. Do not abandon a user's request when they express hesitation about sharing data in chat; instead, authenticate the account and search existing records for usable information (e.g., previous shipping addresses on orders) to fulfill the request, only offering alternative methods (e.g., account portal) after confirming what data is actually available.
60. Never terminate with `finish` without first attempting to authenticate the user when valid identifying information (e.g., email address) has been provided; premature termination prevents discovering that requested data already exists in the account.
61. When a user requests an address change to an address that exists in their order history (e.g., a Washington DC address found in a previous order), retrieve and use that specific address for updating the default account and pending orders, not the old/current address already on file.
62. Do not execute `modify_user_address` or `modify_pending_order_address` with the existing address values when the user has explicitly requested a change to a different address; verify the target address matches the user's request and differs from the current one before writing.
63. After retrieving order details containing an address that matches the user's description, use that retrieved address immediately for the requested updates rather than asking the user to provide it again or defaulting to the old default address.
64. When the user instructs to use an address from one specific order (e.g., Order #W1603792) as the new address for another order (e.g., Order #W1092119), update the target order with the source address, not the reverse; the student incorrectly updated Order #W1603792 with the address from Order #W1092119, swapping the addresses in the wrong direction.
65. Before attempting an item exchange, verify the order status; do not call `exchange_delivered_order_items` on pending orders as it will be rejected—use `modify_pending_order_items` for pending orders instead.
66. When setting the default account address based on a user's clarification about which order contains the new address, use the specific address identified as "new" (760 Elm Avenue from Order #W1603792), not an address from a different order (592 Elm Avenue from Order #W1092119).
67. Never fabricate payment method identifiers (e.g., masked tokens like "PMT-****-8421") — use the actual payment method ID retrieved from `get_user_details` (e.g., `credit_card_5694100`) or ask the user to select from their available payment methods.
68. Do not repeatedly call `get_user_details` (or other read-only lookups) in succession when the requested data is not present in the initial result; if a payment method with specific digits is not found, use the available payment method or ask the user for clarification rather than thrashing with identical queries.
69. When the user instructs to use an address from an existing order and declines to re-provide it, execute the address updates (`modify_pending_order_address`, `modify_user_address`) using the retrieved order details rather than abandoning the task or repeatedly asking for the address.
