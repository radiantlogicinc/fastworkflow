## 1. Symptom

An application team tuning intent detection on a large workflow had no way to tell whether
their work was helping.

`fastworkflow train` reported mean per-context F1 around 0.94. On held-out phrasings the
same models routed 46.2% of utterances to the right command. The team spent three
retraining cycles — roughly nine hours of wall clock — chasing per-context numbers that
later turned out to be noise, and lost a full set of trained artifacts to an unrelated
regeneration step because nothing is versioned.

Every finding below came out of that exercise. They are ordered by what blocks what, not
by how interesting they are.

## 2. What was measured

The reference benchmark scores two axes that the package does not currently distinguish:

- **Routing** — 446 held-out phrasings, two per command, none of which appear in the seed
  table. Scored `top-1` (one confident correct label) and `in-list` (correct label among
  returned candidates).
- **Escalation** — 37 phrasings aimed at a command that is provably absent from the tested
  context's label space but present in one of its ancestors. A confident `wildcard` is the
  only correct answer, because that is what makes the runtime walk up the parent chain.

| Run | Seeds/command | Routing top-1 | Routing in-list | Escalation | Train time |
|---|---|---|---|---|---|
| baseline | 3.2 | 46.2% | 63.9% | not measured | — |
| v2 | 8.0 | 70.4% | 77.6% | not measured | — |
| v3 | 9.3 | 73.8% | 82.7% | 91.9% | 3h35m |
| v4 (wildcard capped 3×) | 9.3 | 76.5% | 84.5% | 83.8% | 2h00m |

Paired comparison of v3 → v4 on identical cases, exact McNemar on the discordant pairs:

| Axis | Fixed by v4 | Broken by v4 | p |
|---|---|---|---|
| Routing top-1 | 52 | 40 | 0.25 |
| Escalation | 1 | 4 | 0.38 |

**92 of 446 routing cases (20.6%) changed verdict between two runs.** That churn is the
single most important number in this document: it is the noise floor of one training run,
and it is larger than any effect measured after the initial seed expansion.

## 3. Findings

Severity: **S1** blocks other work or silently corrupts models · **S2** materially
misleads developers · **S3** cost, ergonomics, or clarity.

### F1 — The reported quality metric measures memorisation (S1)

`model_pipeline_training.py:914` splits the *same* synthetic utterance set the model
trains on:

```python
train_data, test_data = train_test_split(dataset, test_size=0.25, random_state=42)
```

Utterances for one command are generated by a handful of personas from one seed list, so a
random 25% holdout is near-duplicated in the training 75%. Measured gap on that workflow: ~0.94
reported F1 against 46.2% held-out top-1.

There is no held-out concept anywhere in the package. This is the root blocker: every
other improvement here needs a trustworthy signal to be evaluated against, and the loop in
R7 is unimplementable without one.

### F2 — Nothing is seeded; runs are not reproducible (S1)

No `manual_seed`, `random.seed`, `np.random.seed`, or `set_seed` call exists in the
package. The only determinism is `random_state=42` on the split above. Persona selection
is free-running (`train/generate_synthetic.py:43`):

```python
selected_indices = random.sample(range(len(persona_dataset)), num_personas)
```

and model initialisation is unseeded. Consequence: the 20.6% churn in §2. This blocks
incremental training (a command retrained today is not comparable to its neighbours
trained last week), blocks utterance caching (no provenance), and blocks any
convergence loop.

### F3 — A rate-limited command silently becomes unroutable (S1)

`train/generate_synthetic.py:120-122`:

```python
except litellm.exceptions.RateLimitError:
    logger.error("LiteLLM Rate limiting error!")
    return []
```

It returns `[]` — not the seed utterances, nothing. The caller
(`model_pipeline_training.py:857-863`) zips that empty list with the command name, so the
command contributes zero rows and **its label never enters the context's classifier**.
The command becomes permanently unroutable until the next training run. The only trace is
one log line in a run that prints tens of thousands of progress-bar lines.

Compare the `datasets`-missing path at line 26-32, which correctly degrades to
`[command_name] + seed_utterances`. The rate-limit path should do the same.

### F4 — No per-command visibility into training data (S2)

`train()` prints `Generating utterances for context X, command Y ...` with no count, and
never validates that a command ended up with a usable number of rows. A developer cannot
answer "which of my commands are starved?" — which, per F13, is the highest-leverage
question they can ask.

### F5 — Artifacts are overwritten in place, with no versioning (S1)

Training writes directly into `___command_info/<Context>/`. There is no version, no
"current" pointer, and no rollback. To compare two runs the application team had to `mv` 8.6 GB by
hand; a separate scaffold-regeneration step destroyed a complete trained set because
nothing marks these directories as expensive. Selective retraining (R1) is unsafe without
this, and paired evaluation (R7) is impossible without it.

### F6 — `wildcard` is overloaded across two NLU stages (S2)

It carries two unrelated meanings:

1. During `INTENT_DETECTION` it is an **escalation signal**. `train()` assigns it every
   ancestor-context utterance not also valid locally (`model_pipeline_training.py:872-877`
   and `cache_ancestor_utterances`, lines ~~769-801~~ **768-801** [AR7]; the `def` is at 768).
   Note that `cache_ancestor_utterances` reaches ancestor commands through
   `context_model.commands(ancestor_ctx)`, which is **`base`-resolved** — see AR2. At runtime a
   `wildcard` prediction
   sets `command_name=None` (`intent_detection.py:141`), which drives the parent-chain
   walk in `wildcard.py:100-104` and falls back to `you_misunderstood` only when every
   ancestor declines. This is sound design and it works — 91.9% recall on that workflow.
2. During `PARAMETER_EXTRACTION` it is a **bare-value catcher**, which is what its seven
   literal placeholders plus the command name are for (`wildcard.py:10-24`: `"3"`,
   `"france"`, `"id=3636"`, ...).

Role 2's literals are trained into role 1's classifier. They should be separate labels.

### F7 — A `wildcard` inside the top-k silently suppresses escalation (S2)

Only a lone `wildcard` triggers the parent walk. When the classifier is unconfident and
returns `wildcard` alongside local candidates, `intent_detection.py:124-128` takes the
ambiguity branch instead, and `_formulate_ambiguous_command_error_message` (line 281)
filters `wildcard` out of the displayed list. The user is offered local commands; the
model's "this belongs upstairs" signal is discarded with no trace.

Observed on the reference workflow: in context `ReviewTicket`, *"approve everything from this app at once"*
returned `['wildcard', 'ReviewTicket/certify_approve', 'ReviewTicket/show_review_item']`
and produced a two-option prompt, when the correct behaviour was to escalate to
`AccessReviewWorkspace/bulk_decide`.

### F8 — `wildcard` is the majority class in every context that has ancestors (S3)

Because ancestor utterances arrive already expanded by the synthetic generator, and
nothing reweights or resamples, `wildcard` dominates:

| Context | Own rows | Wildcard rows | Wildcard share |
|---|---|---|---|
| Subscription | 28 | 286 | 91% |
| ControlFinding | 37 | 372 | 91% |
| Exception | — | — | **retracted [AR6]; source artifact unavailable — do not cite** |
| Account | 138 | 431 | 76% |
| Directory (no ancestors) | 98 | 8 | 8% |
| Resource (no ancestors) | 116 | 8 | 6% |

The former `Exception` row was `42` own / `312` wildcard / `88%`. Its arithmetic is
internally consistent (`312 / (42 + 312) = 88.1%`), but the external reference workflow, its app-side
training harness, and the row-count artifacts are not present in this checkout. It therefore
cannot be independently reproduced and must not be used as the before-state of R7.2. [AR6]

Range across the 29 measured contexts that have ancestors: 48-91%. Four contexts have no
ancestors; the three application-facing ones (`*`, `Directory`, `Resource`) sit at 5-8%.

**Read the severity carefully.** Contexts above 69% wildcard average 66.1% top-1 against
78.7% for those at or below 55%, but the correlation is only −0.21, and both groups gained
equally from seed work (+29.9 vs +26.1 points). Capping the class was tested directly and
did **not** produce a significant accuracy change (§2: p = 0.25). What it did produce is a
**44% reduction in training time**, 3h35m to 2h00m. This finding is a cost and hygiene
issue, not an accuracy issue, and the spec should not claim otherwise.

### F9 — No class weighting of any kind (S3)

Independent of `wildcard`: per-context label spaces range from 4 to 23 commands on the reference workflow,
and the loss is unweighted with no sampler. Capping is a blunt special case of the general
fix.

### F10 — Escalation recall is not measured anywhere (S2)

No test, metric, or log covers it, yet it is the behaviour that makes context hierarchies
usable. Any change to `wildcard` trades routing accuracy against it silently. That workflow's cap
moved it 91.9% → 83.8% and nothing in the package would have noticed.

### F11 — Artifacts are ~276 MB per context (S3)

Each context directory holds a full DistilBERT copy plus a BERT-tiny (`largemodel.pth`,
`tinymodel.pth`, two threshold files, a label encoder). 33 contexts → 8.6 GB for a
160-command workflow. **Confirmed in-repo at review time [AR7]:** `275M` per context directory
for `fastworkflow/examples/retail_workflow/___command_info/global/` and for both context
directories of the internal `command_metadata_extraction` workflow. The figure is not
workflow-specific and does not require the external reference workflow to reproduce. A shared encoder with
per-context classification heads would cut
this by roughly two orders of magnitude, and would make selective retraining (R1) cheap:
rewriting one context would touch a few MB of head weights instead of 276 MB.

### F12 — Persona sampling is domain-agnostic (S3)

Personas are drawn at random from PersonaHub with no conditioning on the application
domain (`generate_synthetic.py:43`). For an identity-governance workflow, most sampled
personas have no relationship to the vocabulary users actually employ. Allowing an
app-supplied persona set is plausibly a larger generalisation lever than anything in the
training loop.

### F13 — Seed count is the dominant input, and nobody is told (S2)

The measured seed-count curve, holding everything else constant:

| Seeds/command | Routing top-1 |
|---|---|
| 3.2 | 46.2% |
| 8.0 | 70.4% |
| 9.3 | 73.8% |

Nothing in the docs or the training output tells a developer that this is where their
effort belongs, or that returns flatten past roughly eight seeds.

### F14 — Duplicate capabilities are indistinguishable and undiagnosed (S3)

Some workflows expose the same capability twice — on the reference workflow,
`ControlsMonitor/list_findings` and `Directory/search_control_findings` answer the same
question. No amount of utterance engineering separates them; they present as permanent
benchmark failures and send developers chasing an unfixable defect. Training can detect
near-duplicate label clusters and say so.

### R1 — Held-out evaluation

Reserve evaluation data that the model has not trained on, and report both axes.

- Hold out **whole personas**, not random utterances. Holding out 25% of rows from a
  persona whose other rows are in training is the defect in F1; holding out every
  utterance produced by personas *k*..*n* is ~~a real generalisation test~~ **strictly better
  than a random row split but still not a generalisation test [AR1]** — every persona is
  conditioned on the same seed text and the same keyword bag, so the phrasing distribution is
  shared across the split. Read it as an in-generator holdout and label it as such.
- The holdout must be **aligned to `personas_per_batch` boundaries** [AR1]. Personas in one
  batch are generated in a single completion (`generate_synthetic.py:59-61`), so a held-out
  persona that shares a batch with a training persona shares the sampler's context as well as
  the prompt.
- The evaluated model is **not** the shipped model if the held-out personas are dropped from
  training [AR1]. Either train a shadow model for evaluation and ship the full-data model, or
  report the number as a lower bound; state which.
- Accept ~~an optional~~ **a developer-supplied** benchmark file (utterance → expected label,
  plus utterance → `wildcard` escalation cases). This is what the application team built by hand
  and it is the only thing that told them the truth. **[AR1] It is the primary generalisation
  instrument, not an option** — persona holdout cannot substitute for it, because both sides of
  a persona split are drawn from the same conditional distribution.
- **Enforce disjointness** between any benchmark file and the seed table, and fail the run
  on overlap. The external harness caught a real leak this way; without the check a benchmark
  silently decays into a memorisation test the first time someone pastes a failing case
  into their seeds to "fix" it.
- Report `top-1`, `in-list`, and **escalation recall** separately. Keep the existing
  in-distribution F1 but label it as such.

### R2 — Determinism

- A single `TRAINING_SEED` config value seeds `random`, `numpy`, and `torch`.
- Persist, per command, the seed and the **persona IDs actually used**, so a run can be
  reproduced and so cached utterances (R6) carry provenance.
- Document that unseeded runs on a benchmark of a few hundred cases exhibit ~20% verdict
  churn, and that differences below that are not interpretable from a single run.
- **Seeding the RNGs is not sufficient [AR5].** `train()` iterates
  `context_set_for_training`, a `set` of context-name strings
  (`model_pipeline_training.py:820-823, 829`), so visit order follows string hashing and varies
  with `PYTHONHASHSEED` — which `TRAINING_SEED` does not touch. Visit order is load-bearing
  because `context_utterance_cache` is shared across contexts within one run and is written by
  two paths that populate different command sets. R2 must therefore also make the training
  order deterministic (sort the context set) and make the in-run cache order-independent.
  R2's acceptance test — two runs with the same `TRAINING_SEED` producing identical artifacts —
  fails without this, and would fail intermittently rather than reliably.

### R3 — Robust generation

- Retry `RateLimitError` with exponential backoff.
- On terminal failure, return `[command_name] + seed_utterances` — never `[]` — matching
  the existing `datasets`-missing path.
- Emit a per-command table at the end of training: seeds, generated count, final row
  count, whether it fell back, and per-command held-out score once R1 lands.
- Fail the run, or warn loudly, when any command's row count falls below a floor.

### R4 — Versioned artifacts

- Write to `___command_info/<version>/` with a `current` symlink or pointer file.
- Never destroy a previous version implicitly; prune on explicit request.
- ~~This makes R5 safe (merge new work beside old)~~ **This makes R5 *recoverable*, not safe
  [AR3]** — see the amended D8. It does make R7/R8 possible (score two versions on identical
  cases), which is unaffected.
- **Two further obligations, which are what actually make a merged version safe [AR3]:**
  - A **per-version manifest** recording, for each context, the fingerprint of every command
    utterance set that entered it — its own commands *and* the ancestor commands that
    contributed to its `wildcard` class — plus the seed and persona IDs. This is R6's
    fingerprint stored at context granularity.
  - A **promotion-time consistency check** plus an **atomic pointer flip**: refuse to advance
    `current` to a version in which any context's recorded ancestor-contribution fingerprints
    disagree with the fingerprints actually present in that same version, and flip the pointer
    once, after the whole set validates. This re-derives R5's closure as a postcondition rather
    than trusting the dirty-set computation, so a closure bug (of exactly the kind AR2 found) is
    caught at promotion instead of shipped. A crash mid-merge must leave `current` on the old
    version, not on a set that is neither old nor new — which would be F5 again.
- Consider the shared-encoder refactor (F11) here: it changes what a "version" costs from
  8.6 GB to something a developer can keep ten of.

### R5 — Selective training

`fastworkflow train <workflow> [--command C] [--context X] [--changed-only]`

Retraining a single command is not local, and the design must respect that.

The original three closure bullets are replaced by a single rule [AR2] which subsumes the first
and corrects the other two. They are retained here for the record:

> - ~~A context's classifier must be retrained if **any** of its own commands changed.~~
> - ~~A context must **also** be retrained if any of its **ancestors'** commands changed,
>   because those utterances form its `wildcard` class (F6). This is the non-obvious
>   dependency and the main reason to specify this carefully.~~
> - ~~Contexts that inherit a changed command through the `base` axis must be retrained.~~

They are incomplete: they treat the two inheritance axes as independent when the code composes
them. **Corrected closure rule [AR2].** Let `commands(X)` be the effective command list from
`CommandContextModel.commands` (`command_context_model.py:222-266`) — `base`-resolved and
simple-name-shadow-resolved — and `anc(X)` the parent-chain closure from
`get_ancestor_contexts` (`command_context_model.py:169-215`). For a changed command `C`:

```
Carriers(C) = { X : C ∈ commands(X) }
Dirty(C)    = Carriers(C) ∪ { X : anc(X) ∩ Carriers(C) ≠ ∅ }
```

The composition is the point. `cache_ancestor_utterances` collects an ancestor's utterances via
`context_model.commands(ancestor_ctx)` (`model_pipeline_training.py:786-799`), which is
`base`-resolved, so a command reaches a context's `wildcard` class through **any** ancestor that
inherits it — the command's home context need not be an ancestor at all, and need not sit on that
context's parent chain anywhere. Expansion must therefore run over `base` **first**, then over
`parent`. The union of the two original bullets omits exactly the term
`{ X : anc(X) ∩ (Carriers(C) \ {home}) ≠ ∅ }`.

Two constraints on implementing it:

- Compute `Carriers(C)` by **membership-testing resolved `commands(X)`**, never by walking the
  raw `base` graph. `commands()` resolves simple-name shadowing
  (`command_context_model.py:256-259`): a derived context that defines its own `status` does not
  carry the base's `status` and must not be retrained for it. In `tests/todo_list_workflow`,
  `TodoList` declares `base: ["TodoItem"]` and carries `TodoItem/status`, `TodoItem/assign_to`,
  `TodoItem/description`, but shadows `TodoItem/get_properties` and `TodoItem/set_properties`
  with its own.
- Where a workflow roots its hierarchy at the `*` context, `*` is an ancestor of everything and
  a change to an unqualified global command dirties the whole workflow. That is correct, not a
  bug, but `--changed-only` should say so rather than look broken. Rooting at `*` is a
  convention, not a rule: `tests/todo_list_workflow` and `examples/todo_list` do it,
  `examples/messaging_app_4` does not.

Remaining bullets stand:

- `--changed-only` should compute the dirty set from command-file fingerprints plus the
  utterance cache from R6, then close it over both axes in the order above.
- The output must state which contexts were retrained and which were carried forward, so
  the developer can see the closure that was computed.

### R6 — Utterance persistence

- Persist generated utterances per command, keyed by a fingerprint of (seed list, persona
  IDs, generator config, seed value).
- Default to reuse when the fingerprint matches; `--regenerate-utterances` forces a
  refresh.
- ~~Support **aggregation** across runs: a developer who runs generation three times with
  different seeds should be able to union the results rather than replace them, which is
  the cheapest available variance reduction and directly feeds R8.~~ **Superseded
  2026-08-03:** the shipped trainer has one fixed seed and exposes only exact-seed reuse
  plus explicit regeneration. No user path could select aggregation, so the dormant mode
  and its tests were removed rather than preserving a second, unreachable cache policy.
- Cache invalidation must be conservative: any change to the seed list invalidates that
  command, and by R5's closure rule ~~dirties every descendant context's wildcard class~~
  **dirties `Dirty(C)` as corrected by AR2 — the carriers of the command under `base`, and the
  parent-descendants of all of them, not only the descendants of its home context**.

### R7 — Intelligent wildcard construction

Four parts, in dependency order:

1. **Split the label.** Give the parameter-extraction placeholders their own label so the
   escalation classifier is not trained on `"france"` (F6).
2. **Cap by budget, preserving coverage.** ~~Size the ancestor contribution relative to the
   average real command class rather than letting it arrive at 10×.~~ **Superseded by AR4:**
   "3× the average real command class" is a constant fitted on one workflow at one value, and
   the one experiment that tested it cannot distinguish 3× from uncapped (§2: routing p = 0.25,
   escalation p = 0.38), let alone 3× from 2× or 5×. Normalising by the mean is also the wrong
   statistic — an unweighted cross-entropy responds to the ratio against the **smallest** real
   class, and the mean is dragged upward by the large ones. Sizing rule as amended:
   - **Derive the budget from a training-time target, not a class-balance target.** Training
     cost is the only effect the cap was measured to have (44% reduction, 3h35m → 2h00m, D3),
     so it is the only quantity the constant can be principled about. No accuracy claim then
     attaches to it.
   - **Floor the budget at one utterance per ancestor command.** This *is* principled: it is
     the minimum that satisfies the escalation requirement the wildcard class exists to serve,
     and it is derived rather than fitted. The former workflow-specific statement, "`Exception`
     has 33 ancestor intents, so the floor is 33 against a budget of 170", came from the
     unavailable app-side prototype and is not reproducible from this checkout. The algorithmic
     coverage rule stands; the workflow-specific counts are retracted. [AR6]
   - **Core commands are not ancestor sources and do not count toward the floor** (`fix-4ej`).
     `command_routing` unions the core commands into *every* context, so a core command is
     already a local label wherever it could be escalated to: it has no escalation requirement
     to satisfy, and every one of its rows is removed as locally valid before selection. Counting
     it would add a source the coverage pass can never give a row to — making the floor a claim
     about coverage the selection does not honour — and would double-count, since those same rows
     are already in the descendant's own row count and a row cannot be both the local data the
     ratio bounds and the ancestor data it is bounded against. This is also what makes the
     population independent of visit order rather than merely deterministic in it; see the
     correction under AR5 for why ordering alone did not achieve that.
   - If a class-balance justification is wanted later, normalise against the smallest real
     class (or a stated quantile), state the invariant being preserved, and sweep the ratio
     over {1, 2, 3, 5, ∞} on **at least two workflows**, paired, on both R1 axes, after
     establishing the noise floor. One workflow at one ratio cannot distinguish a rule from a
     constant, and at 20.6% verdict churn a single-run sweep over 446 cases is uninterpretable.

   Selection, unchanged by AR4, must be **round-robin across ancestor commands**, so a context
   with 40 ancestor intents keeps all 40 represented instead of spending the budget on
   whichever commands generated the
   most text. Because `_get_utterances` returns `[command_name] + seeds + synthetic`
   (`generate_synthetic.py:158`), taking earliest-first within each command preserves the
   hand-written seeds and discards the synthetic tail first. Reference implementation in
   §7. **[AR6] The former reference-workflow `Exception` transformation — `2352 → 170` ancestor rows and
   `88% → 27%` wildcard share, with 33 ancestor intents represented — is retracted.** Current
   and pinned code expose multiple non-equivalent counts: raw per-command ancestor rows,
   de-duplicated rows assigned to `wildcard`, budget-selected rows, and local training tuples.
   The available numbers cannot be assigned to those denominators from any retained artifact.
   Even allowing whole-percent rounding, `2352` at 88% implies 306–336 own rows while `170`
   at 27% implies 449–471; the ranges do not overlap. With F8's former 42 own rows, 170
   wildcard rows would be 80.2%, not 27%. Do not cite any of these values as a before/after
   transformation. The round-robin coverage guarantee remains a property of the algorithm,
   but the workflow-specific count of 33 is not independently reproducible here.
3. **Add class weighting** (F9), which subsumes capping and handles imbalance among real
   commands.
4. **Do not discard a top-k `wildcard`** (F7). Decide explicitly between escalating and
   prompting rather than defaulting to a local prompt; at minimum, log that the signal was
   dropped.

Acceptance for this requirement is **both** axes measured (R1) and a paired test (R8), not
a single-run routing number. The measured cap looked like +2.7 points and was not significant.

### R8 — Convergence loop (skill, not code)

Delivered as `.claude/skills/fastworkflow-intent-training-convergence/`. Rationale for a
skill rather than a CLI flag: the loop is a judgement-bearing protocol — estimate the
noise floor, increase sample size, test paired, decide whether to continue — and it
composes with the existing house methodology skills rather than duplicating them.

The skill must: establish the noise floor by repeated identical runs before attributing
anything to a change; grow utterance sample size progressively; test paired with exact
McNemar; and stop when the per-step gain drops below the floor. It defers all statistics
conventions to `fastworkflow-proof-and-analysis-toolkit`.

  with wildcard share is −0.21, and capping did not close it.

- *On the second entry (wildcard imbalance and routing accuracy).* AR4 observes that the cap
  tested on the reference workflow was sized at 3× the **mean** real class, and that an unweighted cross-entropy
  responds to the ratio against the **smallest** real class. On that workflow's 4-to-23-command label
  spaces the tested cap may therefore have left the smallest classes still heavily outnumbered.
  This **weakens the negative** — it makes "capping did not help" weaker evidence against

  under-tested. Do not read this as support for it.
- *On the third entry (deep-versus-shallow gap).* AR2 supplies a previously unnoticed candidate
  mechanism: because ancestor commands are collected through the `base`-resolved

  heterogeneous wildcard classes than the parent-only model predicts, and the wildcard-share
  figures in F8 may understate the composition difference. This is a candidate, unmeasured,
  and the −0.21 correlation is unchanged. The entry stands.
- *On the first entry (contentless seeds).* The mechanism by which short pronoun-only seeds
  could act is now specified: `generate_synthetic.py:49-55` unions every word of every seed
  into `utterance_patterns`, which is injected verbatim into the generation prompt at line 89
  as "use varied phrasing based on these themes". Contentless seeds thus contaminate the
  phrasing instruction for **all** of a command's utterances, not only their own row. This is a
  route to an effect, not evidence of one. Still untested, still not refuted.

### AR1 — persona holdout removes duplication, not distribution

D1 claimed that "holding out every utterance produced by personas *k*..*n* is a real
generalisation test". It is not. Reading the generator (`generate_synthetic.py:40-107`), every
persona for a given command is conditioned on three things that are identical across the split:
the full seed list, injected verbatim as `utterance_string` (`:56`, `:82`); a keyword bag
`utterance_patterns` built from the union of every word of every seed (`:49-55`) and injected as
"use varied phrasing based on these themes" (`:89`); and the command name itself (`:87`). What
persona holdout removes is the persona-specific stylistic conditioning — the one factor that
varies. Both halves remain draws from the same conditional distribution over phrasings.

There is a second, sharper dependency. Personas are generated `personas_per_batch` at a time in
a single `litellm.completion` call (`:59-61`, `:112-119`), so a batch's utterances are jointly
sampled: persona 5's text is produced in a context that already contains personas 1-4's text.
A holdout that splits mid-batch shares the sampler, not merely the prompt.

D1 survives in the weaker form now recorded: persona holdout strictly dominates the random row
split of F1, because it removes within-persona paraphrase pairs, and it is worth building. It
does not license the phrase "generalisation test", and it cannot demote the developer-supplied
benchmark to optional. Note also that the residual — the leak persona holdout leaves — is
exactly the vocabulary the prompt injects, so it is not small.

**Cheap detection, no training run required.** Both checks are string operations over R6's
cached utterances:

1. For each held-out utterance `u` of command `c`, compute
   `ov(u) = max over v in train(c) of |tokens(u) ∩ tokens(v)| / |tokens(u)|`. Report the median
   and the fraction at `ov ≥ 0.8`, separately for a random-row split, a persona split, and the
   hand-written benchmark. If the persona split's distribution sits nearer the random split than
   the benchmark, it is still measuring memorisation, and the gap between the two is the size of
   the residual leak.
2. More directly diagnostic of the mechanism above: the fraction of each held-out utterance's
   content tokens that appear in `utterance_patterns`. That bag is in the prompt for both sides
   of any persona split, so a high figure is direct evidence of prompt-induced vocabulary
   leakage that no persona split can remove.

### AR2 — the closure was incomplete; `base` and `parent` compose

fastWorkflow has two inheritance axes and D5 modelled only one. `base`
(`_commands/context_inheritance_model.json`) pulls a context's commands into a derived context's
own label space, resolved by `CommandContextModel.commands`
(`command_context_model.py:222-266`). `parent` (`context_hierarchy_model.json`) drives
`get_ancestor_contexts` (`:169-215`) and determines whose utterances become a context's
`wildcard` class. The two never interact inside the context model — `get_ancestor_contexts`
reads only `parent`.

They interact in the trainer. `cache_ancestor_utterances` enumerates an ancestor's commands with
`crd.context_model.commands(ancestor_ctx)` (`model_pipeline_training.py:792`), which is
`base`-resolved. So a command reaches a context's wildcard class through **any ancestor that
inherits it**, and the command's home context need not be an ancestor of that context, nor sit
anywhere on its parent chain. D5 expanded over `parent` from the home context only; R5's third
bullet expanded over `base` only; their union still omits
`{ X : anc(X) ∩ (Carriers(C) \ {home}) ≠ ∅ }` — the parent-descendants of the *base-derived*
carriers. The corrected rule is in R5.

`tests/todo_list_workflow` carries both models and shows the bridge concretely: `TodoList`
declares `base: ["TodoItem"]`, `TodoItem` declares `parent: ["TodoList"]`, and
`commands("TodoList")` resolves to a list containing `TodoItem/status`, `TodoItem/assign_to` and
`TodoItem/description` while shadowing `TodoItem/get_properties` and `TodoItem/set_properties`
with its own. That workflow's own topology is degenerate for this bug — `TodoList` has exactly
one child, `TodoItem`, which owns the same commands, so `model_pipeline_training.py:872-873`
subtracts them back out as `context_utterances` and the discrepancy self-cancels. The smallest
reproduction needs a **sibling**: give `TodoList` a second child that does not inherit from
`TodoItem`, and that child's wildcard class fills with `TodoItem/*` utterances while neither the
original D5 rule nor R5's `base` bullet marks it dirty when `TodoItem` changes. This
self-cancellation is why the gap is invisible on the repo's shipped workflows and why it would
have surfaced first on a customer workflow.

### AR3 — versioning buys recovery and comparison, not safety

D8's ordering conclusion is right and is strengthened by this review; its rationale is wrong.
Versioning delivers two things: an immutable prior version the `current` pointer can be moved
back to, and the ability to score two versions on identical cases. Neither prevents an
internally inconsistent version from being produced and promoted. Selective training emits a
version in which some contexts were retrained under one seed and persona set and others were
carried forward from another; a carried-forward context's wildcard class was assembled from its
ancestors' utterances at generation time, and if an ancestor was regenerated while the
descendant was carried forward, that class no longer corresponds to the ancestor's live label
space. Versioning does not detect this. Rollback lets you undo it *after* you notice, and per F1
and F10 there is currently no signal that would let you notice.

"Safe" and "recoverable" are different claims and the spec conflated them. What would actually
make merging safe is the manifest, promotion-time consistency check and atomic pointer flip now
added to R4. The check matters most because it is *independent* of the dirty-set computation: it
re-derives R5's closure as a postcondition, so a closure bug of exactly the kind AR2 found is
caught at promotion rather than shipped. Note that this finding lands while `fix-551.7` (R4) is
already `in_progress`.

### AR4 — 3× the mean is a fitted constant, and the mean is the wrong statistic

Two separate defects. First, provenance: the ratio was chosen at 3 on one workflow, and the one
experiment comparing it to the alternative cannot distinguish 3× from uncapped on either axis
(routing p = 0.25, escalation p = 0.38) — so it certainly cannot distinguish 3× from 2× or 5×.
Expressing the budget as a ratio makes it scale-free, which is a real virtue, but scale-freedom
is not principle. Second, the statistic: to the extent class imbalance harms an unweighted
cross-entropy at all — which §8 records as not established — the quantity it responds to is the
ratio of the wildcard class to the **smallest** real class, not to the mean, and the mean is
dragged upward by the large classes. On that workflow's 4-to-23-command label spaces, 3× the mean can
leave the smallest real class outnumbered by an order of magnitude.

The escalation point estimate also moved the wrong way under the cap (91.9% → 83.8%), on the
axis the wildcard class exists to serve. It is not significant and must not be reported as a
regression, but it is the wrong sign for a change being justified on grounds unrelated to it.

The repair is in R7.2: size the budget from the training-time target, because cost is the only
effect the cap was measured to have (D3), and state the coverage floor — one utterance per
ancestor command — separately, because that floor *is* derived, from the escalation requirement
rather than from any workflow's numbers. It also makes explicit what round-robin (D4) is
actually guaranteeing.

### AR5 — a second source of nondeterminism that `TRAINING_SEED` cannot reach (new)

`train()` iterates `context_set_for_training`, a Python `set` of context-name strings
(`model_pipeline_training.py:820-823`, iterated at `:829`). Set iteration order for strings
follows their hashes, which are randomised per process unless `PYTHONHASHSEED` is fixed — and
`PYTHONHASHSEED` is not something a `TRAINING_SEED` value seeding `random`, `numpy` and `torch`
can affect. Visit order is load-bearing because `context_utterance_cache` is shared across
contexts within a run and written by two paths that populate different command sets:

- `cache_ancestor_utterances` writes `cache[ancestor_ctx][cmd]` for `context_model.commands()`
  only (`:792-798`), which excludes core commands — `Core` is popped from the filesystem-derived
  contexts at `command_context_model.py:122`, and `command_routing.py:253` unions the core
  commands back in separately when building `crd.contexts`.
- `train()`'s generation branch writes every command in `train_cmds`, which *is*
  `crd.contexts[ctx] | core_cmds` and therefore includes them (`:852-863`).

So a context first visited as an ancestor of an earlier-trained context takes the cached branch
(`:841-849`), where `if cmd_name in map_cmd_2_uttlist` silently skips every command absent from
the cache. On `tests/example_workflow` that is `IntentDetection/go_up`,
`IntentDetection/reset_context`, `IntentDetection/what_can_i_do` and
`IntentDetection/what_is_current_context` — four labels that contribute zero rows and never
enter that context's classifier. This is F3's failure mode reached by a different mechanism, and
like F3 it is silent.

Read from code; **not reproduced by execution** — training was out of scope for this review.
Cheap reproduction, no LLM calls needed: run `fastworkflow train tests/todo_list_workflow` twice
under different `PYTHONHASHSEED` values and diff the per-context label encoders. The consequence
for the spec is recorded against R2, whose acceptance criterion as written would fail
intermittently. Whether this contributes materially to the 20.6% churn in §2 is **not
established** and should not be assumed; it is a second candidate mechanism alongside the
unseeded RNGs, and the `PYTHONHASHSEED` experiment above separates them.

**Correction — the asymmetry had two consequences, and ordering closed only one of them.**
The framing above treats it as a determinism defect throughout, which reads as though a
stable visit order is the whole repair. It is not, and the two halves were fixed by
different mechanisms two beads apart:

- **The label loss** (core-command labels never entering a context's classifier) was closed
  by `fix-9mo`, and **sorting is not what closed it**. Sorting the context set made *which*
  contexts lost their labels deterministic rather than per-interpreter; the loss itself
  stopped only when the cached branch was made to fill in the commands missing from
  `map_cmd_2_uttlist` instead of skipping them.
- **The escalation coverage floor** was not fixed by either, and stayed open until `fix-4ej`.
  The floor is derived from whatever the shared cache holds when a descendant reads it, so
  ordering the visits only made the floor's value predictable: **a stable order is still an
  order**, and the floor still took whichever value the first visitor wrote. Renaming a
  context changed alphabetical position, which changed which path filled its cache entry
  first, which changed a *sibling's* escalation budget — spooky action at a distance with
  nothing in the diff to explain it. `fix-4ej` removed the dependency rather than
  stabilising it, by filtering core commands out of the escalation population at the single
  point it is derived (`class_balance.group_ancestor_utterances(..., skip_commands=...)`).

So do not reason from AR5 that a deterministic visit order makes the escalation population
order-independent. It makes it *reproducible*, which is a weaker property, and the two were
conflated here.

### AR6 — R7.2's `Exception` figures are retracted (resolved)

The original text combined three claims: F8's `42` own / `312` wildcard / `88%`; R7.2's
`2352 → 170` ancestor rows; and R7.2's `88% → 27%` wildcard share. The first ratio is
arithmetically valid: `312 / (42 + 312) = 88.1%`. The combined transformation is not.

The pinned trainer first stores raw per-command utterance lists, then unions them into a set
(`cache_ancestor_utterances`, `model_pipeline_training.py:784-801` at `23dbe35`), then subtracts
local utterances and unions the eight old wildcard literals before assigning the `wildcard`
label (`:839-876`). The current trainer separately counts local tuples as `own_rows`, regroups
raw ancestor lists, and globally de-duplicates while selecting the budget
(`model_pipeline_training.py:971-1048`; `train/class_balance.py:239-354`). Thus raw candidate
rows, de-duplicated label rows, selected rows, and own rows are all legitimate but different
denominators.

A deterministic no-training reconstruction can make 2,352 raw ancestor-list entries collapse
to 304 unique ancestor utterances; adding the pinned wildcard command's eight literals yields
F8's 312 model rows, and the current round-robin selector can retain 170 while representing all
33 synthetic sources. This proves denominator mixing is possible. It does **not** recover the
That measurement. With 42 own rows, the selected share would be `170 / (42 + 170) = 80.2%`, not
27%. More generally, if the percentages are rounded to whole points, 2,352 at 88% requires
306–336 own rows while 170 at 27% requires 449–471, so no fixed denominator reconciles them.

An exact checkout-wide search found no external reference workflow, training harness, row-count report, or
training artifact; the only retained occurrences of these values are this document itself.
Therefore the evidence cannot determine which original value was transcribed incorrectly or
which unrecorded denominator was used. The correct disposition is an explicit retraction, not a
guessed correction. R7.2 and F8 now mark the `Exception` figures non-citable. The general
round-robin coverage property remains established by code, but the workflow-specific count of 33 is
also not independently reproducible and is not cited.

### M1/M2 — `wildcard` is an escalation signal, never an out-of-scope sink

Probed the committed `examples/retail_workflow` `global` context (20 labels, no ancestors,
so its `wildcard` class held exactly the pre-split 8 rows) by calling `CommandRouter.predict`
directly. Out-of-scope prose predicted `wildcard` in **0 of 6** cases; `wildcard` was predicted
for **3 of 4** bare values (`france`, `id=3636`, `/path/to/my/object`). In a context *with*
ancestors the class is trained on ancestor-command utterances, which are in scope for a parent.
Nothing anywhere is trained to recognise "this belongs to no command at all".

The ruling to drop `WILDCARD_LABEL` where `ancestor_utterances - context_utterances` is empty
(F6/R7.1) is therefore safe: the seven bare-value literals move verbatim to
`PARAMETER_VALUE_LABEL`, both labels are non-routable, both yield `command_name=None`, and in a
root context both terminate the parent walk at `you_misunderstood`. Identical outcome.

What the probe *did* find is that out-of-scope rejection does not exist:

```
'book me a flight to Tokyo'              -> ROUTES to IntentDetection/what_can_i_do
'please summarise the french revolution' -> ROUTES to IntentDetection/reset_context
```

Both are single confident predictions, which `intent_detection.py:182` routes without
prompting. The only rejection mechanism is the ambiguity threshold in
`CommandRouter.predict` (`model_pipeline_training.py:321-334`), and for retail it is
**0.2395 / 0.3392** — anything clearing ~24–34% confidence executes. Those thresholds are not
a calibrated operating point; they are computed at `:1174-1190` as the *mean confidence of
misclassified test samples*, a descriptive statistic of the training run.

### M4 — seeding cannot make training reproducible while an LLM generates the data

Two full training runs of `examples/hello_world`, same `TRAINING_SEED=42`, same code, same
environment, back to back, comparing the per-command utterance sets in
`training_provenance.json`:

```
IntentDetection/go_up                    DIFFERENT   A=28 rows  B=31 rows
IntentDetection/reset_context            DIFFERENT   A=25 rows  B=23 rows
IntentDetection/what_can_i_do            DIFFERENT   A=38 rows  B=34 rows
IntentDetection/what_is_current_context  DIFFERENT   A=29 rows  B=24 rows
add_two_numbers                          DIFFERENT   A=24 rows  B=29 rows

0/5 commands produced identical utterance sets at the same seed.
```

`TRAINING_SEED` fixes `random`/`numpy`/`torch`, persona selection and the `train_test_split`
indices. It cannot fix the LLM. The **training data itself** varies run to run, in both text
and row count, so seeding a shuffle over a different dataset does not yield a reproducible
model.

This inverts part of **D6**, which sequenced the utterance cache as a consumer of determinism.
The dependency runs both ways and this is the binding direction: **R6 (`fix-551.9`, raised to
p0) now blocks R2 (`fix-551.2`, p0)**. R2's acceptance test must be "two consecutive runs at the
same seed produce byte-identical per-context artifacts", which is unreachable until utterances
are persisted and reused. It also means R1's paired comparisons are not yet meaningful: two runs
differ in their training data, so any score delta confounds the change under test with a fresh
draw of utterances.

It also explains, without appeal to test pollution, why
`test_train_modern_stack.py::test_trained_model_routes_utterance` behaves differently standalone
and in-suite. Each run trains on different data.

## 12. Post-integration measurements (waves 2–3)

### M5 — the utterance cache closes M4's gap, but it was only half the problem

With R6's utterance cache installed, `examples/hello_world` at `TRAINING_SEED=42` goes from
**0/5** identical per-command utterance sets to **5/5**, and `training_provenance.json`
becomes byte-identical between two consecutive runs.

That is necessary but not sufficient. `generate_dspy_examples`
(`utils/generate_param_examples.py`) is a **second** LLM-driven generation path, unseeded and
at a hardcoded temperature of 0.9, writing `<command>_param_labeled.json` on every train. R6
does not touch it. Caching it too (`train/param_example_cache.py`, `fix-czb`) moves the
parameter files from 0/1 to 1/1 identical on `hello_world` and from 0/5 to 5/5 on
`messaging_app_4`.

The generalisable lesson is that "is training reproducible?" must be asked once per generation
path, not once per repository. Nothing in the design of R6 suggested a second path existed;
it was found by asking what else calls an LLM during `train`.

### M6 — §11's measurement methodology is too weak to detect its own failure

**M4 and the R2 acceptance test both measure on `examples/hello_world` only, and that
workflow structurally cannot detect a whole class of reproducibility bug.**

A first implementation of the parameter-example cache scored 5/5 on `hello_world` and only
**2/5** on `messaging_app_4`, with every individual example byte-identical. The cause: a
generated example is assembled in regex-match order (`command`, then strings, then bools, then
numbers), while its cached twin round-trips through `json.dump(..., sort_keys=True)`. The two
dicts compare **equal** and serialise to **different bytes**. `hello_world` cannot expose this,
because its fields (`command`, `first_number`, `second_number`) are *already* in alphabetical
order, so the two orderings coincide by accident.

Fixed by canonicalising on both the generation and the cache-hit paths, which removes the class
of problem rather than making one serialiser match the other.

**Consequence for this spec:** any future determinism claim must be measured on at least one
workflow whose parameter fields are not in alphabetical order. A single-workflow reproducibility
claim is not evidence, and §11's methodology should be read as under-powered rather than
authoritative.

### M7 — fine-tuning was already reproducible; the LLM paths were the whole problem

Trained artifacts (`tinymodel.pth`, `largemodel.pth`, `threshold.json`, both ambiguous
thresholds, `label_encoder.pkl`) were byte-identical across two runs in **every** condition
measured — 24/24 on `hello_world` and 96/96 on `messaging_app_4` — *including* the cache-off
runs where the training data itself differed. `determinism.seed_everything` is sufficient here.

Scope of the claim, stated precisely because it is easy to over-read: this is an empirical
result on one machine (CUDA present) across two workflows. Nothing sets
`torch.use_deterministic_algorithms` or `cudnn.deterministic`, so a different GPU, a different
cuDNN, or changed batch shapes could reintroduce drift. The claim R2 can honestly make is
"identical artifacts across two runs at a fixed seed, measured on `hello_world` and
`messaging_app_4`, on a CUDA machine without deterministic-algorithm enforcement" — not
"training is deterministic".

### M8 — R7.2/R7.3 do not fix `fix-2m5` on `hello_world`, and the target is unreachable there

> **Superseded in scope by M10.** Everything below is `hello_world`, and the curve does **not**
> replicate on retail. Read M8 as a single-workflow observation, not a property of the system.
> That this section had to be corrected within a day of being written is the strongest available
> argument for M6.

Capping `parameter_value`'s row count trades one failure mode for another, monotonically:

```
rows=7 (current)   targets 14/20   routing 41/60   bare-value catch 30/35
rows=4             targets 17/20   routing 47/60   catch 22/35
rows=2             targets 19/20   routing 52/60   catch 12/35
rows=0             targets 20/20   routing 57/60   catch  3/35
```

Roughly two to three points of bare-value catch lost per point of routing gained. There is no
setting where both halves of `fix-2m5`'s acceptance criterion hold. Class weighting (R7.3) is
independently a **null result** — McNemar p = 0.72 / 1.00 / 0.51 across three schemes on paired
data — and was not shipped.

Proposed mechanism: `parameter_value`'s rows are contentless by construction (`"3"`,
`"16.7,.002"`), so the class has no semantic centre and its decision region is defined only by
distance from everything else. Row count and class weight are then the same knob on the same
region. **This mechanism is inferred from one 5-command workflow and is not yet replicated**;
`fix-cm2` (a pre-classifier gate) is predicated on it and should not be built until it is.

### M9 — §4's framing of R7.2 as the `fix-2m5` lever does not survive measurement

R7.2's budget never binds on `parameter_value`, which is 7 fixed rows that do not grow with
workflow size. R7.2 is still worth shipping, but only for `wildcard`, whose row count grows
with the ancestor chain. The requirement text should be read as scoped to the escalation class.

### M10 — the trade-off does not replicate, and retail's failure is the inverse of `fix-2m5`

30 runs on `retail_workflow` (6 arms × 5 seeds). Provenance is structural rather than asserted:
the committed artifacts contain `wildcard` and no `parameter_value`, every fresh run contains
`parameter_value` and no `wildcard`, and the harness copies the workflow excluding
`___command_info`, so the stale artifacts could not have been read.

| `parameter_value` rows | routing top-1 | Δ | p | bare-value catch |
|---|---|---|---|---|
| 7 (current) | 61.1% | — | — | 5/35 |
| 4 | 63.1% | +1.9pp | 0.450 | 10/35 |
| 2 | 63.6% | +2.5pp | 0.298 | 0/35 |
| 0 | 60.6% | −0.6pp | 0.906 | 0/35 |

Three things follow, and each contradicts something this document previously asserted.

**1. There is no curve.** Retail spans 3.0pp non-monotonically with no significant arm, against
`hello_world`'s monotone +26.7pp. Capping to 4 rows improved *both* axes, which a trade-off model
cannot produce. M8's curve is a property of a 5-command workflow, not of the design.

**2. `fix-2m5`'s premise is absent at retail scale.** `parameter_value` takes top-1 on **0 of 360**
routing cases (Wilson 95% [0.000, 0.011]), median rank 15th of 20. The mechanism is nonetheless
*real* — P(`parameter_value`) rises 2.5× as utterances shorten (p = 1e-5), and it anti-correlates
with the best real command (Spearman ρ = −0.405) — but P(`parameter_value`) never exceeds
P(best real), by an 11.9× margin at the shortest inputs. **Real force, negligible effect.** The
sharpened mechanism, which survives both workflows: a contentless input goes to whichever class
holds the most low-content *training rows*, not to whichever class is contentless by construction.
On retail that class is `calculate`, a real command whose seed utterances are arithmetic; it takes
24 of 70 bare values outright.

**3. The largest effect was in the direction nobody swept.** Going *up*, to 28 diverse literals,
took bare-value catch from 5/35 to **35/35 at every seed** for −0.8pp routing (p = 0.804). On
retail `parameter_value` is not too strong and stealing commands; it is **too weak to do its job,
and fixable with coverage**. This inverts `fix-cm2`'s premise and exposes a hazard in it: a lexical
pre-gate would intercept `"32 * 4"` and `"id=3636"`, making `calculate` unreachable from its own
natural input. `fix-cm2` should not be built.

**Variance floor is exactly zero.** Two byte-identical runs agreed on all 555 probes at every seed,
so every within-seed difference above is attributable to the arm. This also retires the "~20%
churn" attributed to torch in F2: it was resampling, which R6 has since removed.

**Seeds required.** Five is the floor (7pp detectable). A ~2pp effect needs >20 seeds and is not
worth buying. Because the variance floor is zero, seeds buy generalisation across draws rather than
noise reduction — which is a different argument for them than the one usually made.

### M11 — a prompt-template echo was contaminating every workflow's training data

`fix-iy0`. The synthetic-utterance system prompt demonstrates its output format using the literal
word `utterance` as the placeholder:

```
[Persona_Name]
utterance
utterance
```

Models periodically copy that scaffolding through instead of filling it in, and neither existing
filter caught it: `utterance` is nine characters, so the `len(u) > 3` guard passes it, and it does
not start with `[`. The token was therefore trained as a **positive example of whatever command was
being generated** — 21 of 412 rows (5.1%) on retail, spread across seven real commands at once, so
the classifier was shown one identical string carrying seven conflicting labels. Confirmed
independently in cached artifacts (`list_all_product_types` had 7 such rows).

Fixed by filtering echoes at the point of extraction, not by rewording the prompt: rewording changes
what the model is asked to produce, and so changes the training-data distribution for every command
in every workflow in a way nobody has measured, whereas dropping an echo removes a row that was
never an utterance. The filter is included in the R6 cache fingerprint alongside the generator,
because a post-filter decides which rows become training data just as surely as the prompt decides
which rows exist.

**This is a confound for every measurement in §11 and §12**, all of which trained on contaminated
data, and it pushes in the direction of the observed results. The M10 arms are paired on cached
utterances, so they remain internally valid as comparisons; their absolute numbers are not a clean
baseline and should be re-measured.

**Post-fix update — the decision-relevant M10 baseline has now been re-measured cleanly.**
Five fresh `pv7` runs at seeds 42/7/1234/2026/99 harvested 95 new cache entries containing
**0 template echoes in 2,028 generated rows**. `parameter_value` still stole **0/360** routing
cases (Wilson 95% [0.000, 0.011]), clean held-out catch remained weak at **6/35** (versus 5/35
before), and routing top-1 was 210/360 versus 220/360 (McNemar p = 0.326). M10's absolute
conclusion therefore survives clean data: shipped `pv7` is not stealing retail routes and is not
a reliable bare-value catcher.

The treatment-arm deltas in M10 remain contaminated and formally unrevalidated. Re-running all
25 remaining trainings is not warranted because neither decision-driving absolute claim changed.
If a treatment is proposed for production — especially the 28-row `pv_diverse` arm — rerun only
clean `pv7` plus that treatment across the same five seeds. The decision-relevant durable results
are recorded above; run-specific scripts, benchmark copies, and generated result files were
removed after reconciliation.

### M12 — R5's value is thin, and the spec understated its risk

Shipped as opt-in `--changed-only`, defaulting off. Measured on `messaging_app_4` (the only
bundled example with more than one trainable context), R6 cache warm, one leaf command edited,
two identical copies trained back to back: **83.2 s full vs 62.9 s selective, a 24% saving**.
On `hello_world` selective was *slower* — 24.5 s vs 24.0 s — because the planner costs more than
it saves.

**The structural finding matters more than the percentage.** `hello_world` and `retail_workflow`
each train exactly **one** context (`*`); all 19 retail commands are global with no context
subdirectories. Selective retraining cannot help either, by construction. The floor of ~25 s is
mostly DSPy parameter-example generation, which `--changed-only` does not skip, and the marginal
per-context fit is roughly 6 s — so the flag begins to pay for itself somewhere north of ten
contexts, and no workflow in this repo is close.

Where §4 understates the problem:

**1. The closure is not the whole problem.** §4 frames R5 as "which contexts are affected by a
changed command". That question is real and its answer is subtle — the base and parent axes
compose, so `AdminSession`'s wildcard class carries `Account/close` even though `Account` is
nowhere on its parent chain — but it structurally cannot answer *"would this workflow produce
this model today"*. A `context_inheritance_model.json` edit removes commands from a label space
with **every command file byte-identical**. Roughly half of R5's implementation is a recorded
`TrainingSignature` (per-context label space, ancestors, wildcard sources; global seed, model
ids, persona source, generator digest, reserved-label constants, and a hand-bumped
`ARTIFACT_FORMAT_VERSION`), which §4 does not mention at all.

**2. The R4 interaction is the dangerous part and is absent from the spec.** `publish_version`
removes the compatibility entry of any context its version does not contain. That is correct for
R4 and catastrophic for a naive R5: a selective run publishes a version holding only the
retrained context and thereby **un-trains the rest of the workflow while printing success**.
Anyone implementing R5 from §4 alone would ship exactly that. Carry-forward runs before publish
and raises rather than degrading, so a failure leaves the previous version current and complete.

**3. Absence of evidence was being read as evidence.** Two failure modes in the pre-existing
module converted an inability to check into a passing check: an unresolvable command fingerprint
returned `(None, None)`, which compared **equal to the next run's** `(None, None)` — so a command
whose source could not be read looked unchanged *forever* — and `build_context_maps` swallowed
ancestor-lookup failures and substituted a smaller command set, weakening precisely the axis that
is hardest to reason about. Both now force a retrain. The general rule, which generalises past
R5: a comparison that can fail must not fail *equal*.

**Recommendation: keep it opt-in and do not promote it to the default on this evidence.** The
closure logic is the genuinely hard part and is now written down, tested and audited, which is
worth having. But a false retrain costs minutes and a false skip costs a stale model that nothing
in the package would surface, so the tie must always break toward retraining.

### M13 — parameter-example validation failed open, then failed closed on long text

`fix-b8h`. `generate_dspy_examples` built `validated_examples` but transformed the original
unfiltered source list, so a rejected example still entered the runtime few-shot corpus. The first
investigation had measured zero rejections in 12 real command-runs and therefore could not say
whether this mattered. That zero was not evidence of quality; it was evidence the instrument was
broken. Pydantic v2 exposed a string annotation as `"<class 'str'>"`, while the regex parser
recognized only the literal type name `"str"`, so it extracted no string values and every example
passed vacuously.

The fixed path normalizes Pydantic primitive/optional field types and transforms only validated
source examples. A discriminating real-component test accepts `alice` from `"add user alice"` and
rejects hallucinated `mallory`; it also constructs the exact `dspy.Example` schema consumed at
runtime. A follow-on guard prevents optional unwrapping from flattening unrelated generic types
such as `list[str]`.

One isolated real-LLM draw over the five string-bearing commands in `messaging_app_4` parsed all
75 requested examples: 73 accepted, 2 rejected. Manual audit found **0 obvious hallucinations
among 103 accepted string values**, but both rejections were false positives on valid long
broadcast messages. The mechanism was structural: after exact matching failed on punctuation or
light paraphrase, fuzzy matching compared the entire 10+ word value against windows capped at
five words. Raising the global distance threshold enough to admit those messages would also make
short identifiers unsafe.

The matcher now keeps the original 1–5-word windows for short values and adds windows within two
words of a long value's own length. Revalidating all 105 string values from the real draw produced
zero invalid results, while the `alice`/`mallory` short-identifier rejection remains pinned.
Because `validate_parameters` source is part of the parameter-cache fingerprint, both corrections
invalidate stale cache entries automatically.

`fix-hru` then replaced regex field extraction with an AST + `literal_eval` parser; model-provided
text is never executed. It supports the actual workflow types inventoried in this checkout:
primitives, lists, dictionaries, unions/optionals, literals and enums. Parsed values are checked
against the Pydantic annotation, malformed values and missing required fields are rejected, and
omitted defaulted fields remain valid. Tuples, sets and arbitrary custom objects remain
deliberately unsupported because they do not round-trip through the runtime's JSON-shaped
few-shot schema. Numeric grounding is unchanged: numbers are type-checked but are not required to
appear textually in the utterance.

### M14 — shared encoders are a modeling redesign, not artifact deduplication

`fix-551.8` / F11 is retired. The disk problem is real: one context's TinyBERT + DistilBERT
artifacts occupy 287,342,019 bytes (274.0 MiB), so 33 independently trained contexts require about
8.83 GiB. A frozen shared-encoder layout with context-specific Tiny classifier heads and Distil
pre-classifier + classifier heads would be roughly 348 MiB at 33 contexts, a 96.1% / 26×
reduction.

That saving cannot be obtained by losslessly splitting today's artifacts. Training optimizes all
model parameters independently per context; sampled trained contexts shared **0/41 identical
TinyBERT tensors and 0/104 identical DistilBERT tensors**. Each artifact therefore contains a
different encoder, not one repeated encoder plus a different head.

The smallest coherent implementation would freeze one Tiny and one Distil encoder per workflow
version, train immutable context-specific heads, and introduce a dual-readable artifact schema
with shared encoder hashes and per-context head files. That changes the model being trained and
may reduce routing and escalation accuracy. Joint multi-context fine-tuning invalidates every head
on each encoder update and defeats R5 selective training; adapters/LoRA add serialization,
dependency, concurrency and runtime complexity.

R4/R5 already hardlink carried-forward contexts, so selective versions consume almost no
additional bytes. The remaining cost is one full artifact pair per genuinely distinct context,
retained full versions, and runtime model residency. Without a pre-registered five-seed
non-inferiority experiment on routing top-1/in-list and escalation recall, shipping frozen shared
encoders would exchange known model quality for storage savings. F11 is therefore explicitly
retired rather than left as an apparently simple packaging task.

### M15 — generation volume moves bare-value catch, but reserved share does not explain it

`fix-16d`. A five-seed paired sweep reused the exact clean post-`fix-iy0` utterance draws and
deterministically retained all, half, or one quarter of each command's generated rows. No LLM
redraw occurred. All-bare catch moved from **16/70 full → 60/70 half → 43/70 quarter**. Half
versus full fixed 46 cases and broke 2 (exact McNemar p = 8.36e-12); quarter was significantly
worse than half (4 fixed / 21 broken, p = 0.00091).

This accepts a narrow causal statement for the current model: generated-corpus volume and
composition materially affect the reserved class's ability to close bare-value turns. It refutes
the proposed monotonic explanation that a larger reserved share is always better. Half volume
has a smaller reserved share than quarter volume and substantially better catch; it also preserves
routing top-1 (211/360 versus 210/360 full, p = 1.0). The likely mechanism is a
composition/minimum-coverage optimum, not class share alone.

The historical committed model's 6/14 catch remains fundamentally unattributable. Its actual
generated rows, environment, persona draw, LLM responses, thresholds and training provenance were
not retained; its tiny checkpoint also differs. The clean full-volume seeds already span 0/14 to
7/14, so 6/14 does not require a volume change. No historical setting is inferred. Any future
volume proposal must test the observed half-volume arm prospectively rather than presenting it as
archaeology of the old artifact.

### M16 — generation provenance and context training are different dimensions

`fix-5vb`. A generated utterance set belongs to one fully-qualified command: the generator receives
`(workflow, command_name)`, not a context, and inheritance reuses that same set wherever the command
is a label. The previous trainer nevertheless reached generation through context-specific paths,
could redraw the same command, and stored provenance only by command name, so the last context's
record overwrote earlier use. A workflow-wide row count then concealed contexts where that command
was below the training floor.

Training now generates at most once per fully-qualified command and records two separate
dimensions in provenance schema v2:

- `commands`: one generation record per command (seed, personas, generated/final counts, fallback);
- `context_training`: one record per `(context, command)` with status `included`,
  `included_fallback`, `skipped_no_input`, or `skipped_no_utterances`, plus the actual labelled row
  count and reason.

The training report exposes both the aggregate row count and `rows_by_context`, but applies the
minimum-row floor to **every context independently**. A large inherited total can no longer hide a
starved context. Action-only commands and empty generators are explicit exclusions rather than
