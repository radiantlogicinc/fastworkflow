## 3. Proposed architecture and design

### 3.1 File layout (final state)

```
<workflow>/
  _commands/
    _split.py                  # split settings (moved from _skills/_split.py)
    _helpers.py                # any "_"-prefixed file: an importable helper, never a command
    send_greeting.py           # global execution command (defines ResponseGenerator)
    daily_digest.py            # global planning command  (defines PlanGenerator); its steps
                               #   navigate to the contexts whose commands they run
    Library/
      find_book.py             # execution command in context Library
      book_by_title.py         # planning command in context Library
      reserve_and_notify.py    # planning command in context Library
  context_inheritance_model.json
```

A planning command's steps run from wherever the workflow stands, like any
other steps (2.7). A planning command whose steps run a context's commands
therefore either lives in that context, so that it is matched only where
those commands are on the lookup path (3.9), or starts with steps that
navigate there, as talk_to_ido's global skills start at a hub (2.12).

The rules:

- **One command per file.** A file defines exactly one of `ResponseGenerator`
  or `PlanGenerator`:
  - both is a load error naming the file;
  - neither is today's behaviour for a broken command file.
- **The name is the file stem**, and the qualified name is
  `<Context>/<stem>` (just `<stem>` at the root), exactly as for execution commands
  today.
- **`_`-prefixed files and folders are never commands.** This is already
  true in `command_directory.py:263, 269, 276`.
- **A planning command and an execution command with the same qualified name is a load error.**
  This applies to both layouts during the transition (Phase 7).
- **`_skills/` is read until Phase 7 moves its files.** Its root files load as
  global planning commands, and its subfolders as context planning commands (Phase 1).
  After Phase 7, a workflow with a `_skills/` folder fails to load, with a
  message that names `_commands/` (2.23).

### 3.2 Writing a command at each granularity

The examples are files of the tutorial's sample workflow,
`fastworkflow/examples/library`, shortened. Every command below is in the
`Library` context, `_commands/Library/`, so no step needs to navigate before
it runs. `open_book` is a `Library` execution command that enters the `Book`
context (`descends_to = "Book"`) and returns the book's `book_uid`, `title`,
`author` and `copies`. Imports come from `fastworkflow` (`from_`,
`CommandResponse`) and from
`fastworkflow.planning` (`run`, `pick`, `count`, `listed`; the module is
renamed from `fastworkflow.skill` in Phase 8, 3.11).

Execution command, `Library/find_book`, returning its `Output` (3.14):

```python
class Signature:
    """Find books by title or author."""
    class Input(BaseModel):
        query: str = Field(description="words of the title or the author's name",
                           examples=["Middlemarch", "George Eliot"])
        start: Optional[int] = Field(default=None, description="the first row of the page")
    class Output(BaseModel):
        book_uids: list[str] = Field(description="the uid of each book found, in row order; open_book takes one")
        titles: list[str] = Field(description="the title of each book found, in row order")
        total: int = Field(description="how many books match, on every page")

class ResponseGenerator:
    def __call__(self, workflow, command, command_parameters: Signature.Input) -> Signature.Output:
        library = workflow.command_context_for_response_generation
        found = library.find_books(command_parameters.query)
        rows = page(found, command_parameters.start)
        return Signature.Output(book_uids=rows, titles=[library.books[u].title for u in rows],
                                total=len(found))
```

The framework wraps the returned `Output` into the `CommandOutput` callers and
clients receive, writes `response` as its JSON, and, because `start` makes
the command paged and `total` says how many rows there are, ends that text
with the next page when rows remain (3.14). A command with no `Output`
returns a `str`; one that writes its own text, or sends `artifacts`, returns a
`CommandResponse`; one that declines raises `fastworkflow.Refused`.

Planning command with one phase, `Library/note_member`:

```python
class Signature:
    """Add a note to a member's record."""
    class Input(BaseModel):
        member: str = Field(description="the member's name",
                            json_schema_extra={"in_request": True})
        text: str = Field(description="the note to add")

class PlanGenerator:
    def note(self, input):
        return [run("find_member", query=input.member),
                pick("open_member", named=input.member),
                run("add_note", text=input.text),
                "say whose record the note was added to"]
```

Each field describes the value this command takes, in words a person can
read (3.4, Descriptions): `member` is a whole name, not `find_member`'s
"words of the member's name". The preview shows the description of the
callee field each input is passed to beside it (3.7). `in_request` makes
the member's name a value the request must write, so nothing rewords or
invents it; `text` carries no option, so the extractor may tidy the note's
words. The option means the same on an execution command's field (3.4, The
argument path). `run` writes a step
code runs, quoting any value the step parser would misread, so a note that
ends in brackets reaches `add_note` whole (3.13). `pick` names the row to
open; code finds it in the listing `find_member` just read, and opens it
(3.13). `open_member` moves the
workflow onto the member, where `add_note` then runs. The last line is a
plain string, so the agent writes the answer. The command declares no
`Signature.Output`, so its `CommandResponse.output` is `None`. With one
phase, it runs as one executor run with the agent's step budget (3.5).

Phased planning command (today's skill idiom, with phases that hand on their
callees' `Output`s and a declared `Output`), `Library/book_by_title`:

```python
class Signature:
    """Show who wrote a book, and how many copies the library owns, given its title."""
    class Input(BaseModel):
        title: str = Field(description="the book's title",
                           json_schema_extra={"in_request": True})
    class Output(BaseModel):                     # public: no from_, as on an execution command
        found: bool = Field(description="whether a book was opened for the title")
        book_uid: Optional[str] = Field(default=None, description="the uid of the book opened")
        title: Optional[str] = Field(default=None, description="its title, as the library has it")
        author: Optional[str] = Field(default=None, description="its author")
        copies: int = Field(default=0, description="how many copies the library owns")

class PlanGenerator:
    def find(self, input) -> FindBook.Output:          # from .find_book import Signature as FindBook
        return [run("find_book", query=input.title)]
    def book(self, input, find) -> OpenBook.Output:     # from .open_book import Signature as OpenBook
        if not find.book_uids:
            return []
        return [pick("open_book", named=input.title)]
    def __result__(self, input, book):
        if book is None:
            return CommandResponse(response=f"No book matches {input.title}.",
                                   output=Signature.Output(found=False))
        return CommandResponse(        # copies: from ._wording, a _ helper over count
            response=f"{book.title} is by {book.author}; the library owns {copies(book.copies)}.",
            output=Signature.Output(found=True, **book.model_dump()))
```

Each phase hands on the `Output` of the command it runs, as it is (3.12):
`find` hands on `find_book`'s, and `book` hands on `open_book`'s, the record
actually opened. The phases' facts are private working memory; the `Output`
is the command's public result. `__result__` builds the answer and the
`Output` from the phases' facts, received by name, and returns them as an
execution command's `__call__` returns its result (3.14, 3.16).
`open_book`'s `Output` fields have the names of four of this command's, so
they pass straight through. `book` is `None` in `__result__` when the `book`
phase was skipped, with no default needed (3.4).

`pick` opens the book titled exactly as asked: code finds the one row of
`find_book`'s listing, read in the phase before, whose title is the
request's, or the listing's only row, and runs `open_book book_uid=...`;
when several rows are listed and none has the title exactly, the step goes
to the agent in pick words (3.13). The answer text
`__result__` returns is the call's answer as it is (3.16), and on the fast
path the user reads it as written (3.6). When nothing matches, it still
returns an `Output`, with `found=False`: a caller that reads this command's
`Output`, such as the sample's `book_loans`, would otherwise get no facts
and the warning of 3.14.

When the commands a phase may run are alternatives, a union annotation hands
on whichever ran, and Python reads it. The sample's `find_record`:

```python
class PlanGenerator:
    def find(self, input) -> FindBook.Output | FindMember.Output:
        return [run(FIND[input.kind], query=input.name)]
    def __result__(self, input, find):
        names = find.titles if input.kind == "book" else find.names
        return f"{input.name} matches {listed(names, find.total, input.kind)}."

FIND = {"book": "find_book", "member": "find_member"}
```

A facts model, whose every field is typed with a command's `Output` or
`Input`, is written when one phase's facts come from several commands: the
sample's `Book/shelf_report` (3.12).

Producer hint on any command input (replaces a bare `available_from`), from
`Library/open_book`:

```python
book_uid: str = from_("find_book.book_uids", description="the uid of the book to open")
```

`from_` on an `Input` field is a producer edge: the target is an `Output`
field. A `str` filled from one item of a `list[str]` passes the type check
(3.3, What each edge does), and the unqualified name resolves in
`open_book`'s own context.

### 3.3 `from_`: specification

**Location and exports.** Define `from_` in `fastworkflow/skill_phases.py`,
where `fact_from` is today, and export it from `fastworkflow` and from
`fastworkflow.skill` (both modules are renamed in Phase 8, 3.11).

```python
def from_(source: str | Sequence[str], **field_kwargs) -> Any
```

`from_` names the `Output` field a value comes from (2.3, 2.27), and is
declared only on a command's `Input` field, where it is a producer hint. It
has no `kind=` keyword: forwarding was dropped (2.27), and the copy meaning,
on a facts model's field, went with copy edges (2.33).

**What it returns.** `Field(**field_kwargs)`, whose `json_schema_extra` is
the caller's `json_schema_extra` (if any) with `{"from": source}` merged in.
Other keys the caller passes are kept. A hand-written
`json_schema_extra={"from": ...}` on an `Input` field is read the same way.

**Allowed keys on skill inputs.** `_spec_from_field` rejects any
`json_schema_extra` key outside `SKILL_FIELD_KEYS`
(`skill_commands.py:412`, today `strip`, `subject`, `verify`, `means`,
`in_request`). Add `"from"` and `"available_from"` to it, so that a planning
command's `Input` fields can carry producer edges. `"available_from"` is
only ever there because `from_` wrote it at load (What each edge does,
below). *Amended by 2.46:* the check keys are options of any command's
`Input` field (3.4, The argument path), so the list stops being a planning
command's; a field of either kind may carry `from_` beside them.

**Copy edges, until Phase 15.** `from_` never takes the copy meaning
(2.33). Copy edges keep today's spelling (`fact_from`, or a hand-written
`json_schema_extra={"from": ...}` on a facts model's field, as talk_to_ido's
`_phase_facts._from` writes them), today's resolution (`facts.fact_sources`
and `facts_from_runs`: an `Output` field before the run's `Input` field, and
a plain name resolved against the context the phase ends on) and today's
warnings (`check_phase_sources`), until Phase 15 retires them with the
facts models whose fields copy (3.12). Nothing new is built for them.
`fact_from` was never released, so it is removed then with no alias.

**Reference grammar.** `[<Context>/]<command>[.<field>]`, or a list of such
strings, for several commands that can supply one input.

- **Qualification is optional.** An unqualified `<command>` has one
  resolution rule, since `from_` has one meaning (2.33).
  - It resolves at load
    against the static part of the declaring context's
    lookup path (3.9): its own commands, then its bases', then the global
    commands. Which records enclose a record is known only at run time,
    from `get_parent()`. So a producer in an enclosing context must be
    qualified (`Application/list_rights.right_uid`).
    - Matching two or more commands is an error that lists the qualified
      candidates.
    - A reference that resolves through inheritance is valid.
    - A qualified name in another context is checked for existence and
      type at load. Whether it is reachable from a given record is
      decided at run time by the lookup, which finds it on the live chain
      or returns the navigation message.
    - When the workflow declares descend edges (`collect_descend_edges`),
      `--check` also warns about a qualified producer whose context can
      never enclose the declaring one. This is the coding skill's
      reachability rule (Rule 1), "a sibling context is not reachable";
      without the retired hierarchy file it cannot be an error.
    - talk_to_ido is unaffected: each of its hand-written producers is
      already runnable in the declaring context (2.15).
- **The field is optional.** It is backward compatible
  with today's command-only `available_from`.
  - Without a field, no type check is possible, and `--check` reports an
    *info* line suggesting a field.

**Where it may be declared.** Checked when the workflow is loaded, once per
process and cached with the existing per-workflow caches:

- **On a command's `Input` field (either kind): a producer.** The target
  must be a field of the target's `Signature.Output`, or the reference must
  name the command only. A target that has the field only in its `Input` is
  an error: `"<file>: Input.<field> (from '<source>'): <target>'s <field> is
  an Input field; from_ names the Output field a value comes from. To
  describe the value, write Field(description=...); the preview shows
  <target>.<field>'s description beside it"`. A target that has the field in
  both reads the `Output` field, as a producer always does. A target with no
  field of that name is an error.
- **Anywhere else: error.** An `Output` field is built by code, and a facts
  model's field is typed with the command it comes from (3.12), so neither
  carries `from_`.

| Declaring site | Target field | Edge | Allowed |
|---|---|---|---|
| A command's `Input` field, of either kind | an `Output` field, or command-only | producer | yes |
| A command's `Input` field, of either kind | an `Input` field only | — | **error**: `from_` names where a value comes from (2.27) |
| A facts model's field | any | — | **error**: the field's type names its command (3.12); until Phase 15 a copy written with `fact_from` or a hand-written `"from"` keeps today's behaviour (above) |
| Any `Signature.Output` field, of either kind | any | — | **error**: an `Output` is built by code (`__call__` or `__result__`, 3.4), so its fields cannot declare `from_` (`available_from` is only read on Input fields) |

**What the edge does.**

- **Producer.**
  - At load, `"available_from"` is written into the field's
    `json_schema_extra` as a list of strings:
    - `<qualified command>.<field>` when a field was given;
    - `<qualified command>` otherwise.
  - A field that already carries a hand-written `available_from` is a load
    error naming `from_` (2.23). A producer without a field to name is
    written as a command-only `from_("<command>")`, which says what a bare
    `available_from` entry said.
  - The type check: the target field's annotation must equal the
    declaring annotation, or be `list[T]` / `Optional[list[T]]` of it, or
    be equal modulo `Optional`. Anything else is an error.
  - **A producer edge on a planning command's `Input` must not name one of
    its own callees** (the callee graph, 3.7). The edge tells the agent, as
    it plans and as it runs, to run the target before calling this command, while
    this command's steps run it anyway, so the hint is backwards whatever
    the target's fields are. The message: `"<file>: Input.<field> (from
    '<source>') tells the agent to run <target> first, but this command's
    own steps call <target>. To describe the value, write
    Field(description=...) instead"`. The check needs the callee graph, so
    it is enforced from Phase 5.

A phase's facts need no `from_`: their types name the commands that produce
them (3.12).

**Where errors are reported.**

- Every error above makes `preview --check` fail.
  Today `--check` (`skill_preview.check_previews`) fails only for
  previews that differ, skill files that did not load, and
  `phase_source_problems`; it never looks at execution commands. So
  `check_previews` also appends every problem `resolve_field_sources`
  (Phase 2) reports, for execution and planning commands alike.
- Loading the workflow logs the error and skips only the offending command.
  That is the current policy of `check_step_commands`.
- `check_phase_sources` (`skill_commands.py:1155`, which today only
  *warns* on a `"from"` naming an unknown command field) keeps that policy
  for copy edges until Phase 15 removes them (2.33).
- **Which facts are checked.** The types of 3.12 are checked over
  `command.phase_outputs`: every annotation and facts model `_checked_plan`
  saw over the input grid (`_template_grid`). Return annotations alone are
  not enough, because a phase may choose its facts per input with
  `@phase(output=lambda input: ...)` (8 of talk_to_ido's 20 skills do). A
  model that several planning commands share is checked once and its
  problems are reported once, naming the model and every planning command
  that uses it.

**How consumers render the edges.**

- **`command_metadata_api.py:140-155` and `:990-991`.** Keep the key
  `available_from` and keep the current `str(list)` rendering. Entries now
  carry the `.field` suffix when known. No other change, so the agent and
  planner prompts change only by that suffix. The branch at `:1012-1013`
  that reads `available_from` from *output* fields stays as dead code:
  no Output field can carry `available_from` (the table above), so it
  never fires. Do not remove it in this project.
- **The missing-parameter message (`utils/signatures.py:1260-1267`).**
  Strip the `.field` suffix and the `<Context>/` prefix from every entry,
  before joining. Every entry is written by `from_` (2.23), so for a
  workflow whose entries were bare command names, such as the retail
  example, the message text stays exactly as it is today. Prose that
  talk_to_ido kept in `available_from` moves into the field's description
  (2.12, 2.23).
- **The planner docstring (`workflow_agent.py:1779`).** Unchanged.

### 3.4 Planning commands in the registry

**`CommandDirectory`** (`command_directory.py`):

- Root and context command files are both registered by
  `_register_command` (`command_directory.py:296`, called from the scan
  at `:262-281`). It is deliberately lazy: it does not import the module,
  and it hardcodes `response_generation_class_name="ResponseGenerator"`.
  (`:440-445` is `_register_core_commands`, the CME core commands, which
  are never planning commands.)
- `_register_command` detects a planning command by parsing the file with `ast`,
  without importing it, and checking for a top-level `PlanGenerator`
  class. Importing here is not allowed: it would defeat the lazy load.
  Both a top-level `ResponseGenerator` and a top-level `PlanGenerator` is
  the load error of 3.1.
- For a planning command:
  - `response_generation_class_name="PlanGenerator"`;
  - a new metadata field `is_planning: bool = True`.

  Execution commands get `is_planning=False`. The field is serialised into
  `command_directory.json`; a snapshot without it loads with
  `is_planning=False`.
- `_skills/` files are registered through the same path (Phase 3), with
  their qualified names.
- **The cache fingerprint.** `_command_source_roots` (`:638`) covers only
  `_commands` roots. Add each contributing `_skills` root to it, so adding,
  editing or removing a skill file invalidates `command_directory.json`
  and `routing_definition.json`. This also changes the function-cache and
  FastAPI checkpoint namespaces that key on the same fingerprint, which is
  the intended meaning ("changes when the workflow's commands change").

**Routing.** Planning commands are part of the `RoutingDefinition` for their
context, like execution commands. That is what lets a step that names a planning command
reach it through the CME workflow's exact-prefix name match
(`_workflows/command_metadata_extraction/intent_detection.py`). That name
match follows the lookup path of 3.9, as it does for an execution command. Planning commands
are never in the classifier's label set (Training, below).

**The argument path.** Every command receives its arguments one way,
whichever way it was reached (2.25, 2.46): for a planning command, as the
fast path (3.6), written as a step of the agent's plan or named by the agent
later in its run, or named by another planning command or by a user typing
its name.
`_invoke_command_impl` first runs the CME workflow
(`perform_action(chat_session.cme_workflow, Action(command_name="wildcard", ...))`,
`command_executor.py:260`), which detects the command and extracts
`cmd_parameters` into its `Signature.Input`. The CME then validates them in
one step for every command, `InputForParamExtraction.validate_parameters`
(`utils/signatures.py`), in this order:

1. the parameter screen, the type and pattern checks and `db_lookup`, as
   today;
2. the checks of the field options (2.46), with the request below:
   `check_verdicts`, one Jev classifier call when a field has `verify`, then
   `check_arguments`'s guards for the fields with `in_request`, `subject` or
   `strip`. No check is implied by a field's type;
3. `validate_extracted_parameters`, called once, with `command_text` set to
   the request when the hook declares it, as today;
4. the `Input`'s own validators, with `{"request": <the request>, "workflow":
   <the workflow>}` as their validation context. Today only the planning path
   runs them (`validate_call`, `check_input`); the CME builds an execution
   command's `Input` with `model_construct`, so they mostly do not run.

The hook runs after the guards for both kinds, so a hook that corrects an
argument (talk_to_ido's `resolved_kind`) never runs before the guard that
checks the argument is written in the request (2.25). `run_planning_command`
checks nothing itself; `validate_call` goes.

**The request** is the text the arguments were extracted from: the step,
which is `_invoke_command_impl`'s `command` argument, not the
`raw_user_message` it may substitute for the response generator
(`:296-298`), or the user's message in assistant mode. For a planning command
the agent of a sub-task's run named in a step, it is the sub-task and the
outputs of the turn's earlier steps (3.10). There is no typed planning call (2.25). A
refusal from step 2, 3 or 4 is returned as the CME's message for an invalid
value, the one an execution command gets, so the caller can rewrite its
step. A required argument the extraction could not fill is reported with
the CME's missing-parameter message (3.6). `verify` needs `JEV_API_KEY`
(`check_lm` is `_jev_lm()` today); without it the option checks nothing, and
the load says so once (3.9).

**Descriptions are written for people.** A `Signature` docstring and an
`Input` field's description say what the command does and what the value
*is* ("the member's name"), in words a person can read: the agent reads them
in its list of commands, as it plans and as it runs, and when it asks for a
missing value, and a developer reads them in the preview. They
do not carry instructions to a model ("exactly as the request writes
it"). Where an instruction follows from a rule the framework enforces,
the framework writes it, in one place: the field descriptions the CME
parameter extractor receives, for a field that carries the option the rule
belongs to, on a command of either kind (2.46). That is the only text a
model reads while filling arguments that those rules then check. After the
field's description it appends the sentence of each option the field
carries:

| Option | Sentence appended | The rule, enforced in `check_arguments` |
|---|---|---|
| `in_request` on a `str` | "Copy it exactly as the request writes it." | a verbatim substring of the request |
| `in_request` on an `int` | "A number the request writes." | a number the request writes |
| `subject` | "Copy it exactly as the request writes it. It must name a record the request names." | written in the request, and names a record of it |
| `verify` on a `bool` | "True only when the request asks for it." | Jev's classifier decides it again from the request |

The sentences are constants beside the checks that enforce them, so a rule
and its sentence change together. Nothing else receives them: not the
preview, nor the executor's catalog. A field without the option gets no
sentence, and is not checked. There is no setting. A description that already
says what the sentence says reads twice to the model; the coding skill tells
authors not to write it.

**Dispatch** (`command_executor.py`). `_invoke_command_impl` checks
`is_planning` after parameter extraction and before it instantiates the
response-generation class (`:286-294`); a `PlanGenerator` is never
called with `(workflow, command, command_parameters)`:

- **Agent mode.** The planning command is executed by
  `WorkflowExecutionContext.run_planning_command(qualified_name,
  command_parameters, step_text)` (3.5), which returns a `CommandOutput`.
- **Assistant (deterministic) mode, including `/`-prefixed commands in
  agent mode.** Return `CommandOutput` with
  `CommandResponse(success=False, response="<name> is a planning command;
  it runs in agent mode.")`. Planning commands need an LLM executor by definition.
- **Direct actions.** `CommandExecutor.perform_action` (`:337`) and
  `perform_mcp_tool_call` (`:466`), which back FastAPI's direct action
  calls and MCP tool calls, return the same refusal when the action names
  a planning command of the app workflow. They run one command with given
  parameters and no executor. (`_invoke_command_impl`'s own
  `perform_action` call on the CME workflow names `wildcard`, which is
  never a planning command.)

**The planning command output contract.** `run_planning_command` always returns exactly
one `CommandResponse`, built from what the planning command's `__result__`
returns (2.45, 3.16), by the rules of 3.14 for what an execution command's
`__call__` returns:

- `response`: the text `__result__` returns, as a `str` or as a
  `CommandResponse`'s `response`; the `Output`'s JSON when it returns only an
  `Output`; or, without `__result__`, what the last phase's agent writes.
- `output`: the planning command's `Signature.Output` instance, or `None`.
  - No skill reads `Signature.Output` today, so this is new, and there is
    nothing to migrate. A planning command builds its `Output`, and the
    text a person reads, in a reserved method on its `PlanGenerator`:

    ```python
    def __result__(self, input, <phase name>, ...):
    ```

    This is the planning command's counterpart of an execution command's
    `__call__`, and the only way a planning command supplies an `Output`
    (2.6). Rules:
    - It is not a phase. `phase_methods` (`skill.py`) already skips every
      `_`-prefixed name, dunders included, so it adds no step and no plan
      order.
    - It runs once, after the last phase of the call, as plain code: no
      command, no model call.
    - Its parameters bind by name to the phases' facts, with the existing
      `skill_phases.bound_arguments` a phase uses. A phase that was
      skipped, filled no facts, or is not in this call's `__phases__`
      arrives as `None`; a default is allowed and not needed (2.36).
    - It returns a `str`, an instance of this command's `Signature.Output`,
      or a `CommandResponse` holding either or both, as `__call__` does
      (3.14). An annotation is allowed and not required (2.36).
    - Facts may differ per input (`@phase(output=lambda input: ...)`,
      `record_fact`'s 37 models); the `Output` is one fixed class, so a
      parent's `from_` is type-checked against it.
  - Load errors:
    - a planning command declares `Signature.Output` but defines no
      `__result__`, so nothing can build it;
    - `__result__` names a parameter (other than `input`) that is not a
      phase of the planning command.
  - **Inheritance.** The checks read `__result__` as Python resolves it on
    the `PlanGenerator`, so an inherited one counts as one the file
    defines, and each error above names the class the method came from. A
    `PlanGenerator` may not subclass another command's `PlanGenerator`
    (2.36): `"<file>: PlanGenerator inherits from <command>'s PlanGenerator;
    to reuse its whole job, call <command> in a step; to share phases, move
    them to a base class in a _ module"`. Any other base class is allowed,
    such as a class in a `_` module or in the app.

    The checks are static (signature inspection). `__result__` also runs
    while the template is built, with every fact a placeholder (3.17); one
    that cannot, for example because it builds an `Output` from
    placeholders, is shown in the preview as decided at run time. Its body
    is covered by the author's tests, by `run-code` (3.18) and by the
    run-time rule below.
  - `output` is `None` when the planning command declares no `Output`, or when
    `__result__` returns only text.
  - At run time, when `__result__` raises or returns something other than
    the three forms (an `Output` of another class included), log a warning
    naming the planning command, write the answer with one model call from
    the phases' runs (`write_answer`), and set `output=None`, with `success`
    unchanged. This is the one place a planning command differs from an
    execution command, whose call fails instead: a planning command's runs
    took many steps and still answer the request (3.16).
- `success`: `False` when the frame ran out of budget, failed its
  argument check, or failed.
- The `CommandOutput` that carries this response is appended to the turn's
  `command_outputs`, like any command's. A call that is a step of an agent
  is appended by the agent's command tool
  (`workflow_agent._append_turn_output`); a call on the fast path, which the
  runtime runs right after the agent's plan step (3.6), is appended by the
  runtime. Either way clients receive its `Output` under its `command_name`
  (3.14).

**Catalogs.**

### 3.5 The `PlanFrame` stack

**New module: `fastworkflow/plan_frame.py`.**

```python
@dataclass
class PlanFrame:
    kind: Literal["turn", "planning", "spawned"]   # "spawned" from Phase 18 (Spawned frames, below)
    command_name: Optional[str]          # qualified planning command name; None for the turn frame and a spawned frame
    depth: int                           # 0 for the turn frame
    alias: str                           # "" for turn; "<parent alias>/<stem>#<n>" otherwise
    subtasks: list[str]
    origins: list[int]
    subtask_index: int
    subtask_answers: list[str]
    subtask_exhausted: bool
    evidence_floors: dict[int, int]      # not serialised (as today)
    initial_plan_text: str               # not serialised (as today); goes in Phase 6: a run's plan is its latest plan step (3.6)
    phase_run: Optional[dict[str, Any]]
    phase_live: Optional[tuple[Any, list[Any]]]   # not serialised (as today)
    phased_skill_call: Any = None        # not serialised (as today)
    child_step_ranges: list[list[int]] = field(default_factory=list)  # [first, last] per child run
    invoking_step: Optional[int] = None  # the parent step index this frame runs inside
    agent: Any = None                    # per-frame fastWorkflowReAct, built lazily
    fast_path: bool = False              # the whole plan of its sub-task (3.6)
    def to_state(self) -> dict: ...      # see Serialisation below
    @classmethod
    def from_state(cls, d: dict) -> "PlanFrame": ...
```

`next_step` is deliberately **not** a frame field. `_next_step` is the
turn-wide next free step index (`_run_subtasks_from`, `_record_subtask_answer`
and the phase runner all advance it), and step indexes key the observation
archive (`O{idx}` aliases, `observation_offloading/state.py:current_execute_alias`;
`_archived_command_runs(from_step, to_step)`). One counter keeps every
step index in the turn unique across frames, so it stays a plain attribute
on the context.

**Integrating it into `WorkflowExecutionContext`.**

- Add `self._frames: list[PlanFrame]`. It always holds at least the
  turn frame.
- Replace the attributes listed in 1.2 item 6, except `_next_step`, with
  **properties that read and write `self._frames[-1]`**. Existing code
  that refers to `self._subtasks` and the others keeps working, and the
  diff stays small. `_workflow_tool_agent` becomes a property for
  `self._frames[-1].agent`.
- Four places are about the turn, not the current frame, and must name
  `self._frames[0]` explicitly instead of going through the properties:
  - `serialize_state` / `apply_serialized_state` for the top-level keys;
  - `_begin_turn`, which resets `_frames` to a single fresh turn frame;
  - `_hand_off` (`:2650`), which is turn-frame only;
  - `_clear_subtask_state` (`:1834`, called by `_run_agent` at turn
    start). A planning-command frame's state is released by popping it, never by
    clearing it.
- `_ensure_agent_initialized` builds the turn frame's agent, as today. A
  planning-command frame's agent is built by `run_planning_command` with the same
  factory (`initialize_workflow_tool_agent`), so it gets the same tools,
  `max_iters` and adapter.

**Step numbering across frames.** `fastWorkflowReAct.forward` numbers
steps locally from `first_step` and advances `idx` by one per step
(`utils/react.py`). A child run inside the parent's step `k` must not reuse
`k + 1`, … , which the parent would otherwise number next.

- A child agent's run starts at
  `first_step = max(self._next_step, k + 1)`, where `k` is the parent's
  in-flight step (the index `current_execute_alias` reads). The child's
  frame records `invoking_step = k`.
- When the child run ends, `self._next_step` is already past its last step
  (the existing advance at `:2516` and `:2698` runs on the child frame).
- `fastWorkflowReAct` gains one optional hook, `step_floor:
  Callable[[], int] | None`, defaulting to `None`. Wherever `_run_loop`
  advances `idx`, it sets `idx = max(idx + 1, step_floor())` when the hook
  is set. `WorkflowExecutionContext` sets it on every agent it builds to
  `lambda: self._next_step`. A parent therefore resumes numbering after
  the child's steps, and with no nesting the hook returns a value `<=`
  `idx + 1`, so numbering is unchanged.
- The parent frame appends `[first, last]` of the child's steps to
  `child_step_ranges`.

**`run_planning_command(name, params, step_text)`.**

1. Cycle guard: if `name` is the `command_name` of any frame on the stack,
   return `CommandResponse(success=False, response="<name> is already
   running; call its steps directly.")`. No frame is pushed. The agent can
   continue with execution commands. Because no planning command is ever on
   the stack twice, nesting is never deeper than the number of planning
   commands, so there is no separate depth cap (2.23).
2. Push a frame with:
   - `kind="planning"`, `depth = parent.depth + 1`;
   - `alias = f"{parent.alias}/{stem}#{n}"`, where `n` counts calls to
     `stem` within the parent frame, starting at 1;
   - the subtask list set to `[step_text]`, the single step that invoked
     it;
   - `invoking_step` set as described under Step numbering;
   - `fast_path=True` when the step is the whole plan of its sub-task, the
     one-step plan the agent of a sub-task's run wrote, which the runtime
     runs right after the plan step (3.6, 2.38, 2.43, 2.52); else `False`.
3. **The arguments are already checked.** `params` arrive from the CME's
   one validation step (3.4, The argument path), which ran the field
   options' checks, the hook and the `Input` validators before dispatch, so
   a refused argument never pushes a frame. No planning call and no check
   is made here (2.46).
4. **Build the call and run it** on the top frame, through the properties.
   Every planning command runs this one way, whatever its shape (2.36):
   - Build the `SkillCallPlan` that `plan_skill_call` used to return,
     without any planning call: `plan` from the planning command's steps for
     the checked arguments, `phases` from `call_phases(skill_command, args)`
     (`skill_commands.py:1288`), no `steps_before` / `steps_after`: steps
     the request needs around the call are steps of the plan that calls it
     (2.44). Run it
     with `_start_skill_phases(step_text, skill_command, call,
     first_step=...)` (`:2079`). `call_phases` always returns at least one
     phase.
   - A phase's step budget follows how many phases the call runs: the
     agent's `max_iters` when it runs one, the per-phase cap when it runs
     several. This replaces the "flat" test (`state["flat"]`, `:2106`,
     `:2381-2382`), which read the budget from the phase's shape.
   - There is no template branch. As the fourth amendment wrote this step, a
     planning command with no parameters and one phase that reads nothing
     took the template branch of `_call_agent_for_query` (`:1972`), where
     the planner re-planned it from its template; it now runs its steps
     like any other.
5. On completion, failure or exhaustion:
   - build `CommandOutput(command_response=CommandResponse(...))` with the
     response described in 3.4;
   - append the child's step range to the parent's `child_step_ranges`;
   - pop the frame, which releases `agent` and `phase_live`;
   - return the output. The executor then holds it as the run of the
     parent's step `k` (`_hold_command_run`, `workflow_agent.py:96`),
     because after the pop `current_execute_alias` reads the parent's
     in-flight step.

**Ask_user inside a child, when ask_user suspends the turn** (FastAPI and
other embedders; the codebase calls this Topology B). `fastWorkflowReAct`
catches `AskUserSuspend` inside its loop and returns a suspended `Prediction`; the
exception does not propagate out of the child's agent. So:

1. The child's phase runner returns its suspended result to
   `run_planning_command`.
2. `run_planning_command` does **not** pop. It raises
   `AskUserSuspend(clarification_request)` with the child's clarification.
   `AskUserSuspend` is a `BaseException`, so no `except Exception` on the
   way up swallows it.
3. That exception passes up through the parent's `_execute_workflow_query`
   and is caught by the parent's `_run_loop` at step `k`, which stashes
   the parent's own suspension, exactly as for an execution command that asks.
4. Every frame up to the turn frame returns suspended the same way, and
   `_process_agent_message` ends the turn with `_awaiting_user_output`.
   The stack is serialised with the child on top and every agent on it
   suspended.

**Resuming a nested suspension.** `_resume_agent_message` (`:2790`) gains
one step, after `_post_ask_user_response` builds the observation from the
user's answer and before its existing phased/plain resume:

- While `len(self._frames) > 1`: resume the top frame (its phase runner
  with `resume_observation` when it has `phase_run`, else its agent's
  `resume`).
  - If it suspends again, return the suspended output as today.
  - Otherwise build its `CommandOutput`, record its step range, pop it,
    hold the output as the parent's step `k` run, and turn it into the
    observation that `_execute_workflow_query` returns for a command
    output (factor that formatting into one helper both use). That text
    becomes the observation for the next frame's resume.
- At the turn frame, continue with the existing code using the last
  observation.

`_record_subtask_answer`, `_hand_off` and the "No suspended ReAct state"
check apply to the turn frame only.

**Ask_user inside a child, when ask_user blocks** (the CLI; the codebase
calls this Topology A). The CLI path's ask_user blocks on the
user-message queue inside the tool call (`_ask_user_tool`), with no
suspension. A child that asks simply blocks, and nothing above changes.

**Hand-off.** `_hand_off` and `MAX_HANDOFFS = 2` apply only in the turn
frame. A planning-command frame that exhausts its budget returns `success=False`
to its parent and does not hand off.

*Amended by 2.55:* from Phase 6 the text a continuation starts from is
written by code, not by a planner call. `_hand_off` builds it from what the
capped run left: its answer, which its extract call already wrote and
`_record_subtask_answer` keeps; its plan, the latest plan step in its
trajectory (3.6), each step marked run or not run by `finish_check.check`
over the run's archived rows; and the records it opened (`_opened_part`), as
today. `run_progress_check` goes. The continuation's first step is its plan,
as every run's is. A spawned frame does not hand off either (Spawned
frames, below).

**The turn-wide step budget for nested frames.**

- **What it counts.** Model iterations (the steps that increment
  `fastWorkflowReAct.iteration_counter`; code-run steps do not) taken by
  agents of planning-command frames, depth 1 and below, and from Phase 18 by
  agents of spawned frames (Spawned frames, below), except a fast-path
  frame (`fast_path=True`: the planning command that is the whole plan of
  its sub-task, the agent's one-step plan, 3.6). Steps of the turn frame
  and of a fast-path frame are not
  counted: the fast-path call is the sub-task's own run, which the turn frame
  ran itself before 2.25, not work that nesting adds. The frames below a
  fast-path frame count. The turn frame is already bounded by today's caps:
  `MAX_SUBTASKS = 10` (`workflow_agent.py:1019`) sub-tasks, each with at
  most `MAX_HANDOFFS + 1 = 3` executor runs of `max_iters = 25`, or
  phases of at most 15 steps each, where a fan-out phase runs up to 10
  sub-plans of 15 (the per-phase and fan-out caps, constants from
  Phase 8, 2.23). Flat
  sub-tasks alone reach 750 model iterations. Phased ones reach more:
  talk_to_ido's `permission_holder_sweep` has two fan-out phases, so one
  call is up to 21 sub-plans, 315 iterations, and ten such sub-tasks reach
  about 3,000. A turn-wide cap on the turn frame would cut off turns that
  work now. The budget exists to bound what nesting adds, and it counts
  exactly that.
- `FW_TURN_MAX_STEPS` is optional, with a default of `400`, and is read
  through `fastworkflow.get_env_var`. A value that is not a positive
  integer logs a warning and the default applies, as
  `phase_step_budget()` (`skill_phases.py:432`) does for its setting
  today. It is the one setting this project adds (2.23). The default
  admits one nested call of the heaviest planning command measured (315,
  above) with room to spare. An earlier draft said 200, which would stop
  that call partway.
- One counter, `self._turn_steps_used`, is reset in `_begin_turn` and
  serialised.
- `fastWorkflowReAct` gains a second optional hook, `on_iteration:
  Callable[[], bool] | None`, called right after each
  `iteration_counter += 1`. `run_planning_command` sets it on every planning command
  frame's agent; it increments `_turn_steps_used` and returns `False`
  once the counter reaches `FW_TURN_MAX_STEPS`. The loop treats `False`
  exactly like reaching `max_iters`: it sets `_exhausted_last_run` and
  stops. The turn frame's agent has no hook.
- When the budget is spent, the planning-command frame returns `success=False`
  to its parent with the response "The step budget for nested commands
  is spent; continue with the remaining steps directly." Every further
  `run_planning_command` in the same turn fails the same way without pushing a
  frame. The parent, and the turn frame, continue under their own caps.

**Depth.** The turn frame is depth 0, and a planning command matched or
called from it is depth 1. There is no depth cap: the cycle guard bounds
depth by the number of planning commands, and the turn-wide budget bounds
the work (2.23).

**Attributing runs.** `fill_output` and its helpers (`runs_on_plan`,
`planned_record`, `runs_finding_planned_values`, `runs_that_entered_record`,
`runs_standing_in_for_openers` in `skill_phases.py`) take the runs the phase
runner passes them; they do not query the archive themselves. The phase
runner reads them with `_archived_command_runs(from_step, to_step)`
(`workflow_execution_context.py:2324`), which filters by step index. So
attribution is done by step ranges, in the runner, not by a new archive
column:

- Wherever the context reads archived runs for a frame (the phase
  runner's facts read, the finish check's evidence read, and
  `earlier_runs`), it drops every run whose step lies inside one of that
  frame's `child_step_ranges`.
- A child planning command therefore contributes exactly one run to its parent:
  the run held under the parent's step `k` (step 5 above), whose
  `command` is the planning command's qualified name, whose `input` is its
  checked arguments, and whose `output` is its `CommandResponse.output`.
  A copy `from_("Ctx/<child>.field")` on a parent facts field, naming the
  child planning command, reads that output like any command's.
- **Where a child leaves the workflow.** A planning command navigates like any
  command; talk_to_ido's start at a hub such as `open_directory`. After the
  pop, the workflow is on whatever record the child ended on, and the
  parent's later steps start there. The held run therefore stores the
  context the child ended on (`context_name` and `context_clause`, read
  after the child's last step), not the context when it was invoked. Two
  things read it:
  - the parent phase's facts, which are filled from the runs on the record
    the phase ends on, this one included (3.12; until Phase 15, a copy
    edge's plain name resolves against it as for any run, 3.3);
  - a `bind=True` fan-out item whose sub-plan calls a planning command counts as
    opening the record the held run names (`item_record`,
    `item_record_issues`). Without this, the opening run lies inside the
    child's step range and is dropped, and the item fails as never opened.

  The parent's agent learns where it now is the way it does after a
  navigation command. A planning-command step is dispatched through the same
  `execute_workflow_query` tool function as an execution-command step, which compares the
  context before and after the command and, when it changed, ends the
  observation with `now_in` (`annotated_observation`, `workflow_agent.py`).
  `run_planning_command` must therefore be reached inside that tool function, as
  `_invoke_command_impl` is, and must not bypass it. Nothing restores the
  parent's context on pop, and the preview says nothing about navigation
  that is specific to planning commands: the rule is the one for every
  command (1.3, item 6; 2.7).
- The observability store (`observability/store.py`, `SCHEMA_VERSION = 10`,
  which refuses older stores and has no migrations) is **not** changed.
  `offload_command_runs` keeps its primary key of turn key, step alias
  and ordinal, which stays unique because step indexes are unique across
  frames.

**Tracing.** Every span opened while a planning-command frame is on top gets
the attribute `frame_alias` (the frame's `alias`; spans of the turn frame
get `""`). Adding an attribute changes the span contract, so bump
`SPAN_CONTRACT_VERSION` in `tracing.py` from `23` to `24`, in the same
change, following that constant's existing rules.

**Serialisation** (`serialize_state` / `apply_serialized_state`,
`workflow_execution_context.py:977-1139`).

- The turn frame keeps using the existing top-level keys (`subtasks`,
  `subtask_origins`, `subtask_index`, `subtask_answers`,
  `subtask_exhausted`, `next_step`, `skill_phase_run`, `react`), read
  from and written to `self._frames[0]` (and `_next_step`), so old blobs
  restore unchanged.
- Add these keys:
  - `"frames"`: `[frame.to_state() for frame in self._frames[1:]]`.
    `to_state` writes `kind`, `command_name`, `depth`, `alias`,
    `subtasks`, `origins`, `subtask_index`, `subtask_answers`,
    `subtask_exhausted`, `phase_run`, `child_step_ranges` and
    `invoking_step`. It leaves out what the turn frame leaves out today
    (`evidence_floors`, `initial_plan_text`, `phase_live`,
    `phased_skill_call`) and `agent`.
  - `"turn_child_step_ranges"`: the turn frame's `child_step_ranges`.
  - `"frame_react"`: the `export_suspended()` blob of each nested frame's
    agent, as a list aligned with `"frames"`, with `None` where the frame
    has no agent. On restore, each is imported into a fresh agent built
    with the same factory, under the same `awaiting_user` condition as
    `"react"` (`:1121-1125`).
  - `"turn_steps_used"`: the nested-frame step counter.

  `to_state` also writes `fast_path`. There is no plan-question key: a
  missing argument is asked for by the agent, whose suspension is already
  serialised (3.6).
- **Do not bump the session-state `SCHEMA_VERSION` (`4`).** Absent keys
  mean "no nested frames, no child ranges, zero steps used". This follows
  the file's existing "absent from blobs written before …" pattern.
- `validate_state` (`state_serialization.py:27`) needs no change. It is a
  generic check that the payload round-trips through JSON exactly, not a
  list of allowed keys. Two of its rules constrain the new values: every
  dictionary key must be a string, and no mutable container may be
  reachable by two paths. So `to_state` returns fresh lists and dicts,
  never the frame's own objects.

**Memory.** Popped frames are not retained. Live memory is the frames on
the current branch: at most one frame per planning command, plus the turn
frame, since the cycle guard never stacks one twice. From Phase 18 a branch
may also hold one spawned frame (below).

**Spawned frames** (2.55). Built in Phase 18, and kept only if its
measurement keeps them; until then no frame has `kind="spawned"`.

- **The tool.** A sub-task's run (3.6) has one more tool, `spawn(goal:
  str)`, and no other agent has it: not a spawned frame's, and not the
  agent of a planning command's phases. Its function reaches
  `run_spawned(goal, step_text)` inside the tool call, as
  `execute_workflow_query` reaches `run_planning_command`, so the parent's
  observation ends with the `now_in` note when the frame moved the workflow
  (2.7). Its description says to spawn a run for a step the agent tried and could
  not complete.
- **`run_spawned(goal, step_text)`:**
  1. When the turn-wide budget is spent, return the budget's refusal (The
     turn-wide step budget, above) without pushing a frame.
  2. Push a frame with `kind="spawned"`, `command_name=None`,
     `depth = parent.depth + 1`, `alias = f"{parent.alias}/spawn#{n}"`,
     where `n` counts the parent's spawns from 1, the subtask list set
     to `[goal]`, and `invoking_step` set as for a planning command.
  3. Build its agent with the same factory, without `spawn`, and with the
     `on_iteration` hook, so that its iterations count against
     `FW_TURN_MAX_STEPS`. Run it as `_call_agent_for_query` runs a sub-task
     (3.6): the listing gathered for its goal (3.10), the plan step first,
     and the finish check over its latest plan. A planning command it names
     in a step is checked against the spawning run's sub-task and the
     turn's earlier outputs (3.10). The fast path does not apply: a plan of
     one call runs like any other plan.
  4. On completion, exhaustion or failure, pop the frame and return
     `CommandResponse(response=<its answer>, success=<False when it
     exhausted its steps or the budget, or failed>)` as the observation of
     the `spawn` step. No run is held for the step (`_hold_command_run`
     holds a command's), and the frame's step range is not added to the
     parent's `child_step_ranges`, so the parent's finish check and hand-off
     read the frame's runs as the parent's own (2.55).
- **Ask_user** inside a spawned frame suspends and resumes as inside a
  planning command's frame (above): `run_spawned` does not pop, and raises
  `AskUserSuspend` with the frame's clarification. On resume the frame's
  agent resumes, and when it finishes, its answer becomes the observation of
  the parent's `spawn` step; no run is held for it.
- **Depth.** Only a sub-task's run spawns, so a branch holds at most one
  spawned frame, besides each planning command at most once. There is no
  depth cap.
- **Serialisation.** A spawned frame is serialised as a planning-command
  frame is (`to_state`, under `"frames"` and `"frame_react"`), with `kind`
  `"spawned"`, no `command_name`, and its goal as its one sub-task. No new
  key is added to the session state.

### 3.6 The plan step, the fast path, and a missing argument

The reasoning is in 2.25, 2.43, 2.44, 2.52 and 2.53. This section is gated
by Phase 6's measurement.

**Where planning happens.** `_call_agent_for_query`
(`workflow_execution_context.py:1972`) runs once per sub-task after the
request was refined and split: from `_run_agent` for an unsplit request, and
from `_run_subtasks_from` for each sub-task. It matches a planning command
(`planner_skill_for` → `match_skill`, `workflow_agent.py:1466`) and runs the
agent. It calls no planner: the agent's first step is its plan (2.52). The
run is given:

- `available_commands`: the listing of 3.10, each planning command on it
  with its template. The context-change observer
  (`_refresh_agent_available_commands`) re-renders that listing for the
  active context, instead of replacing it with the executor's list;
- its request: the sub-task; then, when `match_skill` matched a planning
  command confidently, its template, shown first as `_template_text` shows
  it today ("A job like this is usually done by <command>: ..."); then the
  summaries of the conversation's earlier turns
  (`_previous_turn_summaries_for_planner`), which the planner's first call
  read;
- its tools: `plan`, `ask_user`, `what_can_i_do`, `execute_workflow_query`
  and `finish`, and from Phase 18 `spawn` (3.5, Spawned frames). Until
  the run has called `plan`, every tool but `plan` and `ask_user` is
  disabled (`fastWorkflowReAct.disabled_tools`), so the model is not shown
  them.

**The plan step.** `plan(steps: list[str])` is a tool that
`initialize_workflow_tool_agent` adds for a sub-task's run and for a
spawned frame. A planning command's phases have none: their steps, which
their `PlanGenerator` wrote, are their plan. It:

- makes the steps the run's plan, replacing any earlier plan of the run.
  The run's plan is its latest plan step, read from the trajectory, so it is
  serialised with a suspended agent and survives a resume in another
  process with nothing kept beside it. The finish check reads it
  (`_attach_finish_check`, in place of `_initial_plan_text`), and so does a
  hand-off (3.5);
- stays in the model's view. When a trajectory outgrows the context window,
  the fallback that drops the oldest steps from what the model is shown
  (`fastWorkflowReAct.truncate_trajectory`, read by `_model_view`) passes
  over the run's latest plan step and drops the steps around it, as the
  plan in today's request is never dropped. Compaction reads only
  `execute_workflow_query` steps (`observation_offloading/compact.py`), so
  it never offloads a plan step's observation;
- runs the plan checks (below), and returns the plan as numbered lines
  followed by their notes;
- after its first call, enables the tools that waiting for the plan
  disabled; a tool disabled for another reason, such as `ask_user` in an
  unattended turn, stays disabled;
- after a later call, above `FULL_LISTING_MAX_CHARS`, gathers the run's
  shortlist again, from the sub-task and the user's latest response (3.10);
- appends a `PlanningStep` to `_planning_steps_capture` when a distillation
  pass set one, with the step's thought as its reasoning (2.54).

Its description is the planner's instructions, the docstring of
`build_query_with_next_steps` today, with the rule below for a planning
command that matches. The step is traced as its own `fw.agent.step`, with
the plan in `tool_args`; `fw.planner.plan` and `fw.planner.replan` are no
longer emitted. That changes the span contract, so the phase that makes the
change bumps `SPAN_CONTRACT_VERSION` (`tracing.py`), following that
constant's existing rules.

**The plan checks** (2.53). `plan` runs them over the steps as
`finish_check.parse_plan` reads them, in this order:

1. **Producers.** For each command step, and each required `Input` field of
   its command that has a producer `from_` (3.3) and whose value the step
   does not write (`finish_check.step_arguments`): when no earlier step runs
   one of the field's producers, a note naming the step, the field and its
   producers.
2. **Reach.** Code follows the plan from the active context. A step whose
   command declares `descends_to` moves the plan into that context, and
   `go_up` and `reset_context` move it as they move the workflow. For each
   command step whose command is not on the lookup path (3.9) where the plan
   stands, reading the enclosing records from the live chain and from the
   contexts the plan entered: a note naming the step, the context its
   command lives in, and the command that enters it (`collect_descend_edges`).
3. **Coverage.** When `match_skill` matched a planning command confidently,
   and the plan neither calls it nor has a step that runs each command step
   of its template: a note naming the command and the steps the plan lacks.

The notes together are at most `finish_check.NOTE_MAX_BYTES`. A check that
raises adds no note and logs a warning, as the finish check does
(`review_finish`). No check refuses a plan.

**Nothing else plans during a run.**

- In the parameter-extraction stage, `_execute_workflow_query` returns the
  CME's message and the abort confirmation; today it returns a replan
  (`workflow_agent.py:715-728`).
- `_post_ask_user_response` returns the user's answer as the step's
  observation, after `_apply_reply_intent` as today; today it returns a
  replan (`:777-784`).
- A hand-off's text is written by code (3.5, Hand-off).

**A planning command that matches.** The `plan` tool's description says
how to use one, in this order of preference (2.44):

- the one step that calls it, when it covers the whole sub-task: the fast
  path, below;
- the call as one step, with plain steps before or after it for the parts
  it does not cover, never repeating a command its template already runs.
  The agent runs the plan; the call runs nested (3.5) with
  `fast_path=False`, so its steps count against `FW_TURN_MAX_STEPS`; and the
  agent writes the sub-task's answer from every step;
- an adapted copy of its steps, when the request needs some of them dropped
  or changed. The agent runs the copy as ordinary steps, and the command's
  phases, facts and `__result__` do not run.

**The fast path takes no model step after the plan** (2.43). When the plan
is the one step that calls a planning command, the runtime runs that step
right after the plan step, as a step code writes (`by_code`, as a phase's
code-run steps are recorded):

- the CME extracts the planning command's arguments from the step and
  validates them (3.4, The argument path), binding `key=value` in code and
  calling the extractor for words; the request for the checks is the
  sub-task and the turn's earlier outputs (3.10);
- `run_planning_command` pushes a frame with `fast_path=True` (3.5) and runs
  the call; a fast-path frame's iterations are not counted against
  `FW_TURN_MAX_STEPS`, and the frames below it are;
- the runtime appends the call's `CommandOutput` to the turn's
  `command_outputs`, as the agent's command tool would, so clients receive
  the planning command's `Output` (3.14);
- when the call succeeds and its response is text the command wrote (what
  `__result__` returns as a `str` or a `CommandResponse`'s `response`, or
  what its last phase's agent wrote), the run ends there, with no extract
  call: that text is the sub-task's answer, as written.
  `_record_subtask_answer` records it, and `_combined_answer` joins it with
  the turn's other answers, as today;
- when `__result__` returned only an `Output`, or the call was refused, ran
  out of budget or failed, the call's observation is the run's next
  observation. The agent goes on from its own plan, finds a missing value
  or asks for it, and writes the sub-task's answer; hand-off and
  `_run_subtasks_from` work as today.

So everything a matched skill used to get through `plan_skill_call` it now
gets through the agent's plan: its checks (3.4), its phases
(`_start_skill_phases`, 3.5), and steps before and after it for the parts it
does not cover (2.44). Without `JEV_API_KEY` the agent finds the planning
command on its list itself (3.10), and the fast path is the same.

**A missing argument.** A required argument the extraction cannot fill is
reported with the CME's missing-parameter message (`utils/signatures.py`,
`MISSING_INFORMATION_ERRMSG`, the producers named by `available_from`, and
the request for corrected values), the same one an execution command gets.
On the fast path it becomes the run's next observation, after the plan step;
in a longer plan it is the step's observation. The agent then:

- finds the value, with a producer the message names, and runs the step
  again; or
- asks the user with its `ask_user` tool, which suspends and resumes the
  turn as it does for any command (Topology A or B), and runs the step again
  with the answer.

A refused argument (3.4, The argument path) is a failed step with the
refusal's text, which the agent can act on the same way. Nothing about this
is new or planning-specific, and nothing new is serialised.

**Unattended turns never ask.** `_turn_unattended` disables the agent's
`ask_user` tool (`_enable_all_tools`), as today; the agent goes on without
the value or finishes with what it has.

**Removed.** `plan_skill_call` and `typed_signature`, with its rule sentences
moved to the extractor's field descriptions (3.4, Descriptions); and the
plan-time question as first written: the `allow_plan_question` argument, the
`param` / `reason` attributes of `SkillInputError`, the `plan_question`
record and its handling in `_resume_agent_message`, and the preview's
`asked when missing` lines. If Phase 6 finds the nested call's arguments
worse than the typed call's, that design (this section before the fourth
amendment, in this file's history) is the fallback, and this section is
brought back for a decision.

Removed by the seventh amendment (2.52, 2.55): the planner's call for each
sub-task, its two replans and its progress call, that is
`build_query_with_next_steps` with its three signatures,
`run_progress_check` and `fastWorkflowReAct.planner_view`; also
`_initial_plan_text`, `_current_planner_lm` and the two planner spans. If
Phase 6 finds the agent's plans worse than the planner's, the planner as a
tool the agent calls is the fallback (2.52, Alternatives). If that loses
too, the planner's call before the run, as 2.43 and 2.44 decided it, is
brought back for a decision.

**No question for an ambiguous match.** An earlier design also asked the
user which planning command was meant when two scored close, with two
settings for what counts as close. The agent's plan replaces it: the unsure
candidates are on the run's list (3.10), and the agent composes them, or
plans a step that consults the user (2.21). Until Phase 10 lands, an unsure
match shows no template first, and the agent plans from its list. If Phase
10 finds that the agent guesses when it should ask, that question is the
fallback design, with constant thresholds.

### 3.8 Protecting planning commands from the build generator

- **The generated-file header.** `build/command_file_template.py` writes
  `# fastworkflow:generated — regenerate with fastworkflow build; edits may
  be overwritten` as the first line of every file it creates.
- **Refuse to overwrite planning commands.** `create_command_file`
  (`command_file_template.py:143`) and `create_function_command_file`
  (`:22`), before writing over an existing file, refuse when that file
  defines a top-level `PlanGenerator` (checked with `ast`, without
  importing it). This holds even when `overwrite=True`, and it is the
  only refusal condition; the header does not change it.

  A refusal is a warning naming the file. Existing generated execution-command files
  without the header are still overwritten (backward compatible); new
  ones get the header. The header is informational: it tells a reader the
  file is generated, and nothing reads it to decide anything.
- **The build validator.** `validate_command_file_components_in_dir`
  (`build/command_file_generator.py:162`) reports every `.py` file in
  `_commands/` that lacks the execution-command components (a `ResponseGenerator`
  with `__call__`, and the rest). It skips a file with a top-level
  `PlanGenerator` for those execution-command checks and checks only that it has a
  `Signature`. `verify_commands_against_context_model` (`:275`) and
  `validate_command_imports` (`:349`) treat planning-command files like execution command
  files: they are commands in their context folder and must import.
- **Name collisions.** If the generator would create an execution command whose
  qualified name equals an existing planning command's, it skips that file and
  warns.
- **App generators are out of reach.** These rules protect
  fastworkflow's own build generator only. An application may generate
  its `_commands/` tree with its own script. talk_to_ido's
  `gen_ido_scaffold.py` deletes the workflow root, writes `_commands/`
  afresh and restores only its `PRESERVE_TREES` (which list `_skills`).
  A planning command moved into its `_commands/` would be deleted by the next
  regeneration. The migration guide (Phase 8) says so, and gives the rule
  such a generator must follow before its workflow moves: preserve every
  file under `_commands/` with a top-level `PlanGenerator` (detected with
  `ast`, as in 3.4), and the `_` helpers they import.

### 3.9 Scoped lookup: how a request finds its command

The reasoning is in 2.13–2.17. Everything here is gated by the
measurements of Phase 9.

**The path.** For a request on the current object `O`, the lookup visits
these scopes in order:

1. `O`'s context;
2. its bases, in the order `CommandContextModel.commands()` resolves them
   (depth-first, in declared order);
3. the same two steps for `get_parent(O)`, then for its parent, up the
   live chain;
4. the global scope, `*`.

A scope already visited is skipped. That covers a base shared by several
records on the chain (`Resource` in talk_to_ido), a diamond, and a
context that lists `*` as a base (`messaging_app_3`,
`iddm_dataconnector_codegen`).

**Heads.** Each context's classifier learns:

- the context's own commands only (its `"/"` list in
  `CommandContextModel`), not its bases'; planning commands get no labels
  until Phase 10, step 1 decides whether they should (2.20, 3.4);
- the four core commands (`go_up`, `reset_context`, `what_can_i_do`,
  `what_is_current_context`), as today;
- `parameter_value`, unchanged;
- the reserved `wildcard` label, which keeps its name and now means "not
  one of mine". It is trained on up to `NOT_HERE_SEEDS` (8, a trainer
  constant that Phase 9 confirms or replaces) hand-written seeds of every
  command that is not one of the head's labels, planning commands
  included, chosen for diversity of phrasing, with no ancestor sampling
  and no fill up to a ratio (2.15). A command with fewer seeds contributes
  all it has. The sample is chosen once, when the command first enters the
  head, and recorded with the artifact as part of the head's training
  signature (2.50; low priority, after the rest of Phase 9).

The global head never learns the startup command. It sets the root
object, and setting that twice raises (`Workflow.root_command_context`).

`RoutingDefinition.contexts` keeps its meaning: every command runnable on
an object of that context, own and inherited. The exact-name checks, the
catalogs and MCP keep reading it. Only the head's label set changes.

Base contexts get heads that the walk now asks. Today talk_to_ido trains
heads for `Resource`, `Directory`, `EntityLookup` and `ControlCatalog`
that nothing asks, because a head is chosen by the live object's class
name (`Workflow.get_command_context_name`).

**One request, step by step.** This replaces the parent loop in the CME
`wildcard` command (`wildcard.py:96-111`).

1. Ask the next head on the path. Skip a head already asked for this
   utterance.
2. If the head names one command confidently, the scope recognised it:
   bind (below) and stop.
3. If it answers "not here", go on to the next head.
4. If it answers `parameter_value`, stop and end as step 6 does. A bare
   value never starts a walk (2.18).
5. If it is unsure, it returns several labels:
   - if "not here" is not among them, ask the user among its commands
     now, as today;
   - if "not here" is among them, keep its commands as candidates and go
     on. The walk then ends at the next head that names a command,
     confidently or not. The user is asked once, among the kept
     candidates and that head's commands, each named with its scope.

   This replaces today's handling of an unsure head whose labels include
   "not here": the ambiguity prompt drops that signal and offers only the
   local commands (`ESCALATION_OUTCOME_SUPPRESSED_BY_AMBIGUITY` in
   `intent_detection.py`, where code comments call it GAP-18).
6. If the path ends with nothing named and candidates were kept, ask
   once among them. Otherwise end as the climb ends today: the routing
   hint for a known command name (`foreign_context_hint`), else
   `ErrorCorrection/you_misunderstood`.

**Binding.** When a scope recognises the command, set
`command_context_for_response_generation` to that scope's object before
`ParameterExtraction` runs, as the climb does today (2.17):

- `O`, for `O`'s context and its bases;
- the ancestor, for an enclosing scope;
- the root object, for the global scope (it may be `None`, as it is
  today when the climb reaches `*`).

`current_command_context` does not change.

**Calls by exact name** follow the same path, as plain string matches
with no model:

- `_explicit_agent_command` and the CME exact-prefix name match accept a
  command found anywhere on the path, and bind the same way. Today they
  refuse the commands of ancestors and of the global scope.
- The nearest scope wins, so a command shadows one with the same short
  name in an enclosing scope.
- A qualified name (`Application/list_accounts`) must name a context on
  the path; otherwise the existing navigation message stands.
- The existing rule that a qualified token must not collapse onto a
  different command with the same short name (in
  `_explicit_agent_command`) applies within each scope.

**Planning commands** use the same path at the turn frame:

- `match_skill` runs once for each scope on the path that offers
  planning commands, with that scope's planning commands and "none", and the first
  confident match wins (Phase 1, step 2).
- While every planning command is global, this is one Jev call, as today.
- Every sub-task's run starts with the agent's plan (3.6). A confident
  match is shown to it first, with its template, and the agent calls it
  whole (the fast path, 3.6), calls it with other steps, or adapts its steps
  (2.44). Without a confident match, the run's shortlist includes the
  unsure candidates (3.10). Nothing is tried first because of its kind
  (2.20).
- Without `JEV_API_KEY`, `_skill_matcher` returns `None`, `match_skill` is
  not called, and the agent chooses and adapts a declared planning command
  itself, from its list, as it writes its plan (3.6, 3.10, 2.38, 2.44,
  2.52). A workflow that has planning commands and no key logs once, at
  load, at INFO: `"<workflow>: planning commands are chosen and adapted by
  the agent as it plans; set JEV_API_KEY to add Jev's choice and the verify
  checks of <fields>."`, naming the fields whose `verify` option is then
  inactive (2.46). Until Phase 6 gives the agent that rule, the message is the
  warning of 2.31: `"<workflow> has planning commands, but JEV_API_KEY is
  not set: no request will be matched to one; they run only when a plan or
  the agent names one in a step."`

**Filing the run.** The CME step that binds the object records the
object's context name and instance clause on the `CommandOutput` it
returns. These are two optional attributes, and when they are absent the
current context is meant. Two places read them:

- `execute_workflow_query`, for the observation's clause;
- `_hold_command_run`, for the held run's `context_name` and
  `context_clause`.

The observation and the stored run then name the object the command ran
on (2.17). The `now_in` note is unchanged: it reports where the user
stands after the command, which the lookup does not move.

**Catalogs.** Two corrections (2.19). The planner's shortlist, which
replaces its full list, is 3.10; from Phase 6 the planner's listing, and so
both corrections in it, is what a sub-task's run is shown (2.52).

- The planner's sections for other contexts
  (`get_all_contexts_command_display_text`) no longer call a command "not
  callable until then" when it is on the lookup path from the active
  context. That covers the commands of enclosing contexts and the global
  commands.
- The executor's list of other contexts (`get_other_contexts_text`,
  "Other contexts (enter one to see and run its commands)") no longer
  tells the agent to enter a context to run such a command. Navigating
  would move the current context, which running the command in place
  does not.
- In both lists, those commands are listed as callable here, each with
  the scope it comes from. Which contexts enclose the active one is read
  from the live chain when the listing is built.

**Retiring `context_hierarchy_model.json`.** Every reader changes in the
same phase:

- training: the sparse class needs no ancestors
  (`cache_ancestor_utterances` in `model_pipeline_training.py` and
  `class_balance.group_ancestor_utterances` lose their callers);
- `train/selective_training.py`: the `parent` dirtiness rule goes. Adding
  or removing any command dirties every head (2.15). Changing a command's
  seeds dirties only its own head once the recorded samples of 2.50 land;
  until then it dirties every head. `--regenerate-utterances` chooses the
  samples again;
- `command_directory.py`: drop the file from the source fingerprint;
- `command_metadata_api.py`: order the listing's sections by
  breadth-first depth over the descend edges (`collect_descend_edges`)
  instead of by ancestor count, and drop the hierarchy from the workflow
  description;
- `train/heldout_evaluation.py`, `validate_escalation_cases`: score "not
  here" against every command outside the head, instead of against
  ancestors;
- `CommandContextModel`: stop reading the file. When one exists, warn
  once per workflow that it is ignored and can be deleted (2.23).

### 3.10 What a sub-task's run is shown

The reasoning is in 2.21, 2.44 and 2.52. Everything here is gated by the
measurements of Phases 6 and 10.

**Role.** At the turn frame in agent mode, every sub-task's run starts with
a plan the agent writes (3.6). This section is what the run is shown, to
write the plan from and to run it: its `available_commands`. Until the
seventh amendment it was what the text planner, `build_query_with_next_steps`,
was shown, and this section was titled for that planner, the built-in
planning command (2.21).

- While the workflow's full listing (the one
  `get_all_contexts_command_display_text` builds today) fits within
  `FULL_LISTING_MAX_CHARS`, the run is given that listing, as the planner is
  today, and nothing below is gathered. Above that size it is given a
  shortlist instead.
- Each planning command on its list comes with its template: its steps as
  the preview renders them, every value a placeholder (3.17), with a phase
  that does not render shown as decided at run time. The templates count
  toward `FULL_LISTING_MAX_CHARS`. A planning command that `match_skill`
  matched confidently is shown first, with its template, in the run's
  request (3.6), as `_template_text` shows a matched template today: "A job
  like this is usually done by <command>: ...".
- The `plan` tool's description says how to use a planning command that
  matches the sub-task, in this order of preference: when it covers the
  whole sub-task, the plan is the one step that calls it (2.38), the fast
  path, which takes no model step after the plan (3.6); when it covers part,
  the plan calls it as one step, with plain steps before or after it for the
  rest, never repeating a command its template already runs; when the
  request needs some of its steps dropped or changed, the plan is an adapted
  copy of its steps. A declared planning command runs for the requests it
  covers whether or not `JEV_API_KEY` is set.
- The listing is the run's for every step, not only for its plan: it is
  sent with every step's prompt (2.52), re-rendered for the active context
  whenever the context changes (3.6), and gathered again after a later plan
  step. Phase 10 weighs that cost when it sets `FULL_LISTING_MAX_CHARS`.

Assistant mode has no plan step (1.4).

**Gathering.** For the sub-task's text:

1. Ask every scope on the lookup path (3.9), and every context reachable
   from the active one through declared descend edges
   (`collect_descend_edges`), each once.
2. Keep every scope's answer: the command it names confidently, or the
   candidates of an unsure answer. Do not stop at the first scope that
   recognises the sub-task.
3. Add the unsure candidates of the planning-command match (3.9).

Which model answers for each scope follows Phase 10, step 1. Until
planning commands have labels in the heads, the heads answer for
execution commands and Jev answers for planning commands.

**Expansion.** For every command on the shortlist, add:

- the producers of its inputs (its producer `from_` edges, 3.3);
- the commands that navigate to its context from the active one
  (`navigation_steps_to_context`);
- for a planning command, its callees (the callee graph, 3.7);

and add the core commands. Repeat for the added commands until nothing
new is added. In the worst case the shortlist is the whole workflow, which
is today's list.

**Listing.** Below `FULL_LISTING_MAX_CHARS`, the run receives today's full
listing (2.30). Above it, the run receives:

- each shortlisted command in full, as
  `get_all_contexts_command_display_text` shows it today, and a planning
  command with its template. A command in a
  context not yet entered carries the navigation line that
  `format_deferred_planner_command` already writes ("Before executing X,
  navigate to Y as follows: …");
- every other context as one line, in the form of the executor's list
  (`get_other_contexts_text`).

The run and a planning command's phases then use one list format. A later
plan step gathers again, from the sub-task and the user's latest response.

**A shortlist by context** (2.40) is measured beside this one in Phase 10,
step 4. It gathers and expands the same way, then lists in full every
context that holds a shortlisted command, and the active context, with all
of each context's commands of both kinds; every other context is one line,
as above. Whichever listing Phase 10 chooses is the one above
`FULL_LISTING_MAX_CHARS`, and the other is not kept. When both meet its
bar, the shortlist by context is chosen, since its recall depends on fewer
optional declarations (2.50).

**Arguments of a planned planning command.** A planning command that the
agent of a sub-task's run writes as a step runs as a nested call (3.5), or
on the fast path when it is the whole plan (3.6). Its argument checks (3.4,
The argument path) take as the request the sub-task text together with the
outputs of the turn's earlier steps (`_archived_command_runs`), not the step
text. A value the agent made up is in neither, so it is refused; a value an
earlier step found passes. The same holds for a spawned frame's steps
(3.5, Spawned frames). A planning command called from inside another keeps
its invoking step text as the request.

**One argument path** (2.25, 3.6). The fast path, a planning command called
with other steps and one called by another planning command all take their
arguments from the CME's extraction of the step that calls them. Phase 6
measures their quality against `plan_skill_call` before the typed call is
removed.

**Navigation edges.** Gathering and expansion read the descend edges
`collect_descend_edges` builds from `descends_to`, the one declaration 3.15
keeps. A command that moves the workflow without declaring it is reported
when it runs (3.15), so a missing edge shows up in development rather than
as a plan that cannot reach a context.

**Assistant mode.** Once the heads carry planning commands (Phase 10,
step 1), a head that names one produces the refusal of 3.4. Until then,
the "not here" class keeps a head from claiming a planning command's
request, and the walk ends as 3.9 says.

### 3.12 A phase's facts are typed by the commands that produce them

The reasoning is in 2.28 and 2.33.

**The forms.** A phase's return annotation, or the value of its
`@phase(output=...)` (a class, or a `lambda input:` that returns one), is
one of:

- a command's `Signature.Output`, of either kind: `-> OpenBook.Output`,
  with `from .open_book import Signature as OpenBook`, or
  `-> BookByTitle.Output` for a planning command's. The phase hands on that
  command's `Output` from its run in the phase;
- a union of commands' `Output`s, `-> FindBook.Output | FindMember.Output`:
  the `Output` of whichever of them the phase ran;
- a facts model: a pydantic model whose every field is typed with a
  command's `Signature.Output` or `Signature.Input`, a union of them, or one
  of those `| None = None`. A field typed with an `Output` gets that
  command's `Output` from its run in the phase; a field typed with an
  `Input` gets the arguments that run was called with; a `| None = None`
  field is `None` when the phase ran no such command. Properties, methods,
  validators and base classes are ordinary pydantic, and a facts model may
  live in a `_` module and be shared.

A fan-out phase hands on a list of these, one per item. Relative imports
reach a command of the same context folder (`.find_book`) or of another
(`..Book.list_loans`).

```python
class Shelf(BaseModel):                      # the sample's Book/shelf_report
    book: ShowBook.Output
    loans: ListLoans.Output

class PlanGenerator:
    def shelf(self) -> Shelf:
        return [run("show_book"), full_list("list_loans")]
```

A field typed `ShowNotes.Output | None = None` would be `None` when the phase
ran no `show_notes`, and a property such as `borrowers`, returning
`self.loans.borrowers`, gives a name of the model's own.

**Which command it is.** At load, `resolve_field_sources` (Phase 2) maps
every loaded command's `Signature.Output` and `Signature.Input` class to the
command's qualified name, by identity, hydrating commands as needed. The
class must be the command's own, so the import must reach the command's
module, not a copy of its class.

**Filling.** `fill_output` fills each `Output` and `Input`, whether it is
the whole annotation or a field, by today's rules for a phase's runs:

- the run is the phase's run of that command on the record the phase ends
  on (the context a copy edge's plain name resolved against, 3.3); for a
  union, the run of whichever member ran there, the last when several did;
- the pages of a `full_list` step are joined: list fields in page order,
  `total` from the run;
- an `Input` is the run's checked arguments, as archived with the run;
- a required field, or annotation, that no successful run fills fails the
  phase;
- for an inherited command (`Record/add_note` run on a `Member`), its run in
  any context that inherits it counts;
- then the facts model validates, so a validator may derive values or
  refuse facts, and a refusal fails the phase (talk_to_ido's `min_length=1`
  on a match's `uids` becomes such a validator).

**Load errors.**

- A facts model's field typed with anything else:
  `"<file>: <Model>.<field> is <type>; a facts field is typed with a command's Output or Input. Compute other values in a property or method of <Model>"`.
  Until Phase 15, a field that carries a copy (`fact_from`, or a `"from"` in
  its `json_schema_extra`) is not checked by this rule and keeps today's
  behaviour (3.3); after it, the message adds that copies are no longer
  read.
- A facts model's field that carries `from_`: the error of 3.3.
- A phase whose steps, over the placeholder grid, never name a command its
  facts need (the annotation's command; each field's, except a `| None`
  one; one member of a union):
  `"<file>: phase '<phase>' hands on <command>'s Output, but none of its steps runs <command>"`.

**Template and preview.** While the template is built, a phase's facts are
placeholders named by where they are read (`<find.book_uids[0]>`,
`<shelf.loans.borrowers>`). The preview's phases table names the commands
(`` `Library/find_book`'s `Output` ``; a union's members; a facts model's
fields), and its facts section lists each field and type (3.7).

**Migrating.** talk_to_ido's 145 facts models (920 copy edges) become typed
fields before Phase 15 removes copy edges (2.33):

- each group of copy fields that reads one command becomes one field typed
  with that command's `Output`, or its `Input` for an R4 copy of an argument;
- each of the 46 copy edges whose plain name several contexts define
  becomes a field typed with the command of the context its model is filled
  on (the "Context:" line of its docstring), and a union where a model is
  filled on several;
- its seven `Match` models keep `uids`, `labels` and `total` as properties
  over the find's `Output`, so `only_uid` and its callers are unchanged
  (after Phase 13, most of those callers no longer need it, 3.13);
- its `min_length` constraints become validators, and `create_model` builds
  its per-kind models (`FOUND_MODELS`, `opened_model`) with typed fields;
- the code that reads a field one level deeper follows
  (`reach.accounts.account_uids`), unless a property keeps the old name.

### 3.13 Steps: helpers for the wording the runtime reads

The reasoning is in 2.26, 2.35 and 2.47.

**The helpers.** `fastworkflow.planning` (today `fastworkflow.skill`) exports
these step helpers, beside the text helpers `listed`, `count` and `num`:

| Helper | Returns the step | What the runtime does with it |
|---|---|---|
| `run(command, **values)` | `<command> <k=v ...>` | code runs it when every required value is given |
| `full_list(command, **values)` | `<command> <k=v ...> (full list)` | code runs it, then each later page, up to `CODE_MAX_PAGES` (`FULL_LIST_PHRASES`) |
| `pick(command, named=..., x_uid=...)`, the uid optional | `<command> with the uid of the <named> match`, or with a uid `<command> x_uid=<uid>` | code picks the named row from a listing the call read, wherever it read it, and runs the command on it; with a uid, code runs it (below) |
| `when(condition, step)` | `only when <condition>, <step>` | the agent decides whether to run the step (`_CONDITION_RE` before the command) |
| `do_not_run(command)` | `do not run <command>` | a negated step code passes over, and a guard (`_NEGATION_RE`) |

`say(text)` and `no_change()`, which this table listed before the fifth
amendment, are not built: `__result__` writes an answer in code (3.16), and
a guard has no reader once nothing infers who writes the answer (2.34).

Each helper returns a `str`, exactly the text the runtime reads today, so
nothing downstream changes, and the same text written by hand keeps working.
Each takes the command's name, as the step text does (2.35). `when` accepts
another helper's result as its step.

**Picking a row** (2.47). Code runs a `pick` step without a uid on the row it
names, from a listing this call read, wherever it read it:

- the listing is the latest run among the call's own runs (its children's
  are excluded, 3.5, Attributing runs) whose arguments hold the named value
  and whose `Output` has exactly one uid list that fits the command's uid
  parameter: the list named `<x>_uids` for a parameter `<x>_uid`, or the
  list a producer `from_` on that parameter names (3.3). The pages of a
  listing read with `full_list` are joined, as a phase's facts join them
  (3.12);
- when exactly one row holds the named value whole (case, spacing and quotes
  ignored), or the listing has exactly one row, code runs
  `<command> <x>_uid=<that row's uid>` (`pick_step`'s rule, applied to that
  listing rather than only to the step just before);
- otherwise, no such listing, no row or several, the step goes to the agent
  in pick words, as today.

With a uid, `pick(command, named=..., <x>_uid=uid)` writes
`<command> <x>_uid=<uid>`, which code runs: for a rule of the command's own,
or a uid the phase also writes into another step. A `pick` without `named=`,
or with more than one keyword that ends in `_uid`, raises `StepFormError`.

**Values.** `run` and `full_list` write their values as `key=value`, in the
order given. A value that holds `(`, `;`, `=`, `, `, a bracket, a quote or
`...` is quoted (`quote_step_value`, widened from `(` and `;`); a value that
only holds spaces is not (`query=Raj Patel`), since the parser reads it whole
already. A placeholder is written as it is (`find_book query=<title>`). A
value of `None` is left out. A keyword that is not a field of the command's
`Input` raises `StepFormError` when the helper is called, which while the
template is built is the load error of an unknown parameter.

**Notes.** Every helper's step has `.note(text)`, which returns the step
with ` (text)` appended, still marked as the helper's: a note for the agent,
never sent to the command (`run("find_book", query="Dune").note("the first
page")`). The note check below applies to it.

**A note that holds a condition.** A load check runs over every step of the
placeholder grid with `finish_check`'s own rules. A command step that is not
conditional (no `_CONDITION_RE` word before its command or in its chain, and
no `_ANYWHERE_CONDITION_RE` phrase) whose note (its text from the first `(`
or `;` after the command) holds a `_CONDITION_RE` word fails the load:

`"<file>: phase '<phase>', step '<step>': the note holds a condition, but code never reads a note, so <command> would run every time. Decide it in code with if, or write when("<condition>", "<step without its note>") for the agent to decide"`

The note `(full list)` holds no condition word. Because the check is the
runtime's own rule, it cannot disagree with the runtime.

**The examples guard, and quoted values.** `skill_phases.code_step` binds a
step with the CME's key=value parser (`_extract_parameters_from_key_values`),
which declines a value equal to one of the field's `examples`, declines a
value that holds another `word=`, a bracket or `...` even when quoted, and
drops a trailing parenthetical from the last value as a note. `code_step`
only ever runs steps a `PlanGenerator` wrote (steps an agent wrote are never
run by `code_step`; the fast path runs one through the CME, 3.6), whose
values came from checked arguments or facts, so it passes the parser a flag
that skips the examples guard and takes a quoted value whole, with nothing in
it read as a key, a placeholder or a note. Parameter extraction keeps every
guard for steps an agent wrote, in its plan or later in its run.

**Hand-typed forms.** A step that a helper would write, typed by hand, still
loads and runs as today. `preview --check` warns on each, naming the helper,
over the placeholder grid:

- a command step that no helper wrote: `run`;
- a note with a paging phrase (`full list`, `every page`, `all pages`,
  `until complete`, `page through`): `full_list`;
- a condition word before a step's command: `when`;
- a negation before a step's command: `do_not_run`;
- pick words (`with the uid of the ... match`): `pick`.

To tell them apart, each helper returns a `str` subclass that marks what it
wrote; it compares, formats and joins as a `str`. The warning reads:
`"<file>: phase '<phase>', step '<step>': written by hand; write <helper>(...) so that code reads it as you mean"`.

**Not changed.** `command key=value` stays the form code runs, now written
by `run`. Plain strings stay the agent's lines. Typed step objects were
rejected (2.11).

### 3.14 What a command returns, and the result clients receive

The reasoning is in 2.29.

**One `__call__` signature.** `ResponseGenerator.__call__(self, workflow,
command, command_parameters)`: `command_parameters` is the filled
`Signature.Input`, or `None` for a command with no `Input`. The executor
(`_invoke_command_impl`, `perform_action`, `perform_mcp_tool_call`) passes
`command_parameters` whenever `__call__` declares it, and leaves it out of a
two-argument `__call__`, so every shipped command keeps working, as
`validate_extracted_parameters` gets `command_text` only when it declares
it.

**What `__call__` returns.**

| Returned | The `CommandResponse` the framework builds |
|---|---|
| its `Signature.Output` | `response` = the `Output` as JSON, with the paging line below when it applies; `output` = the instance |
| a `str` (a command with no `Output`) | `response` = the text |
| a `CommandResponse` | as returned: its own text, `output`, `artifacts`, `next_actions`, `recommendations` |
| a `CommandOutput` (shipped; not taught) | as returned |
| it raises `fastworkflow.Refused(message)` | `response` = the message, `success=False`, as today |

The framework wraps the response in the `CommandOutput` and fills its
envelope (`workflow_name`, `context`, `command_name`, `command_parameters`,
timings, call id), as `_invoke_command_impl` already does after every call. A
model that is not the command's own `Signature.Output`, or a value of another
type, fails the call, naming the command and the type.

**`success`.** Set by the framework: `True`, unless the command raised
`Refused` (a decline) or another exception (in agent mode, the executor's
"Execution error in ..." observation; in assistant mode, a failed turn), as
today. The long form still accepts `success=False`, for compatibility, and
the tutorial does not teach it.

A planning command's `__result__` returns the same forms, except
`Refused` and the shipped `CommandOutput`, and the framework builds its
response by the same table (3.4, 3.16).

**Paging.** A command is paged when its `Input` has an integer field (`int`
or `Optional[int]`) named in `PAGING_PARAMETERS` (`start`, `offset`, `skip`)
(2.49). One function returns a command's paging parameter, and every reader
of `PAGING_PARAMETERS` (`skill_phases`, `facts`, `pick_step`, this load
check) asks it, so the rule is the same everywhere. A field of another type
with one of those names is an ordinary field.

- **Load check:** a paged command's `Signature.Output` declares `total: int`,
  how many rows there are on every page:
  `"<file>: Input.<param> makes <command> a paged command, but its Output declares no total; declare total: int, how many rows there are on every page, or rename <param> if it is not a page"`.
  All 28 paged commands of today's workflows pass it, and all 28 use an
  integer.
- **The rows** are the `Output`'s list fields of one length, the columns of
  one table, as `narrowed_output` reads them.
- **The next page** is the paging value plus the rows read, while that is
  below `total`. `skill_phases._next_page` and `_more_pages` read it from the
  run (its `Input` and `Output`), and fall back to today's text match only
  for a run with no `Output`.
- **The paging line.** When the framework writes `response` from an `Output`
  and rows remain, it ends the text with
  `Rows <a>-<b> of <total>; next page: <param>=<b>.` A command that writes
  its own text writes its own paging words, if any; code-run paging no longer
  depends on them.

**A command that declares an `Output` and returns none** (a `str`, or a
`CommandResponse` without `output`) logs once per command per process:
`"<command> declares an Output but returned none; phases and from_ references cannot read it"`.
This replaces Phase 3's narrower warning, which covered only `from_`
targets.

**`artifacts`, `next_actions`, `recommendations`.** `artifacts` stays the
channel for data a client should see, on the long form, merged into the
turn's answer at finalize as today. `next_actions` and `recommendations`
stay on `CommandResponse` and on the wire, settable on the long form and no
longer taught; they leave the wire only through a versioned wire change.

**The result clients receive.** Unchanged in type: `render_turn_response`
returns the `TurnOutput` projection, with each `CommandOutput` in
`command_outputs` serialised by `model_dump(mode="json")`, its `output`
included. Two additions make the typed payload usable:

- **The planning command that answered a sub-task is an entry.** On the
  fast path (3.6) the runtime runs the planning command a sub-task's plan
  calls, right after the agent's plan step and with no model step after it,
  and appends its
  `CommandOutput`, with the `Output` its `__result__` returned as `output`,
  to `command_outputs` after the entries of the commands it ran; a planning
  command that is one step of a longer plan is appended by the agent's
  command tool, like any step.
- **Schemas.**
  - The per-command MCP server (`mcp_server.py`): `list_tools` adds
    `outputSchema` (`Signature.Output.model_json_schema()`) for a command
    that declares an `Output`, and `call_tool` (`CommandOutput.to_mcp_result`)
    adds `structuredContent` (`output.model_dump(mode="json")`) beside the
    text content. Planning commands stay out of its tools (3.4).
  - REST: `GET /command_schemas` (operation_id `get_command_schemas`, behind
    the same JWT as the other endpoints) returns, per qualified command name,
    `{"kind": "execution" | "planning", "input": <JSON Schema or null>, "output": <JSON Schema or null>}`,
    built from `CommandDirectory`, so a client can read
    `command_outputs[*].command_response.output` as the type its
    `command_name` declares.

### 3.15 Navigation is declared on the command

The reasoning is in 2.30.

- **One declaration.** `descends_to = "<Context>"` on a command's
  `ResponseGenerator`, with `descend_parameter = "<param>"` when it descends
  only when that parameter is passed, is how a command says it enters a
  context. `collect_descend_edges` reads only these; the parameters a descend
  edge needs come from the command's required `Input` fields, as
  `_required_parameters` reads them today.
- **`enter_command` and `enter_commands` are retired.** They shipped (in
  v3.4.0), so a context class that declares either is a load error (2.23):
  `"<file>: Context.enter_command is no longer read; declare descends_to = "<Context>" on <command>'s ResponseGenerator"`,
  naming the command the declaration's leading token names.
  `entry_declarations.declared_entry_commands` and its readers (the
  foreign-context refusal guard in `intent_detection.py` and the
  unavailable-command path in `context_navigation.py`) read the descend edges
  instead.
- **A move it does not declare.** When a command changes
  `current_command_context` to an object of a context it does not name in
  `descends_to`, and the command is not `go_up`, `reset_context` or another
  core command, the framework logs once per command per process:
  `"<command> moved the workflow into <Context> but declares no descends_to; declare descends_to = "<Context>" so plans can reach <Context>'s commands"`.
  The comparison is the one `execute_workflow_query` already makes for the
  `now_in` note (2.7), made in `_invoke_command_impl` so that assistant mode
  reports it too.
- **talk_to_ido** rewrites its 11 `enter_command` declarations as
  `descends_to` on the commands that enter those contexts; 18 of its commands
  already declare it.

### 3.16 The result: `__result__`

The reasoning is in 2.34 and 2.45.

**The hook.** `def __result__(self, input, <phase>, ...)` on a
`PlanGenerator` returns the call's result, in the forms an execution
command's `__call__` returns (3.14):

- a `str`: the call's answer (`CommandResponse.response`) as it is, with no
  `Output`;
- the command's `Signature.Output`: the `Output`, with its JSON as the
  response, as for an execution command;
- a `CommandResponse`: its own `response`, `output` and `artifacts`.

The cap note is appended to the text when a fan-out was capped (`cap_note`,
as today). Its parameters bind as a phase's do: `input` and the phases by
name (`skill_phases.bound_arguments`), and a phase that was skipped, filled
nothing or is not in this call's `__phases__` as `None`; a parameter that
names no phase is a load error. It runs once, after the last phase of the
call (fan-outs included), as plain code: no command, no model call. It is
not a phase (`phase_methods` skips dunders), so it adds no step and no place
in the order. The output contract of 3.4 says how its value becomes the
call's `CommandResponse`.

**The phases when it is defined.** No phase writes the answer. Every phase,
the last included, is framed as one part of the job (`phase_query`: "Do only
these steps, then finish."), so no executor run writes an answer that is
then thrown away. The last phase still receives the request, since a `when`
condition may read it. A `__result__` that returns only an `Output` has
written no text: the agent that reads the call, the parent's or the
sub-task's run's, words it, as after an execution command (2.43, 2.45).

**Without it.** The last phase's agent writes the answer, as today: from an
executor run when the phase names a command, and from one model call with
no tools when it names none (`write_answer`, with `answer_only_answer`'s
checks). Which of the two runs is the runtime's choice, not the developer's.
The call has no `Output`; declaring a `Signature.Output` without
`__result__` is a load error (3.4).

**The old form.** A last phase whose every step is `say that ...` or a guard
(`answer_by_code` true) is a load error:
`"<file>: phase '<phase>' writes the answer as 'say that' lines, which code no longer copies; return the text from __result__(self, input, ...) instead"`.
`answer_by_code` and `answer_from_steps` stay only to recognise it.

**At run time.** A `__result__` that raises, or returns something other than
the three forms (an empty `str`, or an `Output` of another class, included),
logs a warning naming the planning command, and the call keeps what it has,
with `success` unchanged: one model call writes the answer from the phases'
runs and steps (`write_answer`), as for a last phase that names no command,
and `output` is `None` (3.4).

**On the fast path** the text `__result__` returns is the sub-task's answer,
as written (2.43, 3.6).

**Template and preview.** `__result__` runs with every fact a placeholder
while the template is built, and the preview shows the text it returns under
`Answer: written by __result__` (3.7). If it does not render, for example
because it builds an `Output` from placeholders, the preview says the answer
is decided at run time (3.17).

### 3.17 The template: placeholders, and phases decided at run time

The reasoning is in 2.37 and 2.44.

**Who reads it.** The preview (3.7), and, at run time, the agent of a
sub-task's run, which sees the template of every planning command on its
list (3.10) and, when one matches the sub-task, calls the command whole,
calls it with other steps, or adapts a copy of its steps (2.44, 2.52). A
phase decided at run time (below) is shown to the agent as such, so an
adapted copy cannot hold its steps; called, the command runs it on the real
facts.

**What runs.** While the template is built (`skill_commands.placeholder_template`,
over the input grid of `_template_grid`), every phase method and `__result__`
runs with every fact a `Placeholder`.

**Placeholders.** `Placeholder` keeps what it does today: attributes,
indexes and calls give placeholders named by their path; iteration gives one
item; every test reads as true and is noted; `int()` and `float()` give
999999; `uids.index(uid)` gives 0, the first item's place; a `_` helper
called with a placeholder reads as its name; and a fact named like a `str`
method still reads as the fact. It adds arithmetic: `+`, `-`, `*`, `/`,
`//` and `%` with a number, on either side, and unary `-`, `abs` and `round`,
give a placeholder named by the expression (`<find.total - 1>`). `+` with
text still concatenates. `x is None` still cannot be seen, so the template
shows the branch where every fact exists.

**A phase that does not render.** When a phase method, or `__result__`,
raises while the template is built, other than for the errors below:

- the preview shows that phase's steps, or the answer, as `decided at run
  time`, with the exception's type and message;
- `preview --check` lists it as a warning, and does not fail for it; a
  committed preview that rendered before is stale, so `--check` fails for
  that, as for any changed preview;
- the load checks that read that phase's steps (unknown commands and
  parameters, the note check, a producer hint to the command's own callee)
  and the callee graph skip it, and the cycle guard (3.5) refuses at run
  time a cycle the graph could not see.

**Still load errors**, since each fails at run time too: a step helper
refusing its own arguments (`StepFormError`, such as `pick` without
`named=`, or `run` with a keyword its command's `Input` lacks),
`None` written into a step (`TemplateError`), and, in a step that renders,
a command the workflow does not have.

### 3.18 Running a command's code with no model, and load problems

The reasoning is in 2.39.

**The command.** `fastworkflow command run-code <workflow> <command>
[--input '<json>'] [--start-with '<step>' ...]`, beside `command preview` in
the `command` parser group (`cli.py`):

- it opens a session on the workflow as `fastworkflow run` does, the startup
  command included, then runs each `--start-with` step by code, in order, to
  put the workflow where the command starts; a step code cannot run (not a
  command with every required value written) is an error;
- `--input` gives the command's arguments as JSON. They are validated by
  its `Input`, its `validate_extracted_parameters` and its `Input`
  validators, with `command_text` set to the JSON; the field options' checks
  that compare values with a request (3.4, The argument path) do not run,
  since there is no request;
- for a planning command, it runs the call phase by phase with no model, by
  the runtime's own rules (`skill_phases.plan_code_steps`, `pick_step`,
  `runs_now`, `fan_out_items`, `fill_output`), and prints each phase's steps
  as the runtime writes them, each step code runs (`code runs: ...`), each
  move (`now in: ...`), the facts, then what `__result__` returns: the
  answer and the `Output`. At the first step code cannot run it
  prints `step <n> is open: the agent would run it and the rest`, and stops.
  A step that names a planning command runs that call the same way,
  indented;
- for an execution command, it runs the command and prints its
  `CommandOutput`;
- it exits with 0 when the run completes or stops at an open step, and 1
  when the command does not load, a step fails, or a hook raises;
- its help says that it runs the workflow's real execution commands, so it
  belongs on a development instance of the app.

**The function.** `fastworkflow.planning.run_code(workflow_folder, command,
input=None, start_with=())` returns a `CodeRun` with `text` (what the
command prints), `answer`, `output`, `facts` (by phase) and `open_step`
(`None` when the run completed), for integration tests on real workflows.
`tests/test_skill_tutorials.py`'s `dry_run` becomes a call to it.

**Load problems where developers look.** The problems are those `preview
--check` reports: every command file that did not load, with its error.

- `fastworkflow run` prints them before its first prompt.
- `fastworkflow train` exits with an error listing them, before any
  training.
- `run_fastapi_mcp` logs them once at startup, at ERROR, and serves the
  commands that loaded, as today.
