## 2. Discussion

This section records the arguments behind each decision, so the
implementer does not have to reconstruct them.

### 2.1 Could one recursive pipeline run every level?

Partly. Steps 1 and 2 (refine, split) are the same operation at both
levels. Steps 3 and 4 differ in kind:

- An execution command is Python business logic with no LLM in the loop.
- A planning command is a plan an LLM agent executes.

The useful recursion is therefore not "one function that calls itself".
It is **"a planning command's steps may name any command, including another
planning command"**. That is supported by the frame stack in 3.5. Refining and
splitting stay at the root turn; nested frames receive already-planned
step text.

*Amended by 2.51 and 2.52:* the recursion this section rejects for commands
stays rejected, but planning moves into the agent: every sub-task's run
writes its own plan, as its first step, in its trajectory. Refining and
splitting stay at the root turn (2.56), and a planning command's frame still
receives the steps its `PlanGenerator` wrote.

### 2.2 Why two class names instead of one

`__call__` means two incompatible things today:

- **`ResponseGenerator.__call__(workflow, command, command_parameters)`** is
  the entry point the executor calls (`command_executor.py:306`).
- **`PlanGenerator.__call__(self, input)`** returns the order of the phases
  (`fastworkflow/skill.py`).

An earlier draft proposed telling an execution command from a planning command by the presence
of `_process_command`. That is wrong, because `_process_command` is only a
naming convention. Inferring the mode from method names hides behaviour.
Two class names act as a one-word, explicit switch, and everything else is
shared. Readability wins over nominal uniformity.

The class names keep the kinds apart, and the method names should not
collide either: a developer who learned `__call__` on `ResponseGenerator`
reads `PlanGenerator.__call__` as its entry point. So `PlanGenerator`'s phase
chooser is renamed `__phases__` (2.29), and `__call__` means one thing: run
the command.

The same explicitness decides how a `PlanGenerator`'s methods are read,
with one rule per spelling and no inference:

- a public method is a phase (`skill.phase_methods`);
- a `_name` method is a helper;
- a dunder is a framework hook: `__phases__` chooses the phases, and
  `__output__` builds the planning command's `Output` (2.6).

A reserved plain name such as `output` or `phases` would break the first
rule, and a `_output` would break the second. `__output__` and `__phases__`
are invented dunders, which PEP 8 discourages, but they are the only
spellings that leave all three rules exceptionless.

### 2.3 Why one `from_`, with one meaning

`available_from` and `fact_from` both declare that a value comes from a
field of another command's `Output`. They differ only in where they are
written, and so in what the edge does:

| Declared on | Target field | Edge | Today's spelling |
|---|---|---|---|
| A command `Input` field (execution or planning) | An `Output` field | Producer: call that command first, and its output supplies this value | `available_from` (names the command only) |
| A phase facts model field | An `Output` field, or the run's `Input` field when the `Output` has no field of that name (today's `fact_sources` rule) | Copy: after the phase, code fills the fact from the run | `fact_from` |

One function, `from_`, replaces both, and its one meaning is in its name:
the value comes from that field. A reader who sees `from_("find_book.book_uids")`
knows the target is an `Output` field without opening `find_book`. A third
meaning, forwarding (a planning command's `Input` field passing its value on
to a callee's `Input` field, the proposed `input_from`), was part of this
idiom until the fourth amendment; it pointed the other way, and 2.27 records
why it was dropped.

*Amended by 2.33:* the copy meaning goes too. A phase's facts are typed by
the commands that produce them, so `from_` keeps only the first row of the
table above, and no facts field carries it.

Field-level references also turn the coding skill's Rules 2–4 (the producer
emits the handle the consumer accepts, both ends describe the handle, and
the hints stay true as the tree changes) into checks the tooling runs:

- the target field exists;
- the types are compatible;
- the reference still resolves after a rename.

**A producer edge does not inherit validation or lookup behaviour.** It
means "go call X first", not "resolve this value the way X does".

### 2.4 Why no layers

A layer number is tautological: it is just the longest path in the callee
graph. It also cannot be computed exactly, because an open-ended prose
step such as `f"say who wrote {title}"` names no command. Callees read
from placeholder templates are therefore a lower bound.

Using layers as policy breaks things. For example, "a layer-N planning command
sees only layers below N" would hide navigation commands and break
replans, which can legitimately reach any command. The callee graph is
kept for four jobs only:

- Cycle detection, which is a load error.
- Refusing a producer `from_` that names one of the declaring planning
  command's own callees, which is backwards (3.3, Producer).
- Display in `fastworkflow command preview` (depth shown for information).
- Adding a planning command's callees to the built-in planning command's
  shortlist (3.10), so that a plan can use parts of it. This reads the
  graph's edges, never its depth.

The same reasoning rules out ordering matching by size, and by kind
(2.20). What a matcher sees is decided by contexts, not by depth (2.13).

### 2.5 How planning commands are matched

Planning and execution commands are matched through one contract (2.20).
In each scope on the lookup path (3.9), matching answers one question over
that scope's commands of both kinds, and may answer "not here". Today the
two kinds are matched by different models:

- planning commands by `match_skill`, a typed Jev choice with per-option
  probabilities and a measured threshold (at 0.5, 96.6% of sub-tasks get a
  template and 1.1% get a wrong one);
- execution commands by the classifier heads.

Which model serves which mode is decided by measurement (Phase 10,
step 1). Until then the two keep these roles, and a planning command's
seeds join every head's "not here" class (3.9, Heads).

At the turn frame, a declared planning command that covers the whole
sub-task runs directly, as a one-step nested call (2.25). Anything else goes
to the built-in planning command, which writes the plan from the full
listing while it fits, and otherwise from a shortlist of the commands that
match (2.21, 2.30, 3.10). So nothing orders matching by kind. Planning commands may be
built from planning commands to any depth (2.1, 3.5), and depth plays no
part in matching either.

*Amended by 2.52:* the agent writes every sub-task's plan, from the listing
of 3.10. A declared planning command that covers the whole sub-task is the
one step of that plan, which the runtime runs at once (the fast path, 3.6).

The 96.6% was measured on talk_to_ido's 20 skills, none of which calls
another, so it says nothing yet about a planning command competing with
one of its callees. Phase 10 measures that case with a test set of its
own.

An earlier version of this section kept planning commands out of the
classifiers for good and routed in two steps, planning commands first and
then execution commands. 2.20 records why that changed.

### 2.6 Why the output contract matters

A parent phase reads typed facts from a child. `CommandResponse.output`
already exists for this purpose (`fastworkflow/__init__.py:41-48`). It is
optional, and many commands leave it `None`; for example,
`examples/extended_workflow_example/_commands/WorkItem/get_status.py`
builds its Output and then returns only text.

**An `Output` is built by code, at both levels.** An execution command builds its
`Output` in `__call__` from its parameters and the app, and returns it (2.29). A
planning command builds it in `__output__` from its phases' facts, received by
name as an answer phase receives them (`skill_phases.bound_arguments`). That
makes one sentence true everywhere, and lets the rest of the design treat an
`Output` the same way at every level:

- **An `Output` is public, and a phase's facts are private.** A phase's
  facts are the planning command's working memory: either the `Output` of
  the command the phase ran, as it is (2.28), or a facts model of the
  planning command's own, which may be chosen per input
  (`@phase(output=lambda input: ...)`), shared from a helper, and shaped
  for the next phase's prompt. The `Output` is one fixed class a parent's
  `from_` is type-checked against. Keeping it apart from the facts means a
  planning command can change how it works without changing what it promises.
  *Amended by 2.33:* a facts model's fields are typed with the `Output`s
  and `Input`s of the commands that produce them, instead of copying fields
  by `from_`; facts stay private.
- **No `Output` field carries `from_`.** An execution command's never could; a
  planning command's now cannot either, because its fields are assigned in code,
  not copied from runs. Copy edges live only on facts models.
- **The result may span phases or be computed.** A one-phase rule cannot
  express "the record, its risk and the connected record", or "which of
  the two people is riskier"; ordinary code can.

The alternative was to make a planning command's `Output` the facts model of one
phase. It needed five rules for planning commands only (exactly one phase; a return
annotation or `@phase(output=)`; a `lambda` only if it returns the same
class over the whole placeholder grid; no `Output` on a flat planning command)
and one exception, `Output` fields that carry copy `from_`. Keeping it as
a shortcut beside `__output__` would have added a rule and a second way to
say one thing. Nothing reads a planning command's `Output` today, so dropping it
costs no migration. The cost is a few lines in the simplest planning command,
which copies one facts model's fields into its `Output` (3.2).

`__output__` is the one place a planning command behaves differently from an execution command.
An execution command whose `Output` fails to build fails the call. A planning command whose
`__output__` raises keeps its answer, which took many steps and is still
correct, and returns `output=None` with a warning (3.4).

A parent can only read what a child emits. So:

- A planning command that declares a `Signature.Output` sets `output` to what
  its `__output__` returns (3.4).
- A field named by a producer `from_` must exist in the target's
  `Signature.Output`, and a field named by a copy `from_` must exist in its
  `Output` or `Input` (3.3). This is checked statically.
- At runtime, a command that declares a `Signature.Output` and returns
  none logs a warning naming the command (3.14). Copy edges onto an
  `Input` field are read from the archived run's parameters and need no
  `output`, exactly as `fact_from` does today.

*Amended by 2.45:* a planning command builds its `Output` in `__result__`,
which returns what an execution command's `__call__` returns: a `str`, the
`Output` or a `CommandResponse`. What this section says of `__output__`
holds for it.

### 2.7 Why a planning command leaves the workflow where it ends

Commands navigate. An execution command such as `open_identity_by_uid` moves the
workflow's current context and leaves it there; the next step starts on
that record. A planning command whose steps navigate raises the question of what
the parent sees after the call: the record the child ended on, or the
record the parent was on before it.

**The decision: where the child ended, exactly as after an execution command.** Every
command, of either kind, leaves the workflow where it ends (1.3,
item 6). A step that needs another record navigates to it. This adds
nothing to learn, and it is what skills that navigate already assume:
talk_to_ido's start at a hub and navigate explicitly in later phases
(2.12).

The parent's agent must still know where it is, or it will act on the
record it remembers. Execution commands already solve this: `execute_workflow_query`
compares the context before and after a command and, when it changed, ends
the observation with a `now_in` note (`annotated_observation`,
`workflow_agent.py`), because "a weak model otherwise reads the context the
command ran in as the one it is now in". A planning-command step goes through the
same tool function, so it gets the same note with no new mechanism (3.5).
Internally, the run held for the call records the context the child ended
on, so the parent's copy edges and `bind=True` fan-out items resolve against
the right record (3.5); authors never see this.

The note covers a command that moves the context. A command the lookup
runs on an enclosing record does not move it, and how that run is
labelled is a separate matter (2.17).

**Rejected: restore the parent's context when the child returns.** It
looks safer, but:

- the context is an arbitrary app object (`Workflow.current_command_context`).
  Restoring it in memory is easy, but a child can suspend on ask_user and
  resume in another process, so the saved context would have to be
  serialised, and fastworkflow has no general way to serialise an app's
  context objects;
- setting the context fires the context-change listeners, which refresh
  the agent's tool catalog. A restore would change the agent's tools with
  no step in its trajectory to explain it;
- it defeats children whose purpose is to land somewhere ("open the
  identity named X");
- execution commands do not behave that way, so planning commands would need their own rule.

**Also rejected: a note in the preview, for planning commands only,** saying where each
callee leaves the workflow. It would state, for planning commands only, a rule
that holds for every command, and suggest planning commands behave differently.
The preview cannot know the end context statically anyway; the `now_in`
note reports it when it happens.

### 2.8 Runtime cost, memory and scale

- **LLM calls.** Planning-command matching is one Jev call per sub-task for each
  scope on the lookup path that offers planning commands (3.9). While every
  planning command is global, as all of talk_to_ido's are, that is one call, the
  same as today. No planning command makes a typed planning call any more
  (2.25): each, the one matched at the turn frame included, gets its
  arguments from the CME parameter extraction of the step that calls it,
  which binds a `key=value` step in code and makes at most one extraction
  call for a step in words. That is cheaper than a ReAct replan, and no
  dearer than the typed call it replaces. A planning command with `verify`
  parameters adds one classifier call (`check_verdicts`, 3.4). `__output__`
  is plain code and adds no call. *Amended by 2.38:* without `JEV_API_KEY`
  there is no Jev call; the planner, called anyway for a sub-task no
  planning command matched, chooses the planning command.
- **Classifier calls.** A natural-language request asks one small head
  per scope until one recognises it, and never asks a head twice (3.9). A
  request for one of the current record's own or inherited commands stops
  at the first or second head. In talk_to_ido the worst case is 10 heads:
  a `Permission` inside an `Account` inside an `Identity` inside an
  `Organization` inside `DirectoryExplorer`, with `Resource` asked once for
  all four records, `DirectoryExplorer`'s three bases, and the global
  head. These are TinyBERT calls, with DistilBERT only when TinyBERT is
  unsure, not LLM calls.
- **The planner's prompt.** Today the planner lists every command of the
  workflow in full on every call: 58 commands and about 17,500 characters
  in talk_to_ido. As the built-in planning command (3.10) it keeps that full
  listing while the listing fits within `FULL_LISTING_MAX_CHARS` (2.30), and
  above that size lists a shortlist in full and every other context in one
  line. Gathering the shortlist asks each context's head once, along the
  lookup path and in the contexts reachable from the active one: classifier
  calls, not LLM calls. In the worst case the shortlist is the whole
  workflow, which is today's list. *Amended by 2.52:* this listing is now a
  sub-task run's `available_commands`, sent with every step of the run
  rather than once.
- **Step multiplication.** The per-phase cap is `FW_SKILL_PHASE_MAX_STEPS`
  (default 15), and a flat or non-skill executor run is capped by the
  agent's `max_iters` (default 25, `initialize_workflow_tool_agent`,
  `workflow_agent.py:826`). A fan-out phase runs one executor sub-plan per
  item, each with the per-phase cap, so one phased call can take far more
  than 15: talk_to_ido's `permission_holder_sweep` runs up to 21 sub-plans
  (315 iterations), and `department_roster_walk` up to 11 (165). Nesting
  multiplies the worst case by roughly a whole planning command's worst case per
  level. A single turn-wide step counter shared by all
  nested frames bounds what nesting adds, and the cycle guard never stacks
  a planning command twice (3.5). The turn frame keeps today's caps.
- **Memory.** A popped child frame keeps only its `CommandOutput`, and its
  trajectory and agent are released. Live memory is proportional to the
  depth of the current branch, not to the size of the whole call tree.
  Full detail is still on disk in the observability archive.
- **Scale.** Any one match sees the commands of one scope, not everything
  a context can reach, which helps both matching accuracy and prompt size
  (2.14).
- **Prompt size of richer hints.** Field-level `available_from` text is
  rendered compactly (`Ctx/cmd.field`), never as a sentence.

### 2.9 Ask_user while planning: what is new

*Superseded by 2.25.* The first design asked for a missing argument of a
planning command matched at the turn frame with a plan-time question. The
question came before any executor run existed, so it needed state of its own:
a plan-question record on the turn frame, serialised beside `_awaiting_user`
and `_pending_clarification_request`, which the resume path checked before
it looked for a suspended agent.

With one path for a planning command's arguments (2.25), there is no question
before an executor run. The matched planning command is a step of the turn
frame's executor, a missing argument comes back to that executor in the
step's observation, and the agent asks with its `ask_user` tool, suspending
and resuming exactly as for an execution command. Nothing new is serialised.

**Unattended turns never ask**, as before: `_turn_unattended`
(`workflow_execution_context.py:264`, set in `_begin_turn`) disables
ask_user (`_enable_all_tools`, `:1846-1853`), and the agent goes on without
the value.

### 2.10 Build safety

`generate_command_files(..., overwrite=False)`
(`build/command_file_generator.py:13`) writes class methods into
`_commands/<Class>/` and module-level functions into the `_commands/` root.
Once hand-written planning commands live in `_commands`, an `overwrite=True` run
could destroy them in either place. Planning-command files must be protected
unconditionally.

| Hand a fast-path call's answer to the turn executor to finish | The executor rewrites an answer code wrote, which `run-code` cannot show, and adds model calls (2.43) |
| Run a confidently matched planning command without the planner | Nothing then sees a sub-task the command covers only in part, so the rest of it is lost (2.44) |
| Let the turn executor add steps after a whole-command call | Covers parts after the call, but not parts that must come before it or an adapted copy, and keeps the executor in the fast path (2.43, 2.44) |
| Keep `__answer__` and `__output__` apart | Two hooks with one binding rule, kept for a combination neither workflow has (2.45) |
| Apply the planning commands' type-implied checks to execution commands too | Refuses values the extractor legitimately rewrites, such as a relative date written as a calendar date (2.46) |
| Keep the type-implied checks for planning commands only | A rule by kind on one extraction path, while apps hand-write the same check for execution commands (2.46) |
| Find a pick's listing by the producer `from_` alone | Two of talk_to_ido's open commands declare no producer (2.47) |
| Mark paging explicitly | One more thing to write, and a forgotten marker fails silently: `full_list` reads one page (2.49) |
| Let a head keep stale seeds of other commands | Breaks selective training's rule that a head is reused only when provably unchanged (2.50) |
| Keep the planner as a call before the agent's run | Its plans are outside the trajectory: a check on a plan cannot send it a note, its replans arrive as the workflow's responses, and distillation compares plans apart from what they led to (2.51) |
| Plan in the agent's thought, with no plan step | Nothing to check, grade offline or compare between passes (2.52) |
| A structured plan, with flags for optional and user-gated steps and the request's subjects | Tried and disabled on 2026-09-28 as too slow, a median of 12.1 s against 3.7 s (2.52) |
| Plan checks that refuse a plan, or append the steps it lacks | A check's mistake would stop a run, and code cannot tell which of a template's steps a request needs; a note leaves that to the agent (2.53) |
| A frame for every step of a plan | Every command would cost a run, with its plan step and its finish (2.55) |
| Spawning from any frame, with a depth cap | A constant to choose, and room for a small model to recurse; one level is measured first (2.55) |
| Fold the split into the agent's plan now | Trades the one planning step with a measured gain from optimization, graded exactly, for an unmeasured one (2.56) |

The edge counts come from classifying every `from` of the 145 facts models
the 20 skills load (`command.phase_outputs`) against
`facts.workflow_signatures`: 920 edges, none unresolved, and none whose type
differs from its target beyond `Optional`. The proposed type check (3.3)
therefore accepts all of them.

*Amended by 2.33:* copy edges are retired in Phase 15. Each group of copy
fields that reads one command becomes one field typed with that command's
`Output`, or `Input` for a copy of its arguments; each of the 46 edges whose
plain name several contexts define becomes a field typed with the command of
the context its model is filled on; the per-input and shared models stay,
with typed fields. 2.33 records the mapping and its cost.

**The fixes.**

1. **Copy edges keep run-time context resolution** (3.3). The draft resolved
   an unqualified name against "the declaring command's surface" and made
   two matches an error. A facts model defined in a helper has no declaring
   command, and a global skill's surface holds none of the context commands
   its phases navigate to, so all 920 edges would fail; the 46 `list_accounts`
   edges would fail as ambiguous even under a looser rule. Today's rule stays
   for copy edges: resolve against the context the phase ends on, and at load
   pass when some context resolves every field of the model
   (`check_phase_sources`).
2. **Load-time checks read `command.phase_outputs`** (3.3, Phase 2). Eight
   skills choose their facts model per input, so return annotations miss most
   models. `phase_outputs` already holds every model seen over the
   placeholder input grid. A model shared by several skills is checked once.
3. **A nested call runs the planning command's own checks** (3.4, 3.5).
   `check_arguments` does not run `validate_extracted_parameters` or the
   `Input` rules; `plan_skill_call` runs them afterwards through
   `validate_call`, and decides `verify` parameters with `check_verdicts`.
   talk_to_ido depends on both: `resolved_kind` corrects `kind` from
   catalogue lookups, `control_kind` corrects `control_is` from the value's
   shape, `record_fact` refuses a fact its kind does not have (a login's
   owner), and `identity_comparison` refuses the same person twice. The CME
   path calls the hook with the step text, but validates `Input` without the
   request in the validation context, so the rules that read it
   (`kind_conflict`) pass without checking anything. *Amended by 2.25:* the
   nested path is now every call's path, the CME no longer calls a planning
   command's hook, and `validate_call` calls it once, after the guards, as
   `plan_skill_call` did.
4. **Hand-written `available_from` is rendered verbatim** (3.3). Stripping
   `<Context>/` from every entry would change the missing-parameter message
   for talk_to_ido's 16 hand-written entries. *Superseded by 2.23:* a
   hand-written `available_from` is no longer read. talk_to_ido rewrites
   its 16 entries as `from_` references and moves their prose, such as
   "in current context", into the fields' descriptions.
5. **Moving planning commands into `_commands/` needs the app's generator to keep
   them** (Phase 7). talk_to_ido's `gen_ido_scaffold.py` deletes the workflow
   root and regenerates `_commands/`, carrying across only its
   `PRESERVE_TREES`, which list `_skills`. 3.8 protects fastworkflow's own
   build generator only. talk_to_ido's skills stay in `_skills/` until its
   generator preserves `PlanGenerator` files and the helpers they import.
   Since `_skills/` stops loading after Phase 7 (2.23), that generator
   change lands with Phase 7.
6. **The step-budget arithmetic counts fan-out** (2.8, 3.5). One
   `permission_holder_sweep` call runs up to 21 executor sub-plans (the
   right, then two fan-out phases of 10 holders each) of 15 steps: 315 model
   iterations. Nested, it would hit the draft's 200-iteration budget. The
   default is now 400.

Two smaller changes follow from the same review. A plan-time question named
a planning command by the first sentence of its docstring (3.6), because
talk_to_ido's docstrings run to several sentences of routing notes ("Not ...
(record_fact)"); *superseded by 2.25*, since there is no plan-time question
and nothing reads a docstring's first sentence alone. And the `Calls:` /
`Depth:` preview lines (3.7) make every pinned preview stale, including
talk_to_ido's (`tests/test_skill_previews.py`), which must be regenerated in
step with Phase 5.

**Decided: the two questions nesting raised for talk_to_ido.** The review
raised both; the general reasoning is in 2.6 and 2.7. They were decided by
the goal in 1.3, fewer idioms that mean the same at every level, and
checked against what talk_to_ido needs.

- **A planning command builds its `Output` in code, in `__output__`** (2.6, 3.4).
  The draft's rule, the facts of one phase, fit none of the 20 skills.
  Where the useful result is one phase's facts, that phase's model is
  chosen per input (`record_fact`'s record is one of 37 models keyed by
  kind and fact). Elsewhere the result spans phases (`inspect_entity`: the
  record, its risk and the connected record) or is computed in code
  (`identity_comparison`: which person is riskier). `__output__` expresses
  all three. talk_to_ido's facts models are already written as private
  ("Private ... never shown"), which matches the split between private
  facts and a public `Output`. Also rejected for these skills: a union of
  facts models (cannot express a computed value); an answer phase that also
  returns the `Output` (mixes user-facing text with parent-facing data, and
  answer phases have their own code path); no typed `Output` (nesting would
  pass prose).
- **A planning command leaves the workflow where it ended, like any command**
  (2.7, 3.5). Every talk_to_ido skill navigates, and later steps depend on
  where earlier ones ended: plain `from` names resolve against that
  context, a `bind=True` fan-out item must be opened inside its own
  sub-plan, and steps such as `propose_fix (on X, the current record)`
  assume the record is still open. Each skill starts at a hub
  (`open_directory`, `open_controls_monitor`, `reset_context`), so a child
  never depends on where its parent was, and later phases already navigate
  explicitly. The Phase 5 test of a parent that calls a child which opens
  record X, then acts on the current record, covers this shape.

Adopting nesting is a separate decision for each app. talk_to_ido's `_`
helpers already give reuse at almost no cost, while a nested call costs a
frame, a CME extraction, a classifier call when the child has `verify`
parameters, and a fresh navigation from a hub. Replace a helper with a
nested call only where a measured case shows a benefit; nothing in this
design gets in the way of keeping the helpers.

### 2.13 Why matching follows contexts, not the size of planning commands

Sections 2.13–2.19 record a design discussion of 2026-10-26 and an
adversarial review of its first proposals, checked against fastworkflow
`179fb80` and talk_to_ido `3abe137`.

The discussion began with a question about 2.5: does a "two-step" route
assume that planning commands cannot be built from planning commands? It does not.
Nesting to any depth is an execution feature (the frame stack, 3.5).
But matching did deserve a design. An early proposal matched from the
outermost planning commands down to their callees, then to the execution commands. It was
rejected, because the property that matters is how many commands each
model sees (2.14), and contexts already decide that. A command of either
kind is visible where its context lies on the lookup path (3.9) and
hidden elsewhere.

Ordering by size also fails on its own terms:

- It is a policy based on layers (2.4), and layers are only a lower
  bound, because prose steps name no command.
- Offering the outermost planning commands first hides any planning command that
  another planning command calls. A direct request for it is then reachable only
  through a false "part of X" answer.
- `match_skill` makes one categorical choice whose option probabilities
  are specified to sum to one (the Jev adapter,
  `dspy/adapters/decision.py` in the installed dspy). So a rule
  that prefers a caller when it and its callee both clear 0.5 can never
  fire.
- The splitter sees every planning command (`_job_types_for`) and splits a
  request into one job per subject (`split_merge.py`) before any matching
  happens. It already decides granularity. Preferring a caller over the
  callee that fits a sub-task would run the caller's extra phases.
- Walking level by level costs one Jev call per level descended instead
  of one per sub-task, for up to `MAX_SUBTASKS = 10` sub-tasks a turn.

No talk_to_ido skill calls another, so nothing there would have
benefited, but that is not the argument; one workflow is no evidence
about a feature. The argument is the mechanism above, which holds for any
workflow. Planning commands built from planning commands stay fully supported.

### 2.14 The principle: each model sees one scope at a time

Contexts exist because models degrade as the number of commands they
choose among grows: the BERT classifiers confuse more labels, and the LLM
agents pick worse tools from longer lists. So every matcher should see as
few commands as it can: one scope at a time, with a way to say "not here"
and go on to the next.

Where commands reach a model today, measured on talk_to_ido from an
`Account`:

| Model call | Commands it sees today | Under scoped lookup (3.9) |
|---|---|---|
| Intent classifier | 18 in one head: 4 own, 10 inherited from `Resource`, 4 core | 8 in `Account`'s head; `Resource`'s 10 in its own head, asked next |
| Jev planning-command match | 20 skills, all global | The planning commands of one scope per call |
| ReAct executor (`_what_can_i_do`) | 18 in full, plus one line per other context | Unchanged apart from one correction (3.9, Catalogs) |
| Planner (`build_query_with_next_steps`) | All 58 commands in full, about 17,500 characters, on every call | A shortlist in full, plus one line per other context (2.21, 3.10) |

Three alternatives were weighed against this principle and rejected:

- **Keep inheritance flattened, as today.** It needs one classifier call
  per request, but that saves the wrong thing: every head grows with
  every base it inherits.
- **Add the global commands to every head.** It has the same objection,
  with the global scope added to every head.
- **One flat head per context over everything reachable from it.** That
  means own, inherited and global commands, and the commands of every
  context that can enclose it, with no decline class and the object bound
  at execution. An adversarial review found four problems:
  - it grows talk_to_ido's record heads from 17–20 labels to 37–49;
  - it leaves 3 to 11 labels per chain of records that the live chain
    cannot run;
  - it merges distinct commands that share a short name (`list_accounts`
    of an Identity, an Application and a Repository);
  - it turns an out-of-scope request into a confident wrong answer,
    including a navigation that discards the current record.

  It also binds too late (2.17).

Walking scope by scope costs more classifier calls, but they are small
local models (2.8). Walking the bases was first rejected because, with
today's decline class, it re-creates that class's worst property (2.15).
The sparse "not here" class of 2.15 removes that objection.

### 2.15 The decline class, and a sparse "not here" class

Each context's classifier has a reserved `wildcard` label, meaning "not
mine, try elsewhere" (`nlu_labels.py`). Today it is trained on every
ancestor context's utterances that are not also valid locally, up to as
many rows as the head's own (`ratio=1.0`, `model_pipeline_training.py`
near `reserved_class_budget`). In talk_to_ido's record contexts the pool
is bigger than that bound, so the class makes up half of each such
head's rows. talk_to_ido's `docs/E2E_ISSUES.md` reports this, and it was
re-checked on its current trained artifact.

What talk_to_ido shows:

- **Wrong declines are the largest single cause of its routing misses.**
  A wrong decline escalates a request the head should have answered. They
  were 12 of 30 benchmark misses: 11 in heads where the class is 50%, and
  none in heads without the class. Its write-up calls the link
  correlational, and the figures come from August artifacts.
- **Every "escalated" end-to-end turn was a wrong decline.** All 16 turns
  its end-to-end report scores as "escalated" were for commands already
  in the current head: 9 core navigation commands and 7 `Resource`
  commands. The climb happened to rescue them. The 7 `Resource` ones would
  run on the enclosing record, not the current one, and the harness still
  counts them as successes.
- **Producers don't need the climb.** Each of its 20 hand-written
  `available_from` producers is already runnable in the declaring context.
- **Agent calls by name don't climb.** An agent's call by name to an
  ancestor's command is refused (`_explicit_agent_command`).

So talk_to_ido depends on declining correctly far more than on climbing.

The insight that unblocked the design: **the class is large because of
what it is trained on, not because a walk follows it.** Walking the bases
with today's construction would re-create it. `Account`'s own and core
commands have 243 rows, and its `Resource` and global commands have 447,
so the class would again be capped at half the head.

**The sparse class.** Train "not here" on a few seeds of *every* command
outside the head, planning commands included (2.20), with no ancestor
sampling and no fill up to a ratio. It
then means "not one of mine", which is exactly what each step of the
lookup (3.9) needs to know. With one seed per command, that is about 40–50
rows per talk_to_ido head instead of hundreds. It still covers every
foreign command, but with little weight, so the head no longer leans
towards declining.

**How many seeds per foreign command.** The value is 8 (the trainer
constant `NOT_HERE_SEEDS`; a constant, not a setting, 2.23), taken from
the convergence measurements: routing
accuracy rose with hand-written seeds per command and flattened past
roughly eight (one 160-command workflow; see the
`fastworkflow-intent-training-convergence` skill). That curve measured
seeds for a command's *own* label, not for recognising it as foreign, so
8 is a starting point that step 1 of Phase 9 confirms or replaces. It has
a cost that one seed does not. On `Account`, 8 seeds of about 50 foreign
commands give about 400 rows against 243 own rows, which is near today's
share. Two things make that acceptable to try. Diversity, not row count,
is what the convergence curve rewards. Also, capping today's class was
measured to make no significant accuracy difference (p = 0.25 routing,
p = 0.38 escalation); it only saved training time. So what the class is
trained on, every foreign command rather than ancestors, is the variable
under test, and its size is a training-time cost. That cost grows with the
workflow: on a 160-command workflow every head carries about 1,270
"not here" rows.

**It must be shown to work before it ships** (Phase 9, step 1). The risk
moves from wrong declines to wrong accepts, where a head claims a request
it cannot serve. A wrong accept runs a wrong command, so it is the more
costly error. The measurement works like this:

- **Change one thing at a time.** Keep today's flattening and climb, and
  change only how the class is built. The lookup itself is measured
  afterwards, separately (Phase 9, step 3).
- **Use a test set big enough to decide.** talk_to_ido's benchmark has
  only 11–13 decline cases. Instead, take the utterances of personas held
  out of training (`train/heldout_evaluation.py`, persona holdout). For
  every head, test its own commands' utterances, where the expected
  answer is that command, and every other command's, where the expected
  answer is "not here". Keep the benchmark and the end-to-end check as
  human-written checks, counting "escalated" only for commands the head
  cannot run.
- **Four arms:** today's class as the control; one seed per foreign
  command; eight seeds, the current value; and today's class at ratio
  0.5. If one seed meets the bar as well as eight, the constant drops to
  the smaller value, because it trains faster. Train each three
  times with different seeds, because a single retrain once moved
  escalation accuracy from 90.9% to 81.8%.
- **Measure both directions:** wrong declines; wrong accepts; top-1 and
  in-list accuracy on in-scope requests; and training rows and time.
- **Fix the bar before training.** Compare arms on the same utterances
  with a paired test (McNemar), with an interval on every rate. For
  example: wrong declines fall, with an interval that excludes zero;
  wrong accepts rise by at most 2 points at the top of their interval;
  and in-scope accuracy does not fall.
- **Choose the decline cut-off on a validation split.** Then the class's
  share of rows doesn't decide the trade-off between the two errors.
  Weighting the reserved rows was measured before and made no difference
  (a comment in `model_pipeline_training.py` records it), so it is not an
  arm.

One cost lasts. Every head's class holds a seed of every other command.
So adding or removing a command anywhere, or changing a seed the class
uses, marks every head for retraining. With `NOT_HERE_SEEDS` at 8 and the
authoring rule's eight or so seeds per command, every seed is one the class
uses, so this is the cost of a developer's most frequent edit; 2.31 makes it
part of the bar.

### 2.16 Containment: keep the climb, retire the hierarchy file

The climb (`wildcard.py`) walks the live chain of records through
`get_parent()` when a head declines. It is how a request reaches a
command of an enclosing record without navigating there. In
`messaging_app_4`, "switch to alice" said on user Bob reaches the chat
room's `set_current_user`. In `todo_list`, "create a new list" said on an
item reaches the list manager.

Removing the climb was considered, because talk_to_ido relies on
declining rather than climbing (2.15). It stays. Once the decline class
is small, the climb costs only classifier calls, and it is the
"enclosing" step of the lookup (3.9).

**Who uses it.** Besides talk_to_ido, the fastWorkflow apps on the
owner's machine were checked:

- `identity_reviews` declares review items inside collections, but it
  never enters a child context, so its climb never runs. It is an
  uncommitted July 2025 app on an older API.
- `iddm_dataconnector_codegen` and `defect_remediation` have one context
  each.
- `agent-directory` and the tau-bench retail and airline workflows have
  none.
- The bundled `todo_list` and `messaging_app_4` use the climb naturally,
  but they are demos.

That is a small sample, mostly from one team. That no app uses the climb
does not show that none needs it, which is one more reason to keep it.

**Delegation was rejected.** It was a proposed list, per context, of the
enclosing commands that context offers ("`Account` offers
`Application/list_rights`"), run on the nearest enclosing object of that
type. It is a declared, narrower version of the climb. With the climb
kept, it would add a declaration and buy nothing.

**`context_hierarchy_model.json` is retired.** It declares the same
parent edges `get_parent()` implements, and matching never reads it: the
climb follows `get_parent()`. Training reads it to build today's decline
class, and a few tools read it for ordering and display, including the
order of the planner's listing. The sparse class (2.15) does not need
it, and the descend edges serve the ordering (below).

The file also drifts. talk_to_ido's generator validates its edges because
several went missing (`gen_ido_scaffold.py`, `_validate_nav_parents`). In
`todo_list` a `TodoList` can sit inside a `TodoList`, and neither the
file nor the `get_parent()` annotation declares that.

Where a static parent graph is wanted, for ordering the command listing
or for navigation hints, use the descend edges (`descends_to` on the
navigating command, the one declaration 2.30 keeps; collected by
`context_navigation.collect_descend_edges`), reversed.

**`get_parent()` annotations are not required.** They could be enforced:
a build-time check for a return annotation that names context classes,
and a run-time check of each returned object against it, which would
catch `todo_list`'s nested lists. But once the file is retired, nothing
needs static parent types:

- training no longer samples ancestors;
- the climb uses the live chain;
- ordering and hints use the descend edges.

The cost would be real: talk_to_ido's `Account` would need a union of
four parent types, imported across modules.

### 2.17 Binding before extraction, and filing a run under its object

*Binding* is deciding which object a command acts on. A command goes
through three steps: decide which command it is, fill in and check its
inputs, and run it. The second step can need the object too.

In `messaging_app_4`, "switch to alice" said on user Bob climbs to the
chat room's `set_current_user`. Its `user_name` lookup asks the bound
object for the room's members (`ChatRoom/set_current_user.py`,
`db_lookup`, through
`workflow.command_context_for_response_generation.list_users()`). The
coding guidance tells developers to write lookups that way
(`resolve-parameter-values/SKILL.md`). If the object were bound only at
the third step, the lookup would ask Bob, a `User`, which has no
`list_users()`.

So the object is bound as soon as a scope recognises the command, before
extraction. That is what the climb does today: `wildcard.py` sets
`command_context_for_response_generation` before `ParameterExtraction`
runs. A design that bound at execution was rejected for this reason.

*Filing the run.* After a command runs inside an agent step,
`_hold_command_run` holds the run for the step's archive row, with its
name, parameters, output and the context it ran in. The agent's
observation names that context too (`annotated_observation`). Both take
the context from where the user stands, not from the object the command
acted on: `context_clause_for` reads `current_command_context`.

Suppose the user stands on an Account inside an Application, and the
climb runs `Application/list_accounts` on the Application. The run is
filed as the Account's. Two things then go wrong:

- a later copy of `accounts` "from this account's `list_accounts`" reads
  the application's accounts;
- resolved in context `Account`, the plain name `list_accounts` matches
  three commands, none of them `Account/list_accounts`, so the copy
  raises `AmbiguousFactSourceError` (`facts.py`, `_pick`).

The feedback the agent gets when the context changes does not cover this.
That mechanism (2.7) compares `current_command_context` before and after
a command: it appends the `now_in` note, and the context-change listener
refreshes the agent's tool catalog. The climb never moves
`current_command_context`; it sets only the object for one command. So no
note fires, and the run is filed under the current context.

Today this is rare in agent turns, because a call by name to an
ancestor's command is refused rather than climbed. Under scoped lookup it
becomes the normal path for enclosing and global commands. So the run and
the observation must name the bound object (3.9, Filing the run).

### 2.18 Defects found during the review

These are independent of the redesign. The first three are fixed in
Phase 9, step 2.

- A `parameter_value` prediction, which means "this is a bare value",
  starts the climb exactly as `wildcard` does
  (`resolve_fully_qualified_command_name` maps both to no command), even
  though `nlu_labels.py` declares that it is not an escalation signal.
- The planner is told that ancestor commands are "not callable until
  then" (`get_all_contexts_command_display_text`), although the router
  climbs to them.
- A run the climb executes on an enclosing record is filed under the
  current context (2.17).
- In talk_to_ido, the end-to-end harness counts a wrong decline that the
  climb rescues as a successful escalation (`tests/e2e_complex_tasks.py`,
  `route_turn`). That one is the app's to fix.

### 2.19 The planner's and the executor's catalogs

Scoped lookup narrows what the classifiers and Jev see. It left the two
largest lists sent to a model unchanged:

- the planner receives every command of the workflow in full, on every
  call: 58 commands and about 17,500 characters in talk_to_ido;
- the executor receives the current context's commands in full, plus one
  line per other context (2.14).

The planner sees the whole workflow on purpose: it plans across contexts
in a single call that cannot ask for more. Showing it one scope in full
and one line per other scope would shrink the prompt, but could hurt
plans that span contexts.

This was first left open. It is now decided (2.21):

- The planner, as the built-in planning command, receives a shortlist in
  full and every other context in one line. The shortlist is gathered so
  that it includes the contexts a plan navigates into, and it replaces the
  full list only once Phase 10 shows that plans do not suffer.
- The executor's list keeps its shape. Scoped lookup corrects what it
  says about enclosing and global commands (3.9, Catalogs), and planning
  commands are listed in it by the same rule as execution commands (3.4,
  Catalogs).

*Amended by 2.52:* the planner's list is now what a sub-task's run is shown
(3.10), and the executor's list is the list of a planning command's phases
and the answer of the `what_can_i_do` tool.

### 2.20 One matching contract for planning and execution commands

Sections 2.20–2.23 record a review of this document's non-goals on
2026-10-26, checked against fastworkflow `179fb80` and its v3.6.0 release
tag.

An earlier version of 2.5 kept planning commands out of the classifier
heads for good. Its reason was that "Book *Dune*" (a planning command) and
"find the book *Dune*" (an execution command) are near-duplicates at
different granularities, so one head would confuse them: exactly the
confusion the duplicate-capability check in `fastworkflow train` exists to
prevent. It routed in two steps: planning commands first, with
`match_skill`, then execution commands.

That reason applies just as much to Jev. Jev does not avoid the choice
between a planning command and its callee; it settles it by a fixed rule.
Planning commands were tried first along the whole path, and one won at a
probability of at least 0.5, without Jev ever seeing the callee. Its only
alternative is the option "none: None of the job types fits this
sub-task" (`_skill_matcher`). The 96.6% figure says nothing about that
case (2.5). And once nesting is on, the planner already chooses between
planning and execution commands from one list (3.4, Catalogs). The real
question is whether a small classifier can tell them apart, which is
something to measure, not a principle.

Two matchers also brought back the duplication this project exists to
remove. The design had two of each:

- **Ways to answer "not mine":** Jev's `none`, and each head's "not here".
- **Confidence rules:** `SKILL_MATCH_THRESHOLD = 0.5`, and the per-head
  thresholds set in training.
- **Ambiguity rules:** an unsure Jev call either asked the user at once
  which planning command was meant, or was dropped, while an unsure head
  that includes "not here" carries its candidates up the path and asks once at the end (3.9,
  One request, step by step).
- **Meanings of `plain_utterances`:** training seeds for an execution
  command, prompt examples for a planning command.
- **Orderings:** a natural-language request was ordered by kind first, a
  command named exactly by scope first ("the nearest scope wins").
  Ordering by kind is a two-level version of the layer policy that 2.4
  and 2.13 reject.
- **Visibility rules:** 2.13 says a command of either kind is visible
  where its context lies on the lookup path. That held for a command named
  exactly, but not for a natural-language request, because no head could
  output a planning command. The head either declined or confidently
  picked the callee.

Ordering by kind did one job that was never named. It kept a nearer
execution command from capturing a request that a farther planning
command was written for, which was the concern behind matching from the
largest planning command down (2.13). The built-in planning command now
does that job (2.21): at the turn frame, a match alone never runs an
execution command. The execution command becomes a candidate on the
planner's shortlist, next to the planning commands that also match. In the
classifier heads, the job falls to the "not here" class, which can learn
it only from planning commands' seeds.

What the old rule got right is better stated as costs to measure:

- **Where the decision is made.** In agent mode, a head is reached only
  when the executor writes something other than a command name
  (`_explicit_agent_command`: the tool "takes command names, not
  natural-language intents"). The planner and the executor pick execution
  commands from their lists. So the heads matter mostly in assistant mode,
  where planning commands are refused (3.4).
- **Capacity.** Requests for a planning command combine several things
  ("compare alice and bob and say who is riskier"). A 4-layer TinyBERT may
  not tell them apart from its callees' requests, and 96.6% right with
  1.1% wrong is a high bar.
- **Retraining.** Jev needs no training. Under the sparse "not here" class
  every head holds seeds of every command (2.15), so editing any planning
  command's seeds retrains every head.
- **Jev calls.** If execution commands joined the Jev choice, every scope
  on the path would have something to offer, so a Jev walk could take up
  to about 10 calls per sub-task in talk_to_ido (2.8), against one today.

**The decision.** Every command, of either kind, is matched through one
contract. In each scope, matching answers one question over that scope's
planning and execution commands: which command, if any, is this request
for? The answer is a command, an unsure shortlist, "not here", or a bare
value, and one walk (3.9) and one ambiguity rule act on it. The contract
fixes the question and the answer, not the model. Which model answers in
which mode (the classifier heads, Jev, or the heads with Jev when they are
unsure) is decided by measurement, with pairs of a planning command and
one of its callees as a named test set (Phase 10, step 1). Until then,
planning commands keep Jev and get no labels in the heads. Jev needs
`JEV_API_KEY`, a third-party key, and 2.31 records what that costs a
developer. The first step
needs no change to routing: every head's "not here" class includes
planning commands' seeds (3.9, Heads), so that a head stops claiming
their requests.

### 2.21 The built-in planning command

The gap that 2.20 leaves is a request that no command matches outright.
No head can output a planning command, and the request may need several
commands, or parts of several planning commands. Rather than a head
declining or guessing, such a request should go to a planner that
composes a plan from the commands that partly match.

That planner exists. It is the text planner
(`build_query_with_next_steps`), which writes a plan whenever no planning
command matches. This design calls it the **built-in planning command**.
In agent mode, every sub-task is then run by a planning command: a
declared one when it covers the whole sub-task, otherwise the built-in
one. Two parts of this already work:

- The planner adapts a matched skill's steps to the request: "drop steps
  it does not need and add steps it asks for" (`_template_text`).
- In agent mode, an unsure match in the CME returns its candidate list to
  the agent instead of asking the user (`_execute_workflow_query`, which
  runs `abort` and passes the reply on).

The change applies the same rule at the planning step. When nothing
matches outright, the candidates go to the planner instead of being
dropped or guessed, and the planner is given those candidates instead of
every command of the workflow, the question 2.19 had left open. It also
settles an inconsistency in 3.4 as first written, which listed planning
commands only "on the current context surface" while the planner listed
every execution command of every context: both kinds now reach the
planner by one rule.

**A plan, not a saved command.** The built-in planning command writes a
plan for one sub-task and keeps nothing. A declared planning command is
reviewed code with a typed `Output` and argument checks; a generated plan
has neither. If the planner keeps composing the same plan for one kind of
request, that is a hint for a developer to write a planning command,
which belongs in developer tooling, not in the runtime.

**Four conditions make the shortlist safe.**

1. **Search inward as well as outward, and keep gathering.** The lookup
   path of 3.9 climbs outward, from the current context to its bases, the
   enclosing records and the global scope, and stops at the first scope
   that recognises the request. Plans also go inward. "List alice's
   accounts", said on the directory hub, needs `Identity/list_accounts`,
   which lies on no lookup path from the hub; that is why the planner was
   shown the whole workflow (2.19). So the planning search also covers
   every context reachable through declared descend edges
   (`collect_descend_edges`). It keeps every scope's matches instead of
   stopping at the first, and gives each candidate in a context not yet
   entered the steps that navigate there. Asking that many scopes is cheap
   only with the local classifier heads, which is one more reason to
   measure planning commands in them (2.20).
2. **Build the shortlist for recall.** A classifier is trained to name the
   one right command, but the shortlist must hold every command the plan
   will use. A missing producer or navigation command breaks the plan
   without any error, which the full list never did. So matching finds the
   main candidates, and edges the design already has add the rest:
   - the producers of each candidate's inputs (the planner's prompt
     already says "Walk the graph of commands based on the
     'available_from' hints");
   - the commands that navigate to each candidate's context;
   - the callees of each candidate planning command, so that a plan can
     use parts of several;
   - the core commands.

   That is one more job for the callee graph (2.4). It still reads edges,
   never depth.
3. **Keep one line per other context.** Every context not on the
   shortlist stays visible as one line, as in the executor's list today. A
   plan can still head for a context the shortlist missed, and the
   executor sees that context's commands in full once it gets there. The
   planner and the executor then share one list format.
4. **Keep the full listing while it fits** (2.30). The shortlist exists for
   prompt size, which matters only for large workflows. Below
   `FULL_LISTING_MAX_CHARS` the planner keeps today's full listing, so a
   small workflow never depends on hints it may not declare.

**What it removes.**

- **The ambiguous-match question and its two settings.** The earlier
  design asked the user which planning command was meant when two scored
  close, because an unsure match "silently falls back to the text
  planner" (1.2, problem 2).
  Once the planner receives the unsure candidates, nothing is lost
  silently. It composes them when they are parts of the sub-task, and
  plans a step that consults the user when they are alternatives; its
  prompt already provides for consulting the user. Whether it asks when it
  should is measured (Phase 10), because LLM planners tend to guess rather
  than ask. If it guesses, the ambiguous-match question is the fallback
  design, with constant thresholds.
- **Ordering by kind.** What remains is a fast path: a declared planning
  command that covers the whole sub-task runs without the built-in
  planner. That prefers a reviewed plan to a generated one, which is a
  rule about quality, not about granularity. *Amended by 2.38:* the
  planner may choose that command too, as the one step of its plan; the
  fast path is defined by that shape, not by which model chose it.
- **The typed planning call** (decided in 2.25). The fast path runs the
  declared planning command as a nested call, with the sub-task as its
  step text, instead of through `plan_skill_call`. A planning command
  then receives its arguments one way instead of two (2.22), and the
  missing-argument question goes too (3.6), since a refused nested call
  reaches the executor as an observation. Its argument quality is measured
  against the typed call's first (Phase 6).

*Amended by 2.44:* the planner plans every sub-task. A planning command
that matches comes with its template, and the planner calls it whole (the
fast path, which 2.43 runs without the executor), calls it with steps
before or after it, or adapts a copy of its steps. A confident Jev match
no longer skips the planner.

*Amended by 2.52:* the built-in planning command is no longer a call of its
own. The agent writes every sub-task's plan as the first step of its run,
from the list this section describes (3.10), so the conditions below are
conditions on what that run is shown. The fix that follows applies to the
steps the agent writes.

**One fix.** When the built-in planner writes a planning command as a
step, that command's arguments are checked with the invoking step text as
the request (3.4). The checks that require a value to appear in the
request would then test the planner's own words, which defeats them.
Checking against the sub-task alone would also be wrong, because it
refuses a value that an earlier step of the plan found. So a planning
command called from the turn frame is checked against the sub-task text
together with the outputs of the turn's earlier steps. A planning command
called from inside another keeps its invoking step text as the request,
as 3.4 specifies.

**Assistant mode has no planner, and gets none.** It routes one message
to one execution command. A request there that needs a plan gets the
refusal that 3.4 gives a named planning command ("it runs in agent
mode"), rather than a confidently wrong command, and is never handed to
the agent silently. To recognise such a request, the heads need planning
commands: as labels, so that the refusal can name the command, or at
least in their "not here" class, so that a head stops claiming the
request (2.20).

### 2.22 Argument types follow the mechanism, not the kind

An earlier non-goal kept `_spec_from_field` narrow. A planning command's
`Input` field may today be only `str`, `bool`, `int`, a `Literal` of
strings, or `Optional[str] = None`; a `bool` must default to false, and a
`default_factory` is refused (`_spec_from_field`, `_parse_param`). An
execution command's field may have any type Pydantic and the parameter
extractor handle. As a design rule, that would mean planning commands need
special type rules, which contradicts 1.3, item 2.

None of these limits comes from Pydantic. They come from machinery that
exists only on the planning-command path, where an LLM fills the
arguments from the user's words and the plan then expands into many
steps:

- **The argument checks** (`check_arguments`). A `str` must appear word
  for word in the request; an `int` marked `in_request` must be a number
  the request writes; a `bool` stays false unless the request asks for it;
  a `subject` must name a record of the request; and `verify` arguments
  are decided again by a classifier (`check_verdicts`). Each check is
  written per type, and none exists for a list or a float.
- **The sample-value runs at load** (`_template_values`,
  `_template_grid`). The plan is run for every combination of sample
  inputs: `<name>` for a string, true and false for a bool, the default
  (or 1 and 0) for an int, and each value of a `Literal`. Those runs
  render the preview, check that every step names a real command, and
  collect the facts models that the `from_` type check reads; this design
  also builds the callee graph from them. Each type needs a small, fixed
  set of sample values.
- **The typed planning call** (`typed_signature`), which maps exactly
  `str`, `bool`, `int` and `Literal` onto the DSPy signature. *Removed by
  2.25.*

These limit how arguments are filled and checked, not what a planning
command is. The design itself shows it. A nested planning command receives
its arguments from the same CME parameter extraction an execution command
uses, and then runs the checks (3.4, The argument path). As first written,
one planning command therefore had two ways of receiving its arguments,
which supported different types. Under one argument path (2.25) every
planning command receives its arguments from that extraction, which handles
any type the extractor supports, so what stays type-specific is the checks
and the sample-value runs.

**The decision.** The type rule is stated per mechanism, not per kind of
command:

- an `Input` field may have any type the parameter extractor supports;
- each check key (`strip`, `subject`, `verify`, `means`, `in_request`)
  declares the types it applies to, as most already do (`in_request` is
  int-only, `subject` str-only);
- for a type with no small, fixed set of values, the sample-value runs use
  one sample value.

Widening is Phase 11, after Phase 5 has built the nested path. Taken
further, the check keys could become field options of any command's
`Input`, run after extraction; with one argument path nothing in the design
stands in the way, but it changes how shipped execution commands are
checked, so it is outside this project. talk_to_ido needs none of this: its
20 skills use the four supported types (2.12).

*Amended by 2.46:* the check keys become options of any command's `Input`
field, and no check is implied by a field's type, for either kind.

### 2.23 Names, compatibility and settings

**Nothing about planning commands has shipped.** `fastworkflow/skill.py`,
`skill_phases.py`, `skill_commands.py` and the tutorial workflow's
`_skills/` folder are all absent from the v3.6.0 tag, and the next release
is a major one. The earlier non-goal "No renaming of public APIs other
than those listed here" assumed the opposite, and is dropped: reducing
idioms is the overarching goal, and renaming serves it. So the names this
project replaces get no aliases and no deprecation period:

- `fact_from` is removed; `from_` replaces it (3.3).
- `fastworkflow skill preview` becomes `fastworkflow command preview`,
  with no alias (3.7).
- `_skills/` loads until Phase 7 moves its files. After that, a workflow
  with a `_skills/` folder fails to load, with a message that names
  `_commands/` (3.1).
- The three `FW_SKILL_*` settings become constants (below).
- `PlanGenerator.__call__` becomes `__phases__` (2.29). A `PlanGenerator`
  that defines `__call__` is a load error naming `__phases__`.
- Forwarding and the `kind=` keyword of `from_`, both proposed by this
  document, are dropped (2.27).
- `plan_skill_call` and `typed_signature` are removed once Phase 6's
  measurement passes (2.25).

**What did ship fails visibly.** Four released things change in the
next major release: `available_from`, `context_hierarchy_model.json`
(taught in the public `fastworkflow-article-4.md`), the trained
classifier heads, whose labels change under scoped lookup, and
`enter_command` / `enter_commands` on context classes (2.30). Each break
names what to do instead, and none is kept working beside its
replacement:

- A hand-written `available_from` is a load error naming `from_` (3.3).
  All 19 such declarations in the bundled examples are plain command
  names, so each becomes a command-only `from_` (Phase 2). talk_to_ido's
  16 prose entries, such as `'Application/list_rights in current
  context'`, become `from_` references with their prose moved into the
  field's description. Since every entry is then written by `from_`, the
  earlier design's `available_from_generated` key is not needed.
- A `context_hierarchy_model.json` that is still present is ignored, with
  a warning once per workflow that it can be deleted (3.9).
- A workflow whose heads were trained before scoped lookup fails to load
  with "retrain with `fastworkflow train`", instead of the runtime keeping
  both kinds of head (Phase 9).
- A context class that declares `enter_command` or `enter_commands` is a
  load error naming `descends_to` and the command to put it on (3.15).

Two released things do not change, though a review proposed removing
them: `next_actions` and `recommendations` stay on `CommandResponse` and
on the wire, because they are fields of every `CommandOutput` clients
receive (2.29). The tutorial no longer teaches them.

The one hard constraint is talk_to_ido, the largest workflow with
planning commands (2.12). Its generator rebuilds `_commands/` and keeps
only `_skills/` (2.12), so its generator change has to land
together with Phase 7.

**Fewer settings is a goal** (1.3). A setting exists only where no single
value suits every app; every setting is optional, with a good default
wherever one is available; and no setting exists only to be retired, such
as a switch back to the old behaviour or an experiment's arm. Applied to
this project:

- `FW_COMPOSITE_NESTING` and `FW_SCOPED_LOOKUP` are dropped. They only
  switched back to the old behaviour, and the comparison arms belong in
  the Phase 9 experiment script, where the 0.5-ratio arm already is.
- `FW_SKILL_ASK_MIN_PROBABILITY` and `FW_SKILL_ASK_MAX_GAP` go with the
  ambiguous-match question (2.21).
- `FW_COMPOSITE_MAX_DEPTH` is dropped. The cycle guard refuses a planning
  command that is already on the stack, so nesting can never be deeper
  than the number of planning commands, and the turn budget bounds the
  work.
- `FW_NOT_HERE_SEEDS` becomes the trainer constant `NOT_HERE_SEEDS`, whose
  value Phase 9 chooses.
- The three unreleased `FW_SKILL_*` settings (`FW_SKILL_PHASE_MAX_STEPS`,
  `FW_SKILL_FANOUT_MAX_ITEMS` and `FW_SKILL_FACTS_MAX_LIST_ITEMS`) become
  constants. A fan-out phase already declares `max_items=` in code; a
  per-phase `max_steps=` can be added if an app ever needs more steps; and
  the facts list cap only bounds prompt size.
- `FW_TURN_MAX_STEPS` stays, optional, with a default of 400. It is the
  one bound that varies by app: how much work a single turn may cost.
- The size below which the built-in planner keeps the full listing is the
  constant `FULL_LISTING_MAX_CHARS`, whose value Phase 10 chooses (2.30).
  It is not a setting: the size at which a shortlist starts to pay depends
  on the planner's prompt, not on the app.

**One vocabulary.** A command is an execution command or a planning
command. "Skill" already meant the guides for coding agents (the
`SKILL.md` files, including those shipped in
`fastworkflow/skills_for_coding_fastworkflows/`), and "composite" and
"leaf" were this document's own words: three names for one concept, the
kind of duplication this project removes.

- `PlanGenerator` keeps its name.
- `ResponseGenerator` keeps its name too. It fits "execution command"
  less neatly than `PlanGenerator` fits "planning command", but renaming
  it would touch every command file in every released workflow.
- `ExecutionFrame` was renamed `PlanFrame` before it was built. A frame
  that runs a planning command should not be called an execution frame,
  and every frame runs one plan: the turn's or a planning command's.

3.11 lists the renames.

### 2.24 Testing the design against its goal

Sections 2.24–2.31 record a review of 2026-10-26 that tested the design
against the goal in 1.3: fewer idioms, meaning the same at every level. It
was checked against fastworkflow `179fb80`, against the tutorial
(`docs/tutorials/skills/`) and its sample workflow
(`fastworkflow/examples/library`) written for this design, and against
talk_to_ido `3abe137`. Counts of today's command files below leave the
tutorial's sample out, since it is written for this design.

**What the design achieved.** It unified where commands live and how the two
kinds are registered, scoped, matched and returned: one `_commands/` tree,
one registry, one `Signature` with a public `Output`, one rule for where a
command leaves the workflow, one scoping rule, and no hierarchy file or
`FW_SKILL_*` settings.

**Where it fell short**, measured against everything a developer writes or
meets rather than against the shared core:

- **One spelling over several behaviours.** `from_` had three meanings and
  needed `kind=` to tell two of them apart (2.27). A missing argument was
  handled three ways, by the kind of command and where it was called from
  (2.25). A plain command name resolved by different rules in a producer
  `from_`, a step and a copy edge (2.27).
- **The two largest planning-only idioms were not examined.** Most of the
  tutorial's fifteen pages, and most of the mistakes that fail silently, are
  about the wording of steps (2.26) and the facts a phase hands on (2.28).
- **Two optional hints became correctness requirements** for the built-in
  planner without being required, checked or present in the bundled
  workflows (2.30).

**The success list could not test the goal.** 1.3's eight items count what
the two kinds share, not what a developer learns. As written before this
amendment, the design added about 25 load errors, about 20 of them for
`from_` and `__output__`. Failing loudly is right, but each error is a rule
to learn, and the count showed where the design's own complexity was.

**The decisions.**

- 1.3 now has an inventory of every name, key, phrase and file a developer
  meets, each marked shared or kind-specific.
- Each phase says which rows of the inventory it adds, changes and removes,
  and justifies any rule it adds without removing one (section 4, general
  rules).
- 2.25–2.31 record the changes the review made, each with its reasoning.

### 2.25 One path for a planning command's arguments

**Three ways to ask for a missing argument.** As first written, a missing
required argument was handled three ways:

- an execution command's: the CME parameter extraction's message
  ("Missing parameter values: ... Provide corrected parameter values ..."),
  which the user reads in assistant mode and the agent in agent mode;
- a turn-frame planning command's: a new plan-time question built from the
  docstring's first sentence and the field's description, with its own
  reply classifier and its own serialised record (3.6 as first written);
- a nested planning command's: never asked; the refusal went back to the
  caller's agent.

So 1.3's item 5, "`ask_user` behaves the same everywhere", held for
suspension but not for a missing argument, the commonest reason a command
needs the user.

**Two argument paths.** The turn frame filled a matched planning command's
arguments with the typed planning call (`plan_skill_call`), and a nested
call filled them by CME extraction of the step text. The two paths:

- supported different types, which is the root of the type split 2.22
  records;
- ran the checks in different places;
- ran `validate_extracted_parameters` twice on the nested path, once in the
  CME and once in `validate_call`, which the design turned into a
  developer rule ("hooks must be idempotent").

**The fix was already designed, and scheduled late.** 2.21 and 3.10
proposed running the turn-frame fast path as a nested call, with the
sub-task as its step text, and removing `plan_skill_call`, the plan-time
question and its record if the arguments were as good (Phase 10, step 4 as
first written). That step waited behind Phase 9's training work, while
Phase 6 first built the question it would delete, and the tutorial already
taught the question's rules. It needs only Phase 5's nested path.

**The decision.**

- **The fast path is a nested call.** A planning command that `match_skill`
  matches confidently runs as a one-step plan of the turn frame's executor,
  whose step calls it with the sub-task as its text (3.6).
- **Every planning command's arguments arrive one way:** CME parameter
  extraction of the step that calls it, then the checks of 3.4
  (`check_verdicts`, `check_arguments`, `validate_call`).
- **The hook runs once.** The CME does not call a planning command's
  `validate_extracted_parameters`; `validate_call` calls it, after the
  guards, as `plan_skill_call` did. A hook that corrects an argument
  (talk_to_ido's `resolved_kind`) must not run before the guard that checks
  the argument is written in the request. No idempotency rule remains.
- **A missing argument** comes back as the CME's message, the one an
  execution command's gets, and the agent asks with its `ask_user` tool.
  Unattended turns never ask.
- **The rule sentences** of 3.4 (Descriptions) are appended to the field
  descriptions the extractor receives for a planning command's `Input`: the
  one place a model fills arguments those rules then check.
- **Removed or not built:** `plan_skill_call`, `typed_signature`, the
  plan-time question, its record, `allow_plan_question`, and the `param` /
  `reason` attributes of `SkillInputError`.
- **The fast-path frame is not counted** against `FW_TURN_MAX_STEPS`, as
  the turn frame is not: the call is the sub-task's own run, not work that
  nesting adds. The frames below it count.
- **Phase 6 is now this change, measured first**: argument quality against
  `plan_skill_call` on talk_to_ido's benchmark and end-to-end check. If it
  fails the bar, the plan-time question as first written (3.6, in this
  file's history) is the fallback.
- With one path, the check keys (`strip`, `subject`, `verify`, `means`,
  `in_request`) could become options of any command's `Input` (2.22); that
  stays outside this project.

*Amended by 2.43, 2.44 and 2.46:* the fast path is the planner's plan of
one step calling a planning command, which the runtime runs without the
turn frame's executor, and whose text is the sub-task's answer (2.43); a
confident Jev match goes to the planner with the command's template (2.44).
The check keys become field options of any command, checked in the one
validation step every command's arguments pass through, with the rule
sentences attached to the options rather than to the kind (2.46).

### 2.26 Steps: the words the runtime reads are written with helpers

**The step language.** A planning command's steps are text the agent reads,
and code reads them too (`skill_phases.code_step`, `pick_step`,
`answer_step_kind`; the condition and negation rules of `finish_check`;
`FULL_LIST_PHRASES`). Its rules depend on wording:

- code runs `command key=value` when every required value is written; a
  value equal to one of the field's `examples` makes the key=value parser
  decline the step, as it declines a placeholder, so code hands the step to
  the agent;
- a note in parentheses is never sent, and only five phrases in it
  (`full list`, `every page`, `all pages`, `until complete`,
  `page through`) read every page, so `(all of them)` reads one, which
  only the preview's "Pages:" line shows;
- a condition word before the command or in its chain leaves the step to
  the agent, but "a condition in a note ... is never read: that step is a
  plain command step, held to a run and run by code"
  (`docs/skill_phases.md`), so `renew_loan loan_uid=l1 (only when overdue)`
  renews unconditionally;
- a negation word before the command makes code pass the step over;
- `say that ...` is copied into the answer word for word, `say ...` is the
  model's to write, and a line that starts with `apply`, `do not`, `never`
  or `make no` and holds a negation word is a guard.

talk_to_ido keeps phrase constants (`PAGING`, `FIRST_PAGE`) to keep this
wording consistent across its skills. The design never examined it, though
it is the largest idiom only planning commands have, and 2.2's argument
against inferring a mode from method names ("hides behaviour") applies with
more force to inferring a step's behaviour from its English.

**The decision.**

- `command key=value` stays the one form code runs.
- Every other wording the runtime acts on gets a helper in
  `fastworkflow.planning`, beside `pick` and the text helpers `listed`,
  `count` and `num`: `say(text)`, `full_list(command, **values)`,
  `when(condition, step)`, `no_change()` and `do_not_run(command)` (3.13).
  Each writes exactly today's words, so the planner, the agent, the finish
  check and talk_to_ido's strings are unaffected. A misspelt helper fails
  where the developer sees it; a misspelt phrase did not.
- The dangerous cases fail visibly:
  - a note that holds a condition word is a load error, found with the
    runtime's own condition rule (`finish_check._CONDITION_RE`), so the
    check cannot disagree with the runtime. That is what separates it from
    the docstring check 2.11 rejects;
  - the examples guard is skipped for steps code wrote: their values come
    from checked arguments and facts, not from a model that might copy an
    example. Steps the planner or the agent wrote keep it.
- Paging is read from the run, not the text (2.29), which makes `full_list`
  reliable for every paged command.
- Typed step objects for every line were rejected (2.11): they would
  rewrite every line of talk_to_ido's 4,800, including the lines whose
  wording the runtime never reads.

*Amended by 2.34 and 2.35:* `say` and `no_change` are not built, since
`__answer__` writes an answer in code; `run` writes the step code runs, so
that the commonest step has a helper too; and a hand-typed form a helper
writes still loads, with a `preview --check` warning naming the helper.

### 2.27 Why forwarding was dropped

**Why it was included.** Forwarding let a planning command's `Input` field
point at a callee's `Input` field and borrow its `description`, `examples`
and `pattern`. It had four reasons when this document was first written:

1. **Descriptions drifted** (1.2, problem 5): authors restated a callee's
   description and examples on the skill input by hand. A description then
   also carried instructions to the model ("the item's name exactly as the
   request writes it", which `docs/skill_file_layout.md` still teaches), so
   each restatement copied those too.
2. **The typed planning call read the description.** 3.3 ran forwarding
   before `command_from_module` so that the borrowed text reached
   `typed_signature`, and borrowed `examples` guided that call.
3. **It completed "one cross-reference idiom"**: 1.2, problem 3 counted the
   proposed `input_from` as the third idiom to fold into `from_`.
4. **A borrowed `pattern`** would refuse a malformed value of the planning
   command's input before its plan started.

**Why they no longer hold.**

1. The third amendment moved model instructions out of descriptions into
   rule sentences the framework appends (3.4, Descriptions). What is left
   to borrow is a short phrase saying what the value is, and the caller's
   phrase often should differ: the sample's `note_member.member` replaced
   the borrowed "words of the member's name", which the tutorial called
   "wrong here", because a search fragment is not a whole name.
2. With one argument path (2.25) there is no typed planning call. A planning
   command's arguments are extracted from the step that calls it, and a step
   such as `book_by_title title=Dune` is bound by the key=value parser before
   any model reads a description. Borrowed `examples` had meanwhile turned
   harmful: code declined a step whose value equals an example, and
   forwarding copied them into the planning command's own fields.
3. `input_from` was never built: it appears in no code, issue or app, only
   in this document. Folding it in unified nothing that existed, and gave
   `from_` a second meaning that pointed the other way ("this value is
   passed to X", not "comes from X"). The reference alone did not say which
   meaning applied: the reader had to know whether the target field was an
   `Input` or an `Output` field, and the sample's `book_loans` needed
   `kind="input"` to say it. It was also the only reason for the load error
   on a field the target has in both its `Input` and its `Output`.
4. Patterns are declared only in the retail and messaging examples (ids,
   emails, zip codes), retail's with a `|NOT_FOUND` alternative tied to the
   execution command's default convention, and the callee checks its own
   pattern when its step runs anyway.

talk_to_ido never needed it: its review (2.12) lists everything its 20
skills use, without forwarding, and its `name` input goes to a different
find command depending on `kind` (`find_identity`, `find_account`, ...),
which a single forwarding target cannot describe.

**What survives**, one `description=` per input whose callee's description
happens to fit, is served without an edge: the preview shows, beside each
input, the field of the command the template passes it to, with that
field's description (3.7). It already renders `find_member query=<member>`,
so it knows which input goes where.

**The decision.** `from_` means only "the value comes from that command's
`Output` field": a producer hint on an `Input` field, a copy on a facts
field (2.3, 3.3). `kind=` leaves the public API; talk_to_ido's copy edges,
written as `json_schema_extra={"from": ...}`, never used it. The
both-sides load error goes. A `from_` on an `Input` field whose target is an
`Input` field is a load error that says to write a description instead.
*Amended by 2.33:* the copy on a facts field goes as well, so `from_` is
only the producer hint.

**One confusion goes with it.** A command name was resolved by different
rules in a producer `from_` (the declaring context's static path, so an
enclosing context's command must be qualified), a step (the live path, where
the climb finds it) and a copy edge (the context the phase ended on). The
case developers met was forwarding: `note_member`'s
`from_("Record/add_note.text")` had to be qualified, while its step
`add_note ...` did not. Without forwarding, `from_` on an `Input` field
names a producer to run before this command, from where this command is
declared, and its rule follows from that.

### 2.28 A phase may hand on a command's `Output`

Once every command returns a typed public `Output` (2.6, 2.29), most facts
models re-declare one:

- in the tutorial's sample, all 13 facts models took every field from a
  single command;
- in talk_to_ido, 31 of the 68 facts models its helpers and skills declare
  statically do, and the other 37 combine two to four commands;
- copy edges were 28 of the sample's 34 `from_` uses, and about 920 of
  talk_to_ido's 940;
- `book_by_title`, the example of 3.2, declared the same four fields three
  times: `open_book.Output`, then a `Book` facts model that renamed
  `book_uid` and `title` to `uid` and `name`, then an `__output__` that
  renamed them back.

**The decision.** A phase's return annotation, or its `@phase(output=...)`
value, may be a command's `Signature.Output`, of either kind, imported from
the command's own module (`from .open_book import Signature as OpenBook`;
`-> OpenBook.Output`). The phase then hands on that command's `Output`
from its run in the phase, as it is (3.12). Facts models stay for combining
the fields of several commands, for names of the planning command's own,
and for one shape shared by alternatives (talk_to_ido's per-kind models).

- **Privacy.** 2.6 keeps a planning command's own `Output` apart from its
  facts, so that the command can change how it works without changing what
  it promises. That concerns the command's own result. A callee's `Output`
  is already public, and a facts model's copy edges are type-checked against
  it anyway, so handing it on adds no coupling.
- **The references are Python.** An imported `Signature` fails at the import
  when the command is renamed or moved, and an editor follows it; a `from_`
  string needs the load-time checks.
- **The cost** is a second way to declare a phase's facts. The gain is that
  a developer meets facts models only when combining sources, and that
  `__output__` shrinks to a line in the common case (3.2).
- **Inference was rejected** (2.11): the annotation says which command's
  `Output` the phase hands on, and a phase whose steps never run that
  command is a load error.

*Amended by 2.33:* the second way becomes the only one. A facts model stays
for combining several commands, for names of the planning command's own and
for one shape shared by alternatives, but its fields are typed with the
commands' `Output`s and `Input`s instead of copying fields by `from_`, and a
union of `Output`s covers alternatives without a model.

### 2.29 What a command returns, and the result clients receive

**What each field of the response is for.** An audit of the 156 command
files of the bundled examples, the test workflows and talk_to_ido, against
the framework's readers:

| Field | Set by app commands | Read by | Under this design |
|---|---|---|---|
| `output` | 52 of the 132 that declare an `Output` | facts, `pick`, `from_`, the run archive | the return value |
| `response` | all; 25 write the `Output` as JSON by hand | the agent, the user, code-run paging | the `Output` as JSON, unless the command writes its own text |
| `success` | none sets `False` (2 raise `Refused`) | turn success, MCP `isError`, code steps | set by the framework |
| `artifacts` | 2 (talk_to_ido) | the turn's answer, the CLI, the chatbot UI, observability | kept, on the long form |
| `next_actions` | 3 (talk_to_ido) | the CLI printer, and any client reading the wire | kept on the wire; not taught |
| `recommendations` | none | the CLI printer, and any client reading the wire | kept on the wire; not taught |
| the `CommandOutput` envelope | none | — | built by the framework, which already overwrites its identity fields after every call |

So today's idiom makes the wrong thing the easy thing. 80 commands build an
`Output` and then discard it into text, among them every command of
`tests/example_workflow` and `tests/todo_list_workflow`. The bundled
`simple_workflow_template` reports a failed create as
`Output(success=False, error_msg=...)` inside a `CommandResponse` whose
`success` stays true, so turn success and MCP `isError` report a success.

**The decision: a command returns what it has, and the framework builds the
rest** (3.14). `__call__(workflow, command, command_parameters)` returns its
`Signature.Output`, or a `str` when it has no `Output`, or a
`CommandResponse` when it writes its own text or sends `artifacts`; it
raises `fastworkflow.Refused` to decline. Returning a `CommandOutput` keeps
working, because it shipped, but is not taught. One `__call__` signature
serves every command: `command_parameters` is `None` for a command with no
`Input`, and adding an `Input` no longer breaks the call. A `PlanGenerator`
uses `__phases__` for its phase order, so `__call__` means one thing (2.2).

**What would break, and how it is closed.**

- **Code-run paging.** `skill_phases._next_page` and `_more_pages` found the
  next page by matching `start=<n>` in the response text, which JSON never
  holds; only commands whose text prints it (talk_to_ido's, through a shared
  listing helper) paged at all. Paging is now read from the run: the paging
  parameter in the `Input` (`start`, `offset`, `skip`), the rows in the
  `Output`'s list fields, and `total`. A paged command must declare `total`,
  a load check that all 28 paged commands of today's workflows already
  pass. The response the framework writes for a paged command ends with
  `Rows <a>-<b> of <total>; next page: <param>=<b>.` when rows remain.
- **Guidance written as text.** talk_to_ido's responses tell the agent
  things ("Offer: propose_fix for remediation options ...") and bound their
  own size: `open_portrait` measured 12.7 KB on average and 18.3 KB at most
  when unbounded. Fixed guidance belongs in `Output` field descriptions,
  which the executor's catalog already shows and talk_to_ido already uses
  ("Pass one to a command that asks for an identity_uid."). Guidance that
  changes per call, and bounded or human-oriented text, uses the long form.
  No hint channel is added, and nothing is rendered specially (2.11).
  Retail's text-only `Output`s (`user_details: str` and the like) belong
  here too.
- **`success`.** No command sets it, so it is the framework's: true unless
  the command raises `Refused` (a decline, whose message is the response) or
  another exception (in agent mode an "Execution error" observation the
  agent can recover from; in assistant mode a failed turn). A failure that
  carries data is lost; nothing needs it, and an optional payload on
  `Refused` is where it would go.
- **`artifacts`** stays the client channel, on the long form. The
  framework's own commands keep using it for their signals (`command_name`,
  `cmd_parameters`, `command_handled`).
- **`next_actions` and `recommendations`** have no reader in the framework
  but the CLI printer, which in agent mode prints only the synthesized
  answer, where they are never merged. But they are on the wire:
  `render_turn_response` serialises every `CommandOutput` in full
  (`model_dump(mode="json")`). So they stay. A field leaves the wire only
  through a versioned wire change, as `command_responses` did in v3.0.

**The result clients receive is the envelope, and it stays.**
`invoke_agent`, `invoke_assistant` and `perform_action` all return the
`TurnOutput` projection
`{turn_key, exec_state, status, failure_reason, success, answer, command_outputs}`,
over REST and as the fastapi-mcp tools of the same names. Its type never
depends on which command ran. A text-in API cannot have a fixed result type
per command, because the command is chosen at run time; so the stable type
is the envelope, and the typed value inside it is each command's `output`,
labelled by its `command_name`. Moving the envelope's construction into the
framework makes it more uniform, not less: the 80 commands that send
`"output": null` today, and the template's `"success": true` for a failure,
cannot recur.

Two gaps kept that payload from being usable:

- **A turn answered by a planning command had no typed result on the wire.**
  `append_turn_output` ran for ask_user entries, deterministic commands and
  the agent's tool calls. A planning command called as a step went through
  the tool and was in `command_outputs` with its `output`; one matched at
  the turn frame was not, so its `__output__` reached clients only as
  `answer` text. With the fast path a nested call (2.25), the matched
  planning command is a step of the turn frame's executor, and is appended
  like any command.
- **Clients could not find a payload's type.** No endpoint published command
  schemas. The per-command MCP tools (`mcp_server.py`) published
  `inputSchema` but nothing for output, and returned only the `response`
  text and `isError`. A per-command MCP tool now publishes its
  `Signature.Output` as `outputSchema` and returns the value as
  `structuredContent`, keeping the text; REST gains `GET /command_schemas`,
  each command's kind and `Input` and `Output` schemas by qualified name.

*Amended by 2.43 and 2.49:* the fast path runs without the turn frame's
executor, so the runtime appends the planning command's `CommandOutput` to
`command_outputs` itself, as the agent's command tool would (2.43). Only an
integer field named `start`, `offset` or `skip` makes a command paged (2.49).

### 2.30 Navigation declared once, and a full listing for small workflows

The built-in planner depends on two hints for recall, producer `from_`
edges and descend edges: "a missing producer or navigation command breaks
the plan without any error, which the full list never did" (2.21). The
tutorial told developers that the edges they "already declare" decide what
it can reach. But:

- outside talk_to_ido and the tutorial's sample, no bundled example or test
  workflow declares `descends_to` or `enter_command`, so each context
  reached by descending was listed to the planner as "To enter: no declared
  navigation path" (`get_other_contexts_text`);
- the same fact could be declared on either side: on the navigating command
  (`descends_to`, `descend_parameter`) or on the target's context class
  (`enter_command(s)`, with its own `<param>` markup), merged by precedence
  in `collect_descend_edges`. `entry_declarations.py`'s own note says "two
  sources for one fact is one source plus a drift". talk_to_ido declares
  both: `enter_command` on 11 contexts, `descends_to` on 18 commands;
- Phase 10 measured shortlist recall only on talk_to_ido, the best-annotated
  workflow.

**The decisions.**

- **One declaration, on the command** (3.15). `descends_to` (with
  `descend_parameter`) sits beside the assignment that moves the context, and
  the parameters shown to the agent come from the command's `Input`.
  `enter_command(s)` shipped, so it fails visibly (2.23).
- **A missing declaration is reported when it matters.** A command that moves
  the workflow into a context it does not declare logs a warning, once per
  command per process. The check is reliable, not a heuristic: the
  framework already compares the context before and after every command,
  for the `now_in` note.
- **A small workflow keeps the full listing** (2.21, condition 4; 3.10). The
  shortlist exists for prompt size. Below `FULL_LISTING_MAX_CHARS` the
  planner keeps today's full listing, and a workflow that declares few hints
  loses nothing.
- **The shortlist is measured where hints are few.** Phase 10 adds a
  workflow with no producer `from_` and no `descends_to`, and sets
  `FULL_LISTING_MAX_CHARS` from the size above which plans did not suffer.

*Amended by 2.40:* a shortlist by context, whose recall does not depend on
producer edges within a context, is measured beside the command shortlist.

### 2.31 Two costs the measurements must weigh

**The matcher's provider key.** Without `JEV_API_KEY`, `_skill_matcher`
returns `None`, and no request is ever matched to a planning command, with no
message saying why. The key, for TypeSafe's decision service, which receives
the request and the planning commands' descriptions, appears in
`CHANGELOG.md`, `workflow_agent.py`, one test and this document. It appears
in none of the tutorial, the coding skills, the example env templates,
`README.md` and `AGENTS.md`.

- Until Phase 10 settles the matcher, a workflow that has planning commands
  and no key says so once at load, as the other Jev features already do
  (fix-jdcm in `CHANGELOG.md`), and the example env templates list the key,
  commented out, with its data-egress note (Phase 1).
- Phase 10, step 1 counts "needs no extra provider key" in favour of the
  classifier heads when the arms tie.

*Amended by 2.38:* without the key, the built-in planner chooses planning
commands, so the message at load becomes an INFO line from Phase 6, and the
tie-break favours any arm that needs no extra key, "the planner chooses"
included.

**The cost of editing a seed.** Under the sparse "not here" class, changing
any seed the class uses marks every head for retraining (2.15). With
`NOT_HERE_SEEDS` at 8 and the authoring rule's eight or so seeds per
command, every seed is used, so selective training stops helping on the edit
developers make most often. Phase 9 recorded training time but set no bar on
it. The bar now includes the cost of a one-seed edit on a
talk_to_ido-sized workflow, and the choice between the one-seed and
eight-seed arms weighs it (Phase 9, step 1).

*Amended by 2.50:* each command's "not here" sample is chosen once, when the
command first enters a head, and recorded with the artifact, so editing a
command's seeds retrains only its own head.

### 2.32 Testing the design against its goal, a second time

Sections 2.32–2.41 record a second test of the design against the goal in
1.3, on 2026-10-26, after the fourth amendment. It counted what a developer
meets in the tutorial (`docs/tutorials/skills/`) and its sample workflow
(`fastworkflow/examples/library`), both written for this design, and checked
what it found against fastworkflow `179fb80` and talk_to_ido `3abe137`. The
amendment it led to is proposed and not yet approved.

**What holds.** Everything around a command is unified: where it lives, its
`Signature`, how its arguments arrive (2.25), what it returns (3.14), how a
request finds it (3.9) and where it declares navigation (3.15). Nothing
below changes those.

**Where the learning curve is.** In the body of a planning command:

- 9 of the tutorial's 15 pages teach idioms only planning commands have
  (pages 3, 4, 6, 7, 8, 10, 11, 12 and 13), and 4 teach shared ones (2, 5,
  9 and 14).
- The troubleshooting page (page 15) lists about 38 errors and warnings.
  5 are for migrating from earlier releases. Of the other 33, 23 are for
  planning commands only, 8 of them about `__output__`.
- Both of the fourth amendment's changes to the body added a way rather
  than replacing one: 2.28 ("The cost is a second way to declare a phase's
  facts") and 3.13 (the step helpers, "and the same text written by hand
  keeps working").

So the "about 95% shared" of 1.4 describes the parts of a command the two
kinds share, not what a developer learns.

**What the inventory missed.** 1.3's inventory lists the names, keys,
phrases and files a developer writes. The body also has behaviour chosen by
the shape or the wording of what a developer writes, and never declared:

- who writes the answer, read from the last phase's text: its agent, one
  model call with no tools, or code when every line is `say that ...` or a
  guard (`skill_phases.is_answer_only`, `answer_step_kind`);
- a "flat" call, read from the shape of its phases (`skill._runs_flat`,
  and `state["flat"]` in `workflow_execution_context.py`), which runs with
  the agent's 25 steps instead of the phase cap of 15;
- a "template-only" planning command, one with no `Input` and one phase
  that reads nothing, which the planner re-plans from its template
  (`_call_agent_for_query`, `plan_template`) instead of the phase runner
  running its steps;
- how the step parser reads a value (`_extract_parameters_from_key_values`):
  it drops a trailing parenthetical from the last value as a note, and
  declines a value holding `word=`, a bracket or `...`, quoted or not, so an
  f-string step can lose part of a value with no error;
- the placeholder run that builds the template: every phase method also
  runs at load with every fact a `Placeholder`, and a method that fails
  there, by arithmetic on a fact for one, fails the load.

Each is a mode inferred from what a developer wrote, which 1.4 rules out,
or a rule a developer learns when it bites.

**The decisions.** 2.33 to 2.40 make one change each, and 2.41 changes how
the goal is counted:

- a phase's facts are typed by the commands that produce them, and `from_`
  keeps one meaning (2.33);
- `__answer__` writes an answer in code, and nothing infers who writes it
  (2.34);
- `run` writes the step code runs, and each thing code does has one helper
  (2.35);
- four rules for hooks and phases go, two of them hidden modes (2.36);
- the template is a preview, not a gate (2.37);
- the planner chooses planning commands when no provider key is set
  (2.38);
- a developer can run a command's code with no model, and sees load
  problems where they work (2.39);
- a shortlist by context is measured beside the command shortlist (2.40).

None of them changes the frame stack (3.5), scoped lookup (3.9), the one
argument path (2.25) or what clients receive (3.14).

### 2.33 A phase's facts are typed by the commands that produce them

**Three ways to declare facts, and two meanings of `from_`.** After the
fourth amendment a phase's facts could be:

- a command's `Output`, named as the phase's return annotation (2.28);
- a facts model whose every field copies `<command>.<field>` by `from_`;
- either of these, chosen per input by `@phase(output=lambda input: ...)`.

Copy edges had rules of their own: a type check against the source field; a
fallback to the run's `Input` when the `Output` has no field of that name; a
plain name resolved against the context the phase ends on, with
`AmbiguousFactSourceError` when that fails; and load checks over every model
the placeholder grid produces (3.3 as the fourth amendment wrote it). They
also kept `from_` at two behaviours, a hint to the planner and a copy made
by code, with two resolution rules: the "one spelling over several
behaviours" that 2.24 set out to remove.

**What facts models do in talk_to_ido.** Its `_skills/_phase_facts.py`
(377 lines) shows that a facts model is more than its copies. Its models:

- give seven find commands one shape (`Match`: `uids`, `labels`, `total`),
  with a method every skill uses (`Match.only_uid`);
- combine the commands a record phase reads (`ReachFacts` reads
  `list_accounts`, `list_entitlements` and `list_groups`), and inherit to
  add fields (`PersonFacts(ReachFacts)`; `class RightRisk(RightFacts,
  RiskFacts)` in its module docstring);
- derive and bound what later phases read, in validators
  (`RiskFacts._count_and_sample` keeps 5 of as many as 857 findings);
- constrain the facts, so that the phase fails when the constraint does
  (`min_length=1` on a match's `uids`);
- copy what a command was called with (its R4: `AffectedFacts.finding_uid`
  and `entity_type` are the arguments the phase passed);
- are built per kind (`FOUND_MODELS` and `opened_model`, with
  `create_model`).

So a facts model is a useful container. What a developer should not have to
learn is the copying inside it: a string per field, with its grammar, its
resolution and its type rule.

**The decision.** A phase's facts are typed by the commands that produce
them, with Python references only:

- a phase's annotation, or its `@phase(output=...)`, is a command's
  `Signature.Output`, a union of commands' `Output`s (whichever of them the
  phase ran), or a facts model;
- a facts model is a pydantic model whose every field is typed with a
  command's `Signature.Output` or `Signature.Input`, a union of them, or one
  of those `| None = None` (the phase may end without that run). A field
  typed with an `Output` gets that command's `Output` from its run in the
  phase, and a field typed with an `Input` the arguments the run was called
  with;
- anything else a later phase reads is Python: a property or method of the
  model, a validator, which fails the phase as `min_length` does, or the
  code of the phase that reads it.

`from_` keeps one meaning, the producer hint on a command's `Input` field
(3.3), with one resolution rule. Copy edges go, with their strings, their
resolution, the `Input` fallback and their type check. A field's type names
its command by identity, which an import makes exact and safe to rename:
2.28's argument, applied to every fact.

talk_to_ido's `ReachFacts`, ten copy fields, becomes three typed ones:

```python
class ReachFacts(BaseModel):
    accounts: ListAccounts.Output
    entitlements: ListEntitlements.Output
    groups: ListGroups.Output
```

Its copy of an argument, `finding_uid: str = _from("open_finding.finding_uid")`,
becomes `opened: OpenFinding.Input`. Its 46 copy edges whose plain name
several contexts define (`list_accounts` of an Identity, an Application and
a Repository) sit in models that are each filled on one kind of record, as
the "Context:" line of each docstring says; each becomes a field typed with
that context's command, imported from its folder, so the import says what
the context rule left implicit. A model filled on several kinds would take
a union. The sample's two facts models, in `find_record`, each rename the
fields of one search; a union annotation and a line of Python replace them
(3.2).

**What goes.** For a developer: per-field copy strings and their grammar;
the rule that a plain name depends on where the phase ends; the `Input`
fallback; the copy-edge type check, and the copy halves of two errors (a
type that does not match, a field the target does not have); and `from_`'s
second meaning. Page 10 becomes a page about a model with one field per
command.

**What it costs.**

- talk_to_ido rewrites its 145 facts models (920 copy edges). Each group of
  copy fields that reads one command becomes one typed field, and the code
  that reads it follows (`reach.accounts.account_uids` for
  `reach.account_uids`, or a property keeps the old name). Its `Match`
  models keep `uids`, `labels` and `total` as properties over the find's
  `Output`, so `only_uid` and its callers are unchanged; its `min_length`
  constraints become validators; its `_from` helper goes.
- A typed field holds a whole `Output`, not chosen fields, so a later phase
  reads one level deeper.
- `fill_output` fills a field from its command's run by today's attribution
  rules (`runs_on_plan` and the others), with the command known by its
  class instead of by a string.
- Nothing a copy could reach is lost: a copy read a field of one run's
  `Output` or `Input`, and a facts model can hold both, as two fields.

**Alternatives.** A tuple of `Output`s
(`-> tuple[ShowBook.Output, ListLoans.Output]`) was this review's first
proposal. It needs no class, but holds no validator, method or copy of an
argument, so talk_to_ido's shared shapes, bounds and R4 copies would move
into every phase that reads them. Keeping copy `from_` beside typed fields
keeps two ways and two meanings. Inferring a phase's facts from the commands
its steps run stays rejected (2.11).

### 2.34 Who writes the answer: `__answer__`

**Three modes, read from wording.** The last phase's steps decide who writes
the answer (`skill_phases`, rule 6):

- a phase with a command step is an executor run, and its agent writes the
  answer;
- a phase with no command step is one model call with no tools
  (`write_answer`);
- a phase whose every step is `say that ...` or a guard such as
  `apply no change` is written by code (`answer_by_code`).

A developer learns `say` (3.13), that a guard in such a phase "adds nothing
to the answer" (page 7), and that the answer phase must never be skippable,
because "when the last phase is skipped, the answer is the last phase's
that ran" (page 4). Answers written by code are common: talk_to_ido writes
51 `say that` lines across 14 of its 20 skills, and 7 of the sample's 9
planning commands use `say`. Reading who writes the answer from the wording
of a step is the hidden behaviour 2.2 rejects for method names.

**The decision.** A planning command that writes its answer in code defines
`__answer__(self, input, <phase>, ...)`, which returns the text:

- its parameters bind as `__output__`'s do (3.4): `input` and the phases by
  name, a skipped phase as `None`;
- it runs once, after the last phase, as plain code;
- its text is the call's answer, as an execution command's response is the
  `str` its `__call__` returns (3.14).

Without `__answer__`, the last phase's agent writes the answer, as today.
Whether the runtime runs a last phase that names no command as one model
call with no tools is its own business: either way the developer sees an
answer a model wrote from that phase's steps.

**What goes.** `say` and `no_change`, which 3.13 proposed and Phase 13 has
not built; the answer written by code from `say that` lines; the rule that
the answer phase must not be skippable, since `__answer__` runs after
whatever phases ran; and the guards an answer phase wrote only for code to
pass over.

**Why a dunder, and why not `__output__`.** 2.2's rule makes a dunder a
framework hook. `__output__` builds the data a caller reads, and
`__answer__` the text a person reads; they stay apart, as 2.12 decided
("mixes user-facing text with parent-facing data"). One hook returning
both, as `__call__` may return a `CommandResponse`, would put the commonest
planning command, one that has both, in the long form.

**What it costs.** talk_to_ido's answer phases convert mechanically: the
method becomes `__answer__`, its `say that` texts become the returned text,
and its guards go. A last phase made only of `say that` lines and guards is
a load error naming `__answer__` (3.16), so the old form cannot linger
beside the new.

*Amended by 2.43 and 2.45:* the reason above for keeping `__answer__` and
`__output__` apart does not hold in either workflow, and the two become one
hook, `__result__`, which returns what `__call__` returns; the load error
names `__result__` (2.45). On the fast path the answer it writes reaches the
user as written (2.43).

### 2.35 Steps: `run`, and one helper for each thing code does

**The commonest step has no helper.** The step helpers of 3.13 make a
misspelt phrase fail where the developer sees it. The step code runs most,
`command key=value`, is written as an f-string, and the parser code reads
it with (`_extract_parameters_from_key_values`):

- drops a trailing parenthetical from the last value, as a note:
  `add_note text=prefers email (not phone)` binds `text='prefers email'`
  (run on 2026-10-26);
- declines a value that holds another `word=`, a bracket or `...`, quoted
  or not, so code hands the step to the agent;
- declines a value equal to one of the field's `examples`, which 3.13
  already fixes for steps a `PlanGenerator` wrote.

So the sample's `note_member` (`f"add_note text={input.text}"`) loses the
end of a note that ends in brackets, with no error, and talk_to_ido writes
48 f-string steps that interpolate a value. `pick` already quotes what it
writes (`quote_step_value`).

**Two spellings.** 3.13 also kept each phrase working when typed by hand,
so each behaviour has two spellings, and a near miss (`(all of them)` for
`(full list)`) still does something else, silently.

**The decision.**

- `run(command, **values)` writes the step code runs. It quotes every value
  that holds anything the parser reads (a bracket, `=`, `;`, `, `, a quote
  or `...`), raises for a keyword that is not a field of the command's
  `Input`, and leaves out a value of `None`. For a step a `PlanGenerator`
  wrote (the flag 3.13 gives the examples guard), the parser takes a
  quoted value whole, so nothing in it is lost or declined. Text for the
  agent goes in a note, `run(...).note("...")`, so a note is never part of
  a value.
- The step helpers are `run`, `full_list`, `pick`, `when` and `do_not_run`;
  `say` and `no_change` go with 2.34. Each returns a `str`, as 2.26
  decided, so 2.11's objection to typed step objects does not apply, and a
  plain string keeps working.
- The rule a developer learns is one sentence: a plain string is for the
  agent, and everything code does is a helper call.
- What a helper writes, typed by hand, still loads and runs. `preview
  --check` warns on it, naming the helper: a command step that no helper
  wrote, a paging phrase in a note, a condition or a negation before a
  step's command, and pick words. The words stay the runtime's
  protocol with the planner and the agent, which write them in plans of
  their own (page 14's plan has `list_member_loans (full list)`).
- Helpers take the command's name, as the step text does. Taking the
  imported `Signature` as well (`run(FindBook, ...)`, the reference 2.28
  uses for annotations) was considered and dropped: it would be a second
  way to name a command in a step, and the load check already refuses an
  unknown name.

**What it costs.** talk_to_ido's strings keep loading, with warnings;
converting its 48 interpolating steps to `run` is its choice, and worth it
where a value comes from the user.

*Amended by 2.47:* `pick` needs no uid parameter. Code picks the row from the
listing the call read, wherever it read it, so a pick in a later phase than
its listing no longer needs a uid computed in the phase method.

### 2.36 Four rules the hooks and phases no longer need

**1. A skipped phase is `None`.** Today a parameter named after an earlier
phase that was skipped, or filled nothing, gets its default, and one without
a default fails the phase (`skill_phases.bound_arguments`); and `__output__`
must give every phase parameter a default, or the load fails (3.4). So
"`=None` on a phase that may be skipped" is a rule a developer meets on page
4 and again as a load error. Decision: such a parameter receives `None`; a
default is allowed and not needed. A parameter that names no phase at all
stays a load error, since that is a typo. A phase whose code then reads a
field of `None` fails in its own code, as it failed before for the missing
default, and `run-code` (2.39) shows where.

**2. `__output__` needs no annotation.** The framework knows which class
`__output__` returns, and already checks the value at run time (3.4).
Requiring `-> Signature.Output` asks the developer to write what the
framework knows. An annotation is allowed.

**3. A `PlanGenerator` does not subclass another command's
`PlanGenerator`.** Doing so couples a command to another command's private
phases and facts, which 2.6 keeps apart from its public `Output` precisely
so that a command can change how it works without breaking what depends on
it. It is also the only reason for two load errors and an idiom: an
inherited `__output__` with no `Output`, one that builds the base's
`Output`, and `__output__ = None`. Page 13 already recommends the
alternatives: call the command for its whole job, or keep shared phases in
a base class in a `_` module. Decision: a `PlanGenerator` that subclasses
another command's `PlanGenerator` is a load error naming both alternatives;
any other base class is allowed, and hooks are read as Python resolves them,
as 2.11 requires. talk_to_ido has no skill that inherits another (2.12);
`tests/skill_tutorial_workflow`'s `book_loans` does, and takes the sample's
form, a nested call (page 12).

**4. One way to run a planning command.** Two hidden modes go:

- *Flat.* A call whose one phase reads nothing and fills nothing runs with
  the agent's `max_iters` (25) instead of the phase cap (15), so giving that
  phase an annotation, to feed `__output__`, quietly lowers its budget.
  Decision: a phase's budget follows how many phases the call runs: the
  agent's `max_iters` when it runs one, and the phase cap when it runs
  several. The preview's `Kind:` line, flat or phased, goes.
- *Template-only.* A planning command with no `Input` and one phase that
  reads nothing is not run by the phase runner: the planner re-plans it from
  its template (3.5 as the fourth amendment wrote it) and may drop or add
  steps, while adding an `Input` field makes code run its steps. Decision:
  every planning command runs through the phase runner
  (`_start_skill_phases`), whatever its shape.

Neither talk_to_ido nor the sample has a template-only planning command, and
talk_to_ido's flat routes (`inspect_entity.portrait`,
`access_request_triage.right_only`) keep their budget.

*Amended by 2.44 and 2.45:* rule 2 holds for `__result__`, which replaces
`__output__` (2.45). Dropping or adding steps, which the template-only mode
did implicitly, comes back for every planning command as something the
planner chooses when the command matches a sub-task; it is never the
command's mode (2.44).

### 2.37 The template is a preview, not a gate

**Code that runs twice.** Every phase method also runs at load, once for
each point of the input grid, with every fact a `Placeholder`
(`skill_phases.Placeholder`). What that produces serves the preview, the
load checks on steps (unknown commands and parameters, the note check), the
callee graph (cycles, a producer hint to the command's own callee, the
shortlist) and, until 2.34, the reading of who writes the answer. A method
that fails there fails the load.

The placeholder is already lenient: an attribute, index or call gives
another placeholder, iteration gives one item, every test reads as true and
is noted, `int()` gives 999999, a `_` helper called with a placeholder reads
as its name, and `uids.index(uid)` gives the first item's place, which
talk_to_ido's fan-outs use. What is left fails the load for code that is
correct on real facts: arithmetic on a fact (`find.total - 1`), for which
page 15's fix is to move the arithmetic into a helper, and any operation a
placeholder cannot imitate, such as a lookup keyed by a fact.

**Nothing at run time reads it any more.** After 2.33 a phase's facts are
declared by types; after 2.34 nothing infers who writes the answer; after
2.25 the fast path gives the planner no matched template to adapt; and
after 2.36 no planning command is re-planned from its template. So a
template that does not render need not block a load.

**The decision.**

- Arithmetic between a placeholder and a number gives a placeholder named
  by the expression (`<find.total - 1>`).
- A phase method, or `__answer__`, that still raises on placeholders is
  shown in the preview as decided at run time, with the exception. `preview
  --check` lists it as a warning, and the load checks that read its steps,
  and the callee graph, skip it; the cycle guard (3.5) still refuses a cycle
  at run time.
- Still load errors, because each fails at run time too: a step helper
  refusing its own arguments (`StepFormError`), `None` written into a step,
  and an unknown command or parameter in a step that renders.
- `__output__` is not run at load, as today.

**What it costs.** A phase that does not render loses its static checks,
the lower bound 2.4 already accepts for open steps. A committed preview that
rendered before and now shows a phase decided at run time is stale, so
`preview --check` still catches the change in CI.

*Amended by 2.44 and 2.45:* the planner reads the template of a planning
command that matches a sub-task, to call it whole, extend it or adapt it, so
the template has one reader at run time. It still never blocks a load; a
phase decided at run time is shown to the planner as such (2.44).
`__result__` runs on placeholders where `__answer__` did, and `__output__`
no longer exists (2.45).

### 2.38 Planning commands chosen without a provider key

**The key gates the headline feature.** Without `JEV_API_KEY`,
`_skill_matcher` returns `None` and no request is ever matched to a planning
command (2.31); with it, the request and the planning commands'
descriptions are sent to TypeSafe. A developer who skips page 14 has
planning commands that never run for a request, and since the built-in
planner can compose a similar plan, the cause looks like an unreliable plan
rather than a missing key.

**The planner already has what it needs.** From Phase 5 the planner's list
holds planning commands with their `Signature`, by the rule for execution
commands (3.4, Catalogs). A plan that is the one step calling a declared
planning command runs the reviewed plan, the reason 2.21 gives for the fast
path, and that step's arguments are checked against the sub-task and the
turn's earlier outputs (3.10).

**The decision.**

- The built-in planning command's prompt says that when one planning
  command on its list covers the whole sub-task, the plan is the one step
  that calls it.
- The fast path is defined by its shape, not by who chose it: a sub-task
  whose plan is one step calling a planning command runs that call with
  `fast_path=True` (3.5, 3.6), whether Jev matched the command or the
  planner wrote the step, so its steps do not count against
  `FW_TURN_MAX_STEPS` either way.
- Jev stays an optional shortcut: a confident match skips the planner call
  (3.9).
- Without the key, nothing is reported as a fault: one INFO line at load
  says that the planner chooses planning commands, and that `JEV_API_KEY`
  lets Jev match them without a planner call.
- Phase 10, step 1 measures "the planner chooses" as a fourth arm, beside
  the heads, Jev, and the heads with Jev when unsure. By 2.31's tie-break, an
  arm that needs no extra provider key wins a tie.

**What it costs.** One planner call for each sub-task Jev does not match,
which is what such a sub-task costs today. Whether the planner picks the
declared command as reliably as Jev's 96.6% is what Phase 10 measures.

*Amended by 2.43 and 2.44:* a confident Jev match no longer skips the
planner: it chooses the planning command whose template the planner sees
first, and the planner decides whether the command covers the whole
sub-task (2.44). The fast path stays defined by its shape, and the runtime
runs it without the turn frame's executor (2.43). The INFO line at load says
that the planner chooses and adapts planning commands, and that
`JEV_API_KEY` adds Jev's choice, and the `verify` check (2.46).

*Amended by 2.52:* the agent chooses, as it writes its plan, and the INFO
line says that the agent chooses and adapts planning commands.

### 2.39 Running a command's code with no model, and load problems where developers look

**The tutorial's runs cannot be reproduced.** Every "At run time" trace in
the tutorial comes from `dry_run` in `tests/test_skill_tutorials.py`. It
runs a call with no model: each phase's steps as the runtime writes them,
the steps code runs against the workflow's own execution commands, the facts
filled from those runs, and the answer code writes, stopping at the first
step the agent would take. It is private to the tests, and the design gave
developers nothing like it: their loop for a planning command's body was the
preview, which is static, or an agent run, with keys, training and a model's
variance.

**Load problems are quiet.** A command file that does not load is skipped
and logged (3.3, Where errors are reported), so a typo makes a command
silently absent from `fastworkflow run` unless the developer remembered
`preview --check`.

**The decision.**

- `fastworkflow command run-code` runs one call of a command with no model
  and prints it as the tutorial shows it (3.18). An execution command simply
  runs.
- `fastworkflow.planning.run_code` does the same for integration tests on a
  real workflow, as the testing rules require; the tutorial's tests use it
  instead of their own copy.
- It is not called a dry run: the steps it runs are real commands, against
  a real instance of the app.
- `fastworkflow run` prints the workflow's load problems before its first
  prompt, `fastworkflow train` fails, listing them, and the FastAPI server
  logs them once at startup. Skipping a command that did not load stays the
  server's policy.

**What it costs.** One subcommand and one function, built from `dry_run`'s
parts (`plan_code_steps`, `pick_step`, `fill_output`) on a real workflow
session, which `dry_run`, passing `workflow=None` to each command, does not
have.

### 2.40 A shortlist by context, measured beside the command shortlist

**Recall rests on hints nothing checks.** Above `FULL_LISTING_MAX_CHARS`,
the planner's shortlist is the commands that match, completed by producer
`from_` edges and `descends_to` (3.10). A producer that no `from_` names
drops off it "without any error" (2.21). A missing `descends_to` is reported
when its command runs (3.15); a missing producer edge is reported nowhere.
In a large workflow, producer hints are correctness requirements that
nothing checks.

**The common miss is a neighbour.** Producers are mostly in the context of
the command that needs them: `find_book` and `open_book`, `find_member` and
`open_member` in the sample, and each of talk_to_ido's 20 hand-written
producers is runnable in the context that declares it (2.15).

**The decision.** Phase 10, step 4 compares a third arm with the full
listing and the command shortlist: in full, every context that holds a
command the command shortlist holds, and the active context; every other
context in one line, as now. That is the executor's own format, and 2.14's
"one scope at a time". Its recall does not depend on producer edges within a
context, so `from_` matters for recall only across contexts. Its prompt is
larger than the command shortlist's and smaller than the full listing; the
bar, written into the epic before any run as in Phase 9, decides.

*Amended by 2.44 and 2.50:* between shortlists that meet the bar, the one
that depends on fewer optional declarations wins, which is the shortlist by
context (2.50). Each planning command on either shortlist is listed with its
template (2.44).

### 2.41 Counting what a developer meets

**The inventory counts names, not rules.** Section 4's rule that each pull
request lists the inventory rows it adds and removes caught names, keys,
phrases and files, but none of 2.32's hidden modes, which have no name.
2.24 already noted that "each error is a rule to learn".

**The decision.** Each phase's pull request also says which entries of the
troubleshooting page (`docs/tutorials/skills/15-troubleshooting.md`) it
adds, changes and removes, counting only the entries a developer writing a
new workflow can meet, and not the ones for migrating, and says why for any
entry it adds.

**This amendment's count.** It removes six entries: a phase parameter of
`__output__` without a default; `__output__` without its annotation; the
two errors for an inherited `__output__`; arithmetic on an unknown fact; and
"no request is ever matched to a planning command", which is no longer a
fault. It cuts two to their producer halves (a type that does not match, a
field the target does not have), and widens two to cover `__answer__` (a
hook parameter that names no phase, a hook that raises at run time). It adds
four, each replacing a silent behaviour or a rule that had no entry: a
facts field typed with something other than a command's `Output` or
`Input`, a `PlanGenerator` that subclasses another command's, a hand-typed
form a helper writes, and a phase decided at run time. For migrating it adds
one: a last phase written as `say that` lines.

So the entries a new developer can meet go from about 33 to about 31. The
larger change is in rules that never had an entry, which developers no
longer learn: copy strings and how they resolve, `say` and the three ways an
answer gets written, the flat and template-only modes, how the step parser
reads a value, and that arithmetic must hide in a helper.

### 2.42 Checking the fifth amendment against the code and the workflows

Sections 2.42–2.50 record a check of the fifth amendment on 2026-10-26,
against fastworkflow's code, the tutorial's sample workflow
(`fastworkflow/examples/library`) and talk_to_ido at commit `3abe137`, whose
planning commands were read from its working tree's `_skills copy/` (its
`_skills/` held only the helpers). The amendment they make was approved on
2026-10-26, and the tutorial and its sample workflow were brought to it the
same day.

**What held.** Everything 2.32 lists as unified around a command, and the
decisions of 2.33 to 2.40 that the sections below do not name.

**What it found.**

- The fast path hands an answer code wrote to the turn frame's executor,
  which rewrites it (2.43).
- The fifth amendment removed the planner's adaptation of a matched
  planning command, which today covers requests a command handles only in
  part (2.44).
- The reason 2.34 gives for two result hooks does not hold in either
  workflow (2.45).
- A planning command's arguments are still checked in ways an execution
  command's are not, though both now take one extraction path, and apps
  hand-write the same checks for execution commands (2.46).
- Code picks a listed row only right after the listing, in the same phase,
  so the commonest job is written two ways (2.47).
- Nothing says when to write a planning command rather than an execution
  command (2.48).
- Paging is read from a field's name alone (2.49).
- Editing a seed retrains every head, and the shortlist tie-break favours
  prompt size over what a developer must declare (2.50).

**One thing that was already right.** An execution command's
`validate_extracted_parameters` receives the request: the CME passes the
text the arguments came from as `command_text` to a hook that declares it
(`utils/signatures.py`, `validate_parameters`), and
`tests/test_validation_hook_command_text.py` covers it. 23 of talk_to_ido's
54 execution commands use the hook. What only the planning path does is run
the `Input`'s pydantic validators with the request in their validation
context (`validate_call`); the CME builds an execution command's `Input`
with `model_construct`, so they mostly do not run there. 2.46 runs them in
the one validation step for both kinds.

### 2.43 A code-written answer reaches the user as written

**What the fifth amendment broke.** Today a matched phased skill runs from
`_call_agent_for_query`, which returns `_start_skill_phases(...)` as the
sub-task's result, and an answer phase of `say that` lines is written by code
with no model call (`answer_by_code`). So the text reaches the user as
written, joined with other sub-tasks' answers by `_combined_answer`. 2.25
made the matched command one step of the turn frame's executor, and 3.6
said "its answer is the step's observation, and the executor finishes the
sub-task from it". `_record_subtask_answer` keeps the executor's own
`final_answer`, so the user reads the executor's rewording of what
`__answer__` wrote, though 3.16 and the tutorial's third page say no model
reads or rewrites it. It affects talk_to_ido's 51 `say that` lines across 14
of its skills. `run-code` (2.39) runs with no model and shows the text as
written, so a developer cannot see the difference before the workflow runs
with a model. The step also costs executor model calls: it names the
command in words, which code does not run, so the agent issues it, and then
finishes.

**The decision.** When a sub-task's plan is the one step that calls a
planning command (the fast path, 2.38), the runtime runs that call itself,
as `_call_agent_for_query` runs a matched skill today, without the turn
frame's executor:

- the CME extracts and checks its arguments (3.4) and `run_planning_command`
  runs it in a frame with `fast_path=True` (3.5);
- when it succeeds, the text it returns is the sub-task's answer, as
  written: the `str` or `CommandResponse.response` its `__result__` returns
  (2.45), or what its last phase's agent wrote; and the runtime appends its
  `CommandOutput` to the turn's `command_outputs`, as the agent's command
  tool would;
- when its arguments are refused or one is missing, the turn frame's
  executor takes over with that observation as its first, and finds the
  value or asks the user, as for any command (3.6);
- a planning command whose `__result__` returns only an `Output` has
  written no text, so the executor writes the sub-task's answer from it, as
  it does after an execution command.

A planning command that is one step of a longer plan (2.44) is a step like
any other: its text is an observation, and the executor writes the
sub-task's answer from every step.

**What it costs.** Nothing new: it is today's path for a matched skill. The
rule covers a planning command alone: its text is an answer written for the
person who asked. An execution command's text stays an observation in agent
mode, since it is written for the agent that reads it; talk_to_ido's
responses carry guidance such as "Offer: propose_fix for remediation
options", which a person should not read as an answer.

*Amended by 2.52:* the runtime runs the one step right after the agent's
plan step, so the fast path still takes no model step after the plan. A call
that does not end the run gives its observation to the same agent, which
goes on from its own plan, instead of to an executor that starts afresh.

### 2.44 The planner adapts a planning command that matches

**What the fifth amendment removed.** Today a matched skill is adapted to
the request in two ways:

- a skill with parameters or phases goes through the typed planning call
  (`plan_skill_call`), which fills its arguments and may add `steps_before`
  and `steps_after`: plain command steps for the parts of the request the
  skill does not cover (`typed_signature`). `filter_extra_steps` drops an
  extra step that repeats one the skill runs, reading the skill's template,
  which the call shows as its "expands to:";
- a skill with neither gives the text planner its steps: "A job like this is
  usually done as: ... Adapt this to the request: drop steps it does not need
  and add steps it asks for" (`_template_text`).

The fifth amendment removed both. 2.25 ran a confident match as the whole
sub-task, with no `steps_before` or `steps_after` (3.5, step 4); 2.36 sent
every planning command through the phase runner; and 2.37 concluded that
nothing at run time reads the template. A request a planning command covers
only in part ("who wrote Dune, and which branch holds it") then either ran
the whole command and lost the rest, or went to the built-in planner, which
saw only the command's `Signature` and its callees.

**The decision.**

- The planner plans every sub-task in agent mode. Every planning command on
  its list comes with its template: its steps as the preview renders them,
  every value a placeholder (3.17). A planning command Jev chooses
  confidently (with `JEV_API_KEY`) is shown first, as today's template is:
  "A job like this is usually done by <command>: ...". Without the key, the
  planner finds the planning command that fits the sub-task on its list.
- The planner writes one of three plans:
  - the one step that calls the command, when it covers the whole sub-task:
    the fast path (2.43, 3.6);
  - the call as one step, with plain steps before or after it for the parts
    it does not cover. The call runs nested (3.5), with its phases, facts,
    argument checks and `__result__`; the executor runs the other steps and
    writes the sub-task's answer from all of them;
  - an adapted copy of the command's steps, when the request needs some of
    them dropped or changed. The executor runs the copy as ordinary steps,
    so the command's phases, facts and `__result__` do not run.

  The planner's prompt says to prefer the first plan, then the second.
- The template therefore has one reader at run time: the planner, which
  sees it whenever the command is on its list. Elsewhere it is the preview
  (3.7). A phase the template cannot render (2.37) is shown to the planner
  as decided at run time: the command still runs it when it is called, and
  only an adapted copy can lose it.

**What it costs.**

- One planner call for each sub-task Jev matches, which is today's cost: it
  replaces the typed planning call. The fifth amendment's confident Jev match
  saved it. Jev goes back to choosing which planning command the planner sees
  first, and Phase 10 measures whether that still earns its key, with "the
  planner chooses" as an arm (2.38).
- The planner's list grows by the templates of the planning commands on it;
  `FULL_LISTING_MAX_CHARS` counts them, so a workflow with many planning
  commands reaches the shortlist sooner (3.10).
- A call in the second plan is not the whole plan of its sub-task, so its
  steps count against `FW_TURN_MAX_STEPS` (3.5).
- A developer's template is read by a model again: the tutorial's "What the
  planner sees" sections stay, saying when the planner sees it.

**Alternatives.** A second Jev question, "does the sub-task ask for anything
the command does not do?", would keep the saving when the answer is no, for
one classifier call and a measurement. It can be added if Phase 10 shows the
planner call is worth saving. Letting the turn executor run more steps after
a whole-command call would cover parts after it, but not parts that must
come before it or an adapted copy, and it would keep the executor in the
fast path that 2.43 takes it out of.

*Amended by 2.52:* the agent writes the three plans, as the first step of its
run, and is the template's one reader at run time. The planner call that
this section counts as today's cost becomes the plan step, one for one.

### 2.45 One hook for the result: `__result__`

**Two hooks for one job.** `__answer__` (2.34) and `__output__` (2.6) bind
their parameters the same way, run after the last phase, and differ only in
returning text or data. 2.34 kept them apart because "the commonest planning
command, one that has both" would need the long form. Neither workflow bears
that out: one of the sample's ten planning commands declares an `Output`
(`book_by_title`), and none of talk_to_ido's twenty does, while 8 of the
sample's and 14 of talk_to_ido's write their answer in code. An execution
command already returns both through one entry point (3.14).

**The decision.** A `PlanGenerator` builds its result in one hook,
`__result__(self, input, <phase>, ...)`, which returns what
`ResponseGenerator.__call__` returns:

- a `str`: the call's answer, with no `Output`;
- the command's `Signature.Output`: the `Output`, with its JSON as the
  response, as for an execution command;
- a `CommandResponse`: its own text, its `Output`, or both, and `artifacts`
  if it sends any.

Its parameters bind as a phase's do, with `None` for a phase that was
skipped, filled nothing or is not in the call; it runs once after the last
phase, as plain code. With it defined, every phase is one part of the job
and no phase's agent writes an answer. Without it, the last phase's agent
writes the answer and the call has no `Output`, as today.

**What it costs.**

- A planning command that returns only an `Output` gets its words from the
  agent that reads it, the parent's or the turn executor's, as an execution
  command does, and not from its own last phase's agent. The last phase must
  be framed before the hook runs, so the hook cannot decide afterwards who
  writes the answer. Neither workflow has such a command.
- A hook that raises loses both the answer and the `Output`. One model call
  then writes the answer from the runs, as 3.16 did for a failed
  `__answer__`, and `output` is `None`.
- A hook that builds its `Output` from the phases' facts can fail while the
  template is built, where every fact is a placeholder
  (`**book.model_dump()`). The preview then shows the result as decided at
  run time (2.37); nothing at run time depends on it.

**What goes.** `__answer__` and `__output__`, neither built yet; the load
error for an `__output__` with no `Signature.Output`, since a `__result__`
that returns another class fails as an execution command's `__call__` does
(3.14); and the rule that `__output__` runs after `__answer__`. The load
error for a `Signature.Output` that nothing builds stays, naming
`__result__`.

### 2.46 Argument checks are options of any command's `Input` field

**Two ways to say "the value must come from the request".** A planning
command's arguments get checks no execution command's get (`check_arguments`,
`skill_commands.py`): a `str` must be written in the request, a `bool` must
default to false, and the keys `strip`, `subject`, `verify`, `means` and
`in_request` add more. 2.22 and 2.25 left them per kind, and 3.4 gave their
rule sentences to the extractor for a planning command only. Since 2.25 both
kinds take one extraction path, so this is a rule by kind, which 2.22's own
principle rules out. And the apps want the checks on execution commands:
talk_to_ido's `stated()` (`application/validation.py`) is the "written in
the request" check, hand-written in the `validate_extracted_parameters` of
9 of its 54 execution commands.

Applying the type-implied checks to execution commands as well would refuse
values the extractor legitimately rewrites, such as a relative date written
as a calendar date, so they become options instead.

**The decision.**

- Each check is an option of an `Input` field, on a command of either kind,
  written in `json_schema_extra` as today:
  - `in_request: True`: a `str` must be written in the request (case and
    dashes ignored, widened to a whole identifier match, after its `strip`
    words), and an `int` must be a number the request writes;
  - `subject: True` (a `str`): as `in_request`, and the value must name a
    record the request names;
  - `strip` (a `str`): words removed from either end before the check;
  - `verify: True` (a `bool`, a `Literal`, or a `subject` str): Jev's
    classifier decides the value again from the request; `means` gives a
    `Literal`'s values their meanings.
- No check is implied by a field's type, for either kind. The rule that a
  planning command's `bool` defaults to false goes with the typed planning
  call it served (2.25).
- The checks run in the one step that validates every command's arguments,
  `validate_parameters`: after the parameter screen, the type checks and
  `db_lookup`, and before `validate_extracted_parameters`, so a hook that
  corrects a value still runs after that value's check (2.25). The
  `Input`'s own validators run last, with `{"request": ..., "workflow": ...}`
  as their validation context, for both kinds.
- The request is the text the arguments were extracted from: the step, or
  the user's message in assistant mode. For a planning command the built-in
  planner writes as a step, it is the sub-task and the outputs of the turn's
  earlier steps (3.10).
- The rule sentences of 3.4 attach to the options, for both kinds: the
  extractor reads "Copy it exactly as the request writes it." after a field
  with `in_request` or `subject`, whichever kind of command declares it.
- `run_planning_command` no longer checks arguments itself (3.5): by the time
  it runs, the validation step has.
- `verify` needs `JEV_API_KEY`, as today (`check_lm=_jev_lm()`). Without the
  key it checks nothing, and the INFO line at load (2.38) names the fields
  whose `verify` is inactive.

**What it costs.**

- A planning command's `str` argument is no longer checked unless the field
  says so. talk_to_ido marks 6 fields `in_request`: 25 of its 31 `str` fields
  already carry `subject`, and the other 6 all describe themselves as "... as
  the request writes it" (`department_roster_walk`, `list_records`,
  `tag_record`). Its 18 `bool` fields lose a load rule they all meet.
- A shipped execution command is unchanged unless it adds an option;
  talk_to_ido may replace its `stated()` calls with `in_request`.
- `Input` validators now run for execution commands, which none of the
  bundled examples, test workflows or talk_to_ido's execution commands
  declares.

**What goes.** The checks implied by type, the planning-only key list
(`SKILL_FIELD_KEYS`), the load error for a `bool` defaulting to true,
`validate_call`, and the planning-only branch of the argument path in 3.4
and 3.5.

### 2.47 `pick` reads the listing wherever the call read it

**One job, two spellings.** Finding a record by name and opening it is the
commonest job in both workflows. Code picks the row (`pick_step`) only when
the listing ran in the step just before, in the same phase; in a later phase
it leaves the step to the agent. So the sample writes the job two ways:
`note_member` keeps the find and `pick(..., member_uid=None)` in one phase,
and `book_by_title` and `member_report` split it across phases and compute
the uid with a helper written for the purpose (`only_uid` in `_names.py`).
talk_to_ido does the same: 12 of its 13 `pick` calls compute the uid with
`Match.only_uid` or an equivalent (`app_uid`), whose rule is `pick_step`'s
own: the one row whose label is the name, case and spaces ignored, else the
only row. A mode chosen by where a step sits is what 1.4 rules out.

**The decision.** `pick(command, named=...)` opens the named row of a
listing this call read, wherever it read it:

- code looks among the call's runs, not its children's (3.5), for the latest
  whose arguments hold the name and whose `Output` has one uid list that fits
  the command's uid parameter: `<x>_uids` for `<x>_uid`, or the list a
  producer `from_` on that parameter names. `identity_uids` fits
  `open_identity_by_uid`'s `identity_uid`, and all seven of talk_to_ido's
  find and open pairs, and the sample's two, are named so;
- when exactly one row holds the name whole (case, spacing and quotes
  ignored), or the listing has exactly one row, code runs the command on its
  uid; otherwise the step goes to the agent, written in pick words, as
  today;
- the uid parameter is optional: `pick(command, named=..., <x>_uid=...)`
  runs the command on the uid given, for a rule of the command's own or a
  uid the phase also writes into another step.

**What it costs.**

- In talk_to_ido, 10 of the 12 calls drop their `only_uid` argument.
  `cross_system_privilege_audit` names its row "<right> group" and would
  name it by the right; `access_population` writes the uid into its next
  step as well, so it keeps the uid. `application_recertification`'s own
  rules (`group_pick`, `RightsList.pick`) write their steps by uid already
  and do not change.
- `from_` cannot be the only signal: `open_group_by_uid` and
  `open_organization_by_uid` declare no producer.
- A listing read in pages is read as its pages joined, as a phase's facts
  are (3.12).

**What goes.** The rule that code picks only right after the listing, in
the same phase; the `only_uid` helpers written to get around it; and the
load error for a `pick` without a uid parameter, which remains only for a
`pick` without `named=`.

### 2.48 When to write a planning command

**No rule says.** 1.3's third item says how to tell the two kinds apart,
not when to write which. The tutorial teaches planning commands with jobs
that need no agent: 8 of the sample's 10 have no plain-string step and write
their answer in code, and the other 2 have one plain string, which asks the
agent to word the answer. talk_to_ido's are the other kind: 16 of its 20
have steps that leave a value for the agent to find (`open_finding
finding_uid=<the first finding_uid listed>`). A job that code can decide
entirely is shorter as an execution command, runs in assistant mode and
through direct actions and MCP, which refuse planning commands (3.4), and
needs none of the planning-only idioms.

**The decision.** Write an execution command when code can decide every
step, and a planning command when the agent should run, judge or recover
part of the job. A planning command gives a job steps the agent follows and
recovers from, with code running the steps it can and an answer worded the
same way each time; an execution command gives a job that never needs the
agent. 1.3 states the rule (item 3), and the tutorial's first page and the
`author-workflow-skills` coding skill teach it (Phase 8). The tutorial keeps
the sample's planning commands, which show the idioms, and says which of
them would be shorter as execution commands.

### 2.49 Paging is read from an integer field

**A mode read from a name.** A command is paged when its `Input` has a field
named `start`, `offset` or `skip` (`facts.PAGING_PARAMETERS`), and 3.14 adds
a load error for a paged command whose `Output` declares no `total`. All 28
paged commands of today's workflows use integers, but a new app's
`start: datetime` or `skip: bool` would be read as paged, and fail with a
paging error.

**The decision.** A command is paged when its `Input` has an integer field
(`int` or `Optional[int]`) named `start`, `offset` or `skip`. The load error
of 3.14 names both fixes: declare `total`, or rename a field that is not a
page. Every reader of `PAGING_PARAMETERS` takes a command's paging parameter
from one function, so the rule is the same everywhere. An explicit marker,
a `Field` option or a type, was rejected: it is one more thing to write, and
a forgotten one fails silently, since `full_list` then reads one page.

### 2.50 Two smaller changes, and this amendment's count

**Seed edits (low priority).** Under the sparse "not here" class (2.15),
every head carries seeds of every other command, so editing any seed
retrains every head (2.31). `train/selective_training.py` reuses a head only
when its recorded training signature is identical ("safe by
construction"), so the fix cannot let a head keep stale seeds. Instead,
each command's "not here" sample is chosen once, when the command first
enters a head, and recorded with the artifact as part of that head's
signature. Editing a command's seeds then retrains only its own head;
adding or removing a command retrains every head; and
`fastworkflow train --regenerate-utterances`, the one training-policy
override, chooses the samples again.

**The shortlist's tie-break.** Above `FULL_LISTING_MAX_CHARS`, producer
`from_` edges decide what the command shortlist can reach, and a missing one
is reported nowhere (2.40). Phase 10, step 4 chose "the smaller prompt"
between shortlists that meet the bar. Between such shortlists, the one that
depends on fewer optional declarations wins, which is the shortlist by
context, as 2.31 favours an arm that needs no extra provider key.

**This amendment's count** (2.41). Among the entries a developer writing a
new workflow can meet, it removes one, an `__output__` with no
`Signature.Output`; narrows two, `pick`'s parameter error (now only a
missing `named=`) and the paging error (now only integer fields); and
changes three to name `__result__` (a hook parameter that names no phase, a
hook that raises at run time, a declared `Output` that nothing builds). It
adds one, a check option on a type it does not apply to, which Phase 11
already planned for planning commands and now covers both kinds. The larger
change is in rules that never had an entry, which developers no longer
learn: checks implied by a field's type for one kind of command, a `bool`
that must default to false, code picking a row only right after its listing,
two result hooks and their order, and paging read from a name alone.

### 2.51 Testing where plans are written

Sections 2.51–2.57 record a review of 2026-10-27, which tested the design's
separation of planning from execution against the goal in 1.3, checked
against fastworkflow `179fb80`. The amendment it led to was approved the
same day.

**Where plans are written.** In agent mode the runtime refines the request
(`_refine_user_query`) and splits it (`split_into_subtasks`). Then, for each
sub-task, `_call_agent_for_query` matches a planning command
(`planner_skill_for`), calls the planner (`build_query_with_next_steps`, one
DSPy `ChainOfThought` call on `LLM_PLANNER`), and only then runs the ReAct
agent (`fastWorkflowReAct`, on `LLM_AGENT`), with the plan pasted into its
request ("Execute these next steps: ..."). This design keeps that order.
3.10 calls the planner the built-in planning command, but it is not a
command in any other sense: no step can call it, it returns a plan rather
than a result, and it runs before the agent, outside its trajectory. 2.1
chose this on purpose: "Refining and splitting stay at the root turn; nested
frames receive already-planned step text." So every plan a model writes is
written outside the agent that runs it.

**The planner also writes where the workflow's responses go.** The runtime
calls it three more times during a run:

- after a parameter-extraction error, `_execute_workflow_query` returns the
  planner's replan ("What's done: ... What remains (execute these next
  steps): ...") in place of the command's response;
- after the user answers `ask_user`, `_post_ask_user_response` returns the
  planner's replan as the step's observation;
- before a hand-off, `_hand_off` asks it what is done
  (`run_progress_check`), and the continuation starts from its text.

So a run's observations hold the decisions of a second model, in the place
of the workflow's responses.

**What that costs.**

- **Credit.** A step's observation is read as what the workflow answered.
  Nothing that reads the trajectory, a person, a check or the
  teacher/student comparison, can tell a replan from a command's response,
  or charge a wrong step to the plan that asked for it. Distillation
  therefore keeps plans and actions apart: it captures the plans inside the
  planner's call (`_planning_steps_capture`), compares them separately from
  the actions, and extracts insights from each with a prompt and a file of
  its own (`planning_agent_insights.md`, `execution_agent_anti_patterns.md`).
  The planning prompt has to allow that "a plan that looks different but
  leads to the same correct actions may be acceptable". A comment in
  `_execute_workflow_query` shows the cost in code: the replan is handed the
  pass's planner model because "otherwise replans silently fall back to
  LLM_PLANNER instead of the teacher/student LM".
- **A check on a plan has no one to tell.** The finish check reads the plan
  against the runs at the end of a run, and sends its note back into the
  loop (`fastWorkflowReAct.finish_reviewer`). A check on the plan itself
  cannot, since the planner makes one call and is gone. On talk_to_ido,
  wrong plans, mostly plans that left out steps of the matched skill, caused
  33 of the 89 answer lines lost in one benchmark stage (2026-10-18). The
  check measured after planning could only append the missing steps, and
  its code-only form appended steps that apply only when the request asks
  for them.
- **Mechanisms that exist because the plan is written elsewhere.** The three
  calls above; `_initial_plan_text`, kept for the finish check; the fast path
  as a runtime path of its own (2.43); and much of the shortlist's recall
  machinery. 2.19 shows the planner the whole workflow because "it plans
  across contexts in a single call that cannot ask for more", and 2.21
  accepts that a missing producer or navigation command "breaks the plan
  without any error". An agent can ask for more.

Agents in the literature that plan and execute in one recursive loop
support the change. In THREAD (arXiv 2405.17402) one model plans and
executes by spawning child threads, and gains 10 to 50 points over existing
frameworks with Llama-3-8B and CodeLlama-7B. ADaPT (arXiv 2311.05772)
decomposes a task only when its executor fails, and beats ReAct and
plan-and-execute baselines by up to about 30 points; it keeps a separate
planner prompt, so it is evidence for recursion more than for one prompt
doing both jobs.

**The decisions.** 2.52 to 2.56 make one change each, and 2.57 counts them:

- the agent writes each sub-task's plan, as the first step of its run
  (2.52);
- code checks the plan, and the agent reads the notes (2.53);
- distillation reads one trajectory (2.54);
- a hand-off needs no planner, and a step the agent cannot finish may get a
  run of its own (2.55);
- the split stays as it is until folding it into the agent proves its worth
  (2.56).

None of them changes how a planning command's phases run (3.5), scoped
lookup (3.9), the one argument path (2.25) or what clients receive (3.14).
2.55 adds a kind of frame.

### 2.52 The agent writes the plan

**The decision.**

- **A sub-task's run starts with its plan.** The agent has a tool,
  `plan(steps)`, whose argument is the plan: a list of step strings, each a
  command line or a sentence, as the planner writes them today. Until the
  run has called it, the agent's only other tool is `ask_user`; the rest are
  disabled (`fastWorkflowReAct.disabled_tools`), so the model is not shown
  them. A run with nothing to run writes an empty plan and finishes.
- **The plan step is a step like any other.** It is recorded as
  `thought_<n>`, `tool_name_<n>` (`plan`), `tool_args_<n>` (the steps) and
  `observation_<n>`, which is the plan as numbered lines followed by the
  notes of the plan checks (2.53). It is traced as the step's own
  `fw.agent.step`; `fw.planner.plan` and `fw.planner.replan` are no longer
  written. One difference: when a long trajectory is cut to fit the context
  window, the run's latest plan step is never among the steps dropped from
  the model's view, as the plan in today's request never is (3.6).
- **The run is shown what the planner was shown**, so the plan is written
  from the same information:
  - its `available_commands` is the planner's listing (3.10): the full
    listing while it fits within `FULL_LISTING_MAX_CHARS`, and above it the
    shortlist gathered for the sub-task, each planning command on it with
    its template;
  - its request carries what the planner's call carried: the sub-task; the
    template of a planning command Jev matched confidently, shown first
    (`_template_text`: "A job like this is usually done by <command>:
    ..."); and the summaries of the conversation's earlier turns
    (`_previous_turn_summaries_for_planner`);
  - the planner's instructions, the docstring in
    `build_query_with_next_steps` with 3.10's rule for a planning command
    that matches, become the `plan` tool's description. The planner's
    instructions in the prompt-optimization program (`fix-ygkt`) are then
    this text.
- **The agent revises its own plan.** It may call `plan` again at any step.
  The latest plan is the run's plan: the finish check reads it, in place of
  `_initial_plan_text`, and so do the plan checks. Nothing else plans during
  a run:
  - after a parameter-extraction error, the observation is the CME's message
    and the abort confirmation;
  - after the user answers `ask_user`, the observation is the answer, after
    `_apply_reply_intent` as today.
- **The three plans of 2.44 stay, written by the agent.** For a planning
  command that matches the sub-task, the `plan` tool's description gives them
  in this order of preference: the one step that calls it, when it covers
  the whole sub-task; the call as one step, with plain steps before or after
  it, never repeating a command its template runs; an adapted copy of its
  steps, when the request needs some of them dropped or changed. A call that
  is one step of a longer plan runs nested (3.5) and counts against
  `FW_TURN_MAX_STEPS`, as before.
- **The fast path keeps its shape and its guarantee** (2.43). When the plan
  is the one step that calls a planning command, the runtime runs that step
  right after the plan step, as the sixth amendment ran the planner's
  one-step plan: the CME extracts and checks its arguments against the
  sub-task and the turn's earlier outputs, `run_planning_command` runs it
  with `fast_path=True`, and text the command wrote ends the run as the
  sub-task's answer, as written. Otherwise (an `Output` only, a refused or
  missing argument, an exhausted or failed call) the call's observation is
  the run's next observation, and the agent goes on from its own plan.
- **The argument checks** of a planning command the agent names in a step
  take as the request the sub-task text and the outputs of the turn's
  earlier steps, as 2.21 decided for the planner's steps: the step is the
  agent's own words.

**What goes.** The planner's call for each sub-task in
`_call_agent_for_query`, its two replans, its progress call (2.55) and
distillation's call of it (2.54): `build_query_with_next_steps` with its
three signatures, `run_progress_check`, `fastWorkflowReAct.planner_view`,
`_initial_plan_text` and the two planner spans. The built-in planning
command stops being a component: its listing, its shortlist and the
templates on it stay, as what a sub-task's run is shown (3.10).
`LLM_PLANNER` stays, for the split (2.56) and the conversation summary.

**What it costs.**

- **The listing is in every step's prompt, not in one call's.**
  `CommandsSystemPreludeAdapter` puts `available_commands` in the system
  message, which every step sends again. A listing of about 17,500
  characters, talk_to_ido's today, is then sent with every step of a run
  instead of once per sub-task. The system message changes only when the
  context does, so a provider's prompt cache can absorb much of the cost, but
  the design does not assume one. Phase 6 measures prompt tokens and latency
  per sub-task, and Phase 10 weighs them when it sets
  `FULL_LISTING_MAX_CHARS`.
- **The agent picks each step from a longer list.** The executor was shown
  the current context's commands in full and one line for each other context
  (`_what_can_i_do`). A sub-task's run is now shown the planner's list:
  below `FULL_LISTING_MAX_CHARS` a small workflow's whole listing, and above
  it a shortlist built for the sub-task, which in the shortlist by context
  (2.40) holds the executor's list. Phase 6 counts wrong commands per step.
- **One model plans and executes.** A deployment that paired a strong
  `LLM_PLANNER` with a small `LLM_AGENT` now plans with the small one. Small
  models in a ReAct loop tend to plan one step ahead and finish early; the
  dedicated planner exists partly to prevent that, and the finish check
  exists because they do it even with a plan. Phase 6 measures the coverage
  of the steps each request needs against the planner's, and its fallback
  keeps the plan in the trajectory if the agent's own plans lose.
- **Model calls do not change.** The plan step replaces the planner's call
  one for one, and the fast path still takes no model step after the plan. A
  run that would have replanned or handed off saves those calls.

**Alternatives.**

- **The planner as a tool the agent calls**: a `plan()` with no steps, whose
  observation is the planner's plan. The plan is in the trajectory, and the
  agent chooses when to replan, but the reasoning behind the plan is in a
  sub-call, and two models still plan and execute. It is Phase 6's fallback
  if the agent's own plans lose to the planner's.
- **Plan in the agent's thought, with no plan step.** There is then nothing
  to check, grade or compare. The plan is an argument so that the checks can
  parse it, and so that offline grading can compare it exactly: the
  prompt-optimization program grades plans against references known by
  construction (`fix-ygkt`), and grading a plan step costs one model call, as
  grading the planner's call did.
- **A structured plan**, with flags for optional and user-gated steps and the
  request's subjects. It was tried as the structured planner and disabled on
  2026-09-28, because it was slow (a median of 12.1 s against 3.7 s); a list
  of strings is what the text planner writes.
- **The listing until the plan is written, and the executor's list after
  it.** Cheaper per step, but a later plan would be written from less than
  the first, and a list that changes after one step is a rule of its own. It
  is the fallback if Phase 6 finds the listing's cost at every step too high.
- **Let the agent decide whether to plan.** It would save a call for a
  request of one command. But today every sub-task is planned, and Phase 6
  compares like with like; this can be measured once the plan step is in
  place.

### 2.53 Code checks the plan, and the agent reads the notes

**The decision.** The `plan` tool checks, in code, the plan it records, and
returns the notes in its observation. A check never refuses a plan: the plan
is recorded either way, and the agent revises it with another `plan`, or
goes on. The checks read the plan with the finish check's parser
(`finish_check.parse_plan`), so a step means the same to them as to the
finish check, and each reads only what the workflow already declares:

1. **A producer that no earlier step runs.** A command step whose command
   has a required `Input` field with a producer `from_` (3.3), whose value
   the step does not write, when no earlier step runs one of its producers:
   "Step 1 runs open_member, whose member_uid comes from find_member; no
   earlier step runs find_member."
2. **A context the plan does not reach.** Code follows the plan from the
   active context: a step whose command declares `descends_to` (3.15) moves
   the plan into that context, and `go_up` and `reset_context` move it as
   they move the workflow. A command step whose command is not on the lookup
   path (3.9) where the plan stands gets a note naming the command that
   enters its context, from the descend edges: "Step 2 runs
   list_member_loans while the plan is in Library; enter a member first
   (open_member)."
3. **A matched planning command's steps left out.** When Jev matched a
   planning command confidently, and the plan neither calls it nor runs
   every command step of its template, a note names the command and the
   steps the plan lacks: "This request matches member_report. The plan
   neither calls it nor runs its steps list_member_loans and show_notes: call
   member_report, or add the steps the request needs."

The notes together are at most the finish check's bound
(`finish_check.NOTE_MAX_BYTES`, 1,024 bytes). A check that raises adds no
note and logs a warning: a plan is never stopped by a check's error, as a
finish is never stopped by the finish check's (`review_finish`).

**Why these, and why notes.**

- They keep to the rule that a model proposes and code checks what code can
  decide. Each check reads a declaration the developer already wrote, so
  `from_` and `descends_to` are checked against every plan, not only shown in
  a prompt.
- A note leaves to the agent the judgement code cannot make. The third check
  names steps; the agent decides which of them the request needs
  (`show_notes` runs only when the request asks for notes). The check
  measured after planning could not do that: it appended the steps, and its
  code-only form appended steps that apply only when the request asks for
  them (2.51). The model-judged form measured then (Jev, with a threshold of
  0.9 for each missing step) can be added beside these as one more note,
  under the same rule; it is not part of this amendment.
- The finish check already works this way, at the end of a run. These are
  the same kind of check, at its start.

**What it costs.** Three functions over the parse, which read edges the
shortlist already collects (3.10). A wrong note costs a step, since the
agent may follow it. Phase 6 measures the checks as an arm of their own, so
that their effect is not mistaken for the plan step's.

### 2.54 Distillation reads one trajectory

**Today.** A distillation pass (`DistillationSession._run_agent_pass_body`)
runs a plan-then-execute sequence of its own: it calls the planner on the
pass's planner model (`LLM_TEACHER_PLANNER` or `LLM_STUDENT_PLANNER`),
captures each plan the planner writes, replans included
(`_planning_steps_capture`, appended inside `build_query_with_next_steps`),
and runs the agent on the plan. It matches no planning command and runs no
phases, so a pass is not what a turn runs. Plans and actions are then
compared separately (`compare_planning_traces`, `compare_trajectories`), and
each kind of insight has its extraction prompt and its file. Nothing in
fastworkflow reads those files at run time yet (`load_workflow_insights` is
called only to avoid duplicate insights): they are the material from which
planning commands and checks are to be extracted (`fix-sb8`).

**The decision.**

- A pass runs the request as one sub-task, through `_call_agent_for_query`,
  as a turn runs a sub-task. The planning-command match, the plan step, its
  checks, the fast path and the finish check then run in a pass as in a
  turn.
- A pass's plans are its `plan` steps. The `plan` tool appends each to
  `_planning_steps_capture`, with the step's thought as its reasoning, and
  `compare_planning_traces` reads them as before.
- A pass's plans are written by its agent model (`LLM_TEACHER_AGENT`,
  `LLM_STUDENT_AGENT`). `LLM_TEACHER_PLANNER`, `LLM_STUDENT_PLANNER` and
  their keys are no longer read, and a workflow that sets them logs once
  that they are ignored (2.23). `_current_planner_lm`, which carried the
  pass's planner model into replans, goes with the replans.
- The two comparisons and the two files stay. A plan and the steps that
  followed it are now in one trajectory, so a planning insight can cite the
  plan step and what it led to; the planning prompt keeps its rules about
  context that differs between the passes.
- The checks distillation is meant to yield run where the checks of 2.53
  run: on the plan step, with their notes in the trajectory. Replaying the
  student against a stored teacher trace to test a candidate insight
  (`fix-sb8.11`, "exactly the shape a planner verifier needs") can start
  from a plan step, as from any step.

**What it costs.** A pass now matches planning commands, and can take the
fast path or call one nested, which a pass never does today, so its
comparisons cover those runs too. Two settings and their keys go, with a
warning for a workflow that still sets them.

### 2.55 A hand-off needs no planner, and a step may get a run of its own

**The hand-off continues from what code knows.** A sub-task's run that
reaches its step cap is continued by a fresh run, as today (`_hand_off`, in
the turn frame only, at most `MAX_HANDOFFS` times). The text the
continuation starts from is written by code, from what the capped run left:

- its answer, which its extract call already wrote and
  `_record_subtask_answer` keeps;
- its plan, each step marked run or not run by the finish check's
  attribution (`finish_check.check`, over the run's archived rows);
- the records it opened (`_opened_part`), as today.

`run_progress_check` goes, and with it the planner's call. The
continuation's first step is its plan, as every run's is, and it may keep
the steps not yet run.

**A step may get a run of its own** (Phase 18, gated).

- A sub-task's run has one more tool, `spawn(goal)`. It runs the goal in
  a fresh run of the same agent, in a frame of its own, and returns that
  run's answer as the step's observation. Its description says to spawn a run for a
  step the agent tried and could not complete, rather than retry it in a
  trajectory that already holds the failure. That is ADaPT's rule (2.51):
  decompose only when execution fails.
- The frame (3.5) has `kind="spawned"`, no command name, the goal as its
  one sub-task, and an agent from the same factory
  (`initialize_workflow_tool_agent`). Its run is a sub-task's run in every
  other way: its first step is its plan; it is shown the listing gathered
  for its goal (3.10); a planning command it names in a step is checked
  against the sub-task's text and the turn's earlier outputs, since the goal
  is the agent's own words (2.21); and its `ask_user` suspends and resumes
  through the stack, as a planning command's does (3.5).
- **Only a sub-task's run spawns.** A spawned frame, and a planning
  command's phases, have no `spawn` tool. That bounds depth with no new
  constant: a branch of the stack holds at most one spawned frame, and
  each planning command at most once (the cycle guard).
- **Its steps count against `FW_TURN_MAX_STEPS`**, as a nested planning
  command's do: they are work the spawned run adds, which is what that budget
  bounds (3.5). A spawned frame that reaches its step cap returns
  `success=False` with its answer, and is never handed off; the run that
  spawned it decides what to do next, as after any failed step.
- **Its runs count as the spawning run's.** A spawned frame does part of
  its parent's plan, so the parent's finish check and its hand-off text read
  the frame's runs as the parent's own. A planning command's frame differs:
  its facts are its own, so it contributes one held run (3.5).
- The fast path is a sub-task's run's (3.6): a spawned frame runs a plan of
  one planning command's call like any other plan.

**Why gated.** Spawning adds a tool and a kind of frame, and a small model
may spawn where it should act. Phase 18 builds it only after Phase 6 has
passed, and merges it only if it helps the sub-tasks that fail or reach
their step cap today.

**Alternatives.**

- **A frame for every step of a plan.** Every command would then cost a
  run, with its plan step and its finish, instead of one step.
- **Spawning from any frame, with a depth cap.** A constant to choose
  (2.23 dropped `FW_COMPOSITE_MAX_DEPTH`), and room for a small model to
  recurse. One level is the smallest version to measure; deeper spawning
  can follow a measurement that shows the need.
- **One budget over every frame, the sub-task runs included.** The turn
  frame alone can take thousands of model iterations today (3.5). The
  sub-task runs keep their caps, and the budget bounds what spawning adds.

### 2.56 The split stays until folding it proves its worth

**The decision.** The split stays a call of its own before any run
(`split_into_subtasks` on `LLM_PLANNER`, with `merge_subtasks`,
`resolve_referents` and a workflow's `_split.py`), and each sub-task gets a
run of its own, as today. Folding it into the agent, as the first plan of
one run for the whole request whose steps are its sub-tasks, each of them
run in a spawned frame (2.55), is not part of this project unless a measurement shows it
is worth it (Phase 19).

**Why.** The split is the one planning step whose optimization has a
measured gain. On talk_to_ido's cases that the optimization never saw, the
optimized split instructions handled 60 of 68 multi-part requests (88%),
against 52 of 68 (76%) for the built-in default instructions, with
single-job requests equal (126 and 125 of 128; `fix-ygkt`, 2026-10-16). The
sample is small, and GEPA's instructions were not measured apart from the
five rules written beside them by hand. The split is also graded exactly,
against splits known by construction. Folding it would trade a measured
component for an unmeasured one.

**The bar** is written into the epic before any run: the same cases as that
measurement, three runs per arm, and arms compared case by case with a
paired test and an interval on every rate. For example: multi-part success
no lower than the split's, with the lower end of the paired interval no
more than 2 points below it; single-job success no lower; and no more model
calls per request. If the bar is not met, nothing changes.

### 2.57 This amendment's count

**What a developer writes** does not change: the amendment adds no name,
key, option, file or setting a developer writes (the inventory of 1.3). The
inventory's rows that name the planner now name the agent: the template's
(the agent adapts a template when its command matches a sub-task) and
`JEV_API_KEY`'s (Jev chooses the planning command the agent sees first).
From Phase 18, `FW_TURN_MAX_STEPS` also counts spawned frames.

**Settings.** None is added. Distillation's `LLM_TEACHER_PLANNER` and
`LLM_STUDENT_PLANNER`, and their keys, are no longer read (2.54).
`LLM_PLANNER` stays, for the split and the conversation summary.

**The troubleshooting page** (2.41). No entry is added or removed; the
entries that name the planner name the agent's plan instead. The plan
checks' notes are read by the agent, in the trajectory, at run time; they
are not load problems.

**What the framework developer maintains.** One planner fewer: its call and
its three signatures, two replans, the progress call, `planner_view`,
`_initial_plan_text`, `_current_planner_lm` and two kinds of span. Added:
the `plan` tool and its three checks, and from Phase 18 the `spawn` tool
and the spawned frame. The built-in planning command, a mechanism of its
own in 1.3, becomes the listing a sub-task's run is shown.

**The tutorial.** Most of its pages said what "the planner" sees and does:
every page's "What the planner sees" section, page 14 in most detail, the

planner became the agent, writing its plan as the first step of its run from
the same list, and each page's section became "What the agent plans from".
Page 14's "How the planner uses a planning command" became "How the agent
plans a request", its "What the planner is shown" became "What the agent is
shown", and it gained a section on the checks of 2.53, "The checks on a
