## 4. Phased implementation plan

Updated 2026-10-26: the baseline is already measured, so work starts at
Phase 1. Implementation lives in its own worktree. Each phase is proved
on `fastworkflow/examples/library` with the targeted tests that phase
names. talk_to_ido is updated and tested only after that, in a worktree
of its own repository.

General rules for every phase:

- Activate `.venv` first.
- **Where the work lives.**
  - Implement this architecture in its own git worktree of this
    repository, on its own branch off `main`. The primary checkout stays
    on `main`.
  - Update talk_to_ido in a separate git worktree of its own repository,
    `~/rl/talk_to_ido`. The primary talk_to_ido checkout stays as it is.
  - In the talk_to_ido worktree, point the editable fastworkflow source
    at the fastworkflow worktree above. The primary checkout's
    `pyproject.toml` has
    `fastworkflow = { path = "../fastworkflow", editable = true }`
    under `[tool.uv.sources]`. A worktree that sits next to
    `~/rl/fastworkflow` still resolves that relative path to the primary
    checkout, so set `path` to the unified-command-architecture worktree
    and run `uv sync` there. The version pin
    (`fastworkflow[training,server]==…`) has to match that worktree's
    version. Use the worktree's `.venv` (`make` already calls
    `.venv/bin/python` and `.venv/bin/fastworkflow`); `uv run` re-syncs
    and can replace that install.
- **Tests:**
  - All tests are integration tests against real workflows
    (`tests/example_workflow`, `tests/hello_world_workflow`,
    `tests/todo_list_workflow`, the skill tutorial workflow
    `tests/skill_tutorial_workflow`, whose files the pages in
    `docs/tutorials/skills/` quote, and
    `fastworkflow/examples/library`, the sample those pages are written
    against). Do not use mocks.
  - Do not delete any existing test. Where existing behaviour is
    intentionally changed, update the assertion in place and say why in
    the commit message.
  - Run only the targeted tests the phase names: the new file it adds,
    and the existing files it says to update or re-run. A full suite runs
    only when the user explicitly asks for it in that turn. The full
    suite takes about 2 hours 7 minutes; if one is requested, never run
    two at once.
  - Prove the phase on `fastworkflow/examples/library` first. Check the
    library files and the tutorial pages that show what the phase
    implements, and fix any difference in the same change. The library
    example is written for this architecture (`_commands/`, `from_`,
    `__result__`) and does not load on earlier releases; exercise the
    parts the phase has made loadable. Once that is satisfactory, apply
    the phase's talk_to_ido steps in the talk_to_ido worktree and run
    that phase's targeted talk_to_ido checks there, against this
    fastworkflow worktree.
- **Baseline.** Already established and measured (see below). There is
  no Phase 0. Later phases compare against that baseline. They do not
  re-record it, and they do not run the full suite to refresh it.
- **Tracking:** create one bd epic for this project and one child issue per
  phase, starting at Phase 1. Close each child as its phase lands, close
  the epic after the last phase, and run `bd export -o .beads/issues.jsonl`
  after every bd write.
- **Branches:** every phase is its own commit series and its own PR, on
  the unified-command-architecture worktree, in this order, with these
  exceptions:
  - Phase 9 may run alongside Phases 1–8.
  - Phase 10 needs Phases 5 and 9.
  - Phase 11 needs Phase 5.
  - Phase 12 needs Phase 3, and its turn-frame entry (3.14) needs Phase 6.
  - Phase 13 may run alongside Phases 1–8; its helpers
    move to `fastworkflow.planning` with Phase 8's rename sweep.
  - Phase 14 needs Phases 3 and 13.
  - Phase 15 needs Phase 3, and talk_to_ido's facts models rewritten as
    typed fields (its external step, in the talk_to_ido worktree).
  - Phase 16 needs Phases 14 and 15.
  - Phase 17 needs Phase 3; its lines for nested calls need Phase 5.
  - Phase 18 needs Phases 5 and 6, and merges only if its measurement keeps
    spawning (2.55).
  - Phase 19 needs Phase 18, or runs its folded arm without spawning if
    Phase 18 did not merge, and changes nothing unless its bar is met
    (2.56).

  The rename sweep of Phase 8 runs when no other phase's branch is open,
  because it touches every file that names a skill. Each phase must leave
  the worktree's branch working, and must merge in an order that leaves
  `main` working.
- **What a developer learns.** Each phase's PR lists the rows of the
  inventory in 1.3 it adds, changes and removes, and updates the inventory. It
  also lists the entries of the troubleshooting page
  (`docs/tutorials/skills/15-troubleshooting.md`) it adds, changes and
  removes, counting only those a developer writing a new workflow can meet
  (2.41). A phase that adds a developer-facing name, key, phrase, file, rule
  or troubleshooting entry without removing one says why in its PR.
- **The tutorial and its sample.** They are written for the final state,
  seventh amendment included (2.57). Each phase checks the pages and the files of
  `fastworkflow/examples/library` that show what it implements, and fixes
  any difference in the same PR.
- **Coding skills:** load the `fastworkflow-architecture-contract` and
  `fastworkflow-change-control` skills before Phases 4–6, 9, 10, 12 and 18.
  Phases 6, 9 and 10 also need `fastworkflow-nlu-pipeline-reference` and
  `fastworkflow-intent-training-convergence`.

### Phase 1: contexts for planning commands in `_skills/`

1. In `_skill_files` (`workflow_agent.py:1119`), load
   `_skills/<Context>/<name>.py` files. The qualified name is
   `<Context>/<name>`. Keep skipping `_`- and `.`-prefixed entries, and
   remove the "not loaded yet" warning. Root files keep their bare names.
2. **Visibility and order.** `load_skills` / `_skill_matcher` /
   `load_skill_commands` take the active context name. Planning commands are
   matched scope by scope along the lookup path of 3.9:
   - `match_skill` runs once for each scope on the path that offers
     planning commands: the active context, its bases, each live ancestor's
     context and its bases, then the root planning commands;
   - each call offers that scope's planning commands and "none", and the first
     confident match wins;
   - with only root planning commands this is one call, as today.

   The path's enclosing part comes from `get_parent()` on the live chain,
   so this step does not depend on Phase 9's classifier work.
   - The caches (`_build_parsed_skills`, `_skill_matcher`) keep their
     per-workflow key and load every skill once per process; visibility
     filters that full load by the active context. Do not key the caches
     on the context name.
   - The callers pass the active context: `planner_skill_for` /
     `match_skill` are called from `_call_agent_for_query`, which reads it
     from the active workflow's `current_command_context_name`.
3. **Unknown contexts.** `_skills/<Context>/` where `<Context>` is not a
   context of the workflow (no `_commands/<Context>/` folder and not in
   `context_inheritance_model.json`) is a load error for each of its
   files.
4. **Collisions.** A skill with the same qualified name as a command (a
   root skill and a root command, or a context skill and a command in that
   context) is a load error for the skill, reported by `preview --check`.
5. **Preview output.** Write context skills to `<out>/<Context>/<name>.md`
   (3.7), and regenerate `docs/tutorials/skills/previews/` if any preview
   text changed.
6. **The provider key** (2.31, 3.9). A workflow that has planning commands
   and no `JEV_API_KEY` logs the warning of 3.9 once, at load; Phase 6
   turns it into the INFO line, once the agent chooses planning commands as
   it plans (2.38, 2.52). Add `JEV_API_KEY` to
   `fastworkflow/examples/fastworkflow.passwords.env`, commented out, with a
   note that it is optional and that matching sends the request and the
   planning commands' descriptions to TypeSafe.
7. **Tests.** Add `tests/test_skill_contexts.py`. Use a test workflow with
   `_skills/Library/` and a root skill and verify:
   - the context skill matches when `Library`, a context inheriting from
     it, or a record inside a `Library` is active, and not elsewhere;
   - the root skill matches everywhere;
   - when a context skill and a root skill both fit, the context skill's
     scope is asked first and wins;
   - preview lists both;
   - a skill folder for an unknown context is a load error;
   - with `JEV_API_KEY` unset, loading a workflow with planning commands
     logs the provider-key message once, and one without planning commands
     logs nothing.

**Done when:** `tests/test_skill_contexts.py` passes, the library
example's context planning commands match on the scopes this phase
defines, and the recorded baseline is unchanged. talk_to_ido is not
part of this phase.

### Phase 2: `from_`

1. Implement `from_` and its exports (3.3), for producer edges only: `from_`
   on anything but a command's `Input` field is an error. `fact_from` and
   copy edges stay as they are until Phase 15 removes them (2.33), so
   nothing in this phase changes how a facts model is filled. Add `"from"`
   and `"available_from"` to `SKILL_FIELD_KEYS`. `from_` has no `kind=`
   keyword, and there is no forwarding (2.27).
2. **Load-time resolution.** Add `resolve_field_sources(workflow)` in
   `skill_commands.py`. It runs once per workflow when commands and skills
   are loaded, checks where every `from_` is declared, runs the type
   checks, applies the producer `available_from` write, and builds the map
   from each command's `Signature.Output` and `Signature.Input` class to its
   qualified name that 3.12 reads. A field with a hand-written
   `available_from` is reported as an error naming `from_`, and its command
   is skipped. It returns its problems, which `check_previews` reports
   (3.3). `check_phase_sources` keeps its warning policy for copy edges
   (3.3).
3. **Execution commands.** Run the same resolution for `Signature.Input` fields
   of execution commands when `CommandDirectory` hydrates a command's
   `Signature` (`ensure_command_hydrated`, the lazy path). Cache the
   result per workflow. The producer `available_from` write happens on
   the hydrated `Signature` class, before `command_metadata_api.py` reads
   it.
4. **Rendering.** Update the missing-parameter message (strip the suffix
   and the prefix from every entry) and leave `command_metadata_api.py`
   emitting the list `from_` wrote (3.3).
5. **Tests.** Add `tests/test_field_sources.py`, covering:
   - each allowed edge;
   - each error row of the table in 3.3, including `from_` on a facts
     model's field;
   - a field the target has in both `Input` and `Output` resolves to the
     `Output` on a command's `Input`;
   - a `from_` on a command's `Input` field whose target has the field only
     in its `Input` is a load error that says to write a description;
   - unqualified-name resolution of producer edges, including the
     ambiguity error;
   - an existing copy edge (`fact_from`) still fills its facts model as
     before;
   - the missing-parameter message text being byte-identical for
     `fastworkflow/examples/retail_workflow` before and after the
     migration in step 6 (the message strips the `.field` suffix);
   - a hand-written `available_from` reported as an error naming `from_`,
     with its command skipped;
   - metadata output containing `.field` suffixes when `from_` is used.
6. **Migrate the bundled examples.** Every hand-written `available_from`
   in `fastworkflow/examples/` is in `retail_workflow/_commands/`: 19
   declarations in 10 files, all plain command names. Convert each to
   `from_`:
   - the two declarations whose producers declare the field they supply
     take field references: `get_user_details.py` `Input.user_id` →
     `from_(["find_user_id_by_email.user_id",
     "find_user_id_by_name_zip.user_id"], description=...)`, and
     `modify_user_address.py` `Input.user_id` → the same list;
   - the other 17 take command-only references, such as
     `from_("get_user_details")`. Their producers (`get_user_details`,
     `get_order_details`, `get_product_details` and
     `list_all_product_types`) each declare one text field in their
     `Output` (`user_details`, `order_details`, `product_details`,
     `status`), so a field-level reference to them is impossible without
     changing those Outputs, which is outside this project.

   Both producers of `user_id` declare `Output.user_id: str` but return a
   `CommandResponse` without `output`. Make each also set
   `output=Signature.Output(user_id=...)`, so the edge is readable at
   runtime and the missing-output warning (Phase 3) does not fire.
7. **External: talk_to_ido.** After this phase is satisfactory on
   `fastworkflow/examples/library`, the talk_to_ido worktree converts its
   hand-written `available_from` entries, moving their prose into the
   fields' descriptions (2.12, 2.23). That is the app's change, against
   this fastworkflow worktree.

**Done when:** `tests/test_field_sources.py` and the retail workflow's
existing tests pass, and the library example's `from_` edges resolve.
The talk_to_ido conversion, once run, matches the recorded baseline
except for the prose moved into descriptions.

### Phase 3: output contract and the registry of planning commands

1. **The skill's result** (2.45, 3.16). A matched skill call at the turn
   frame (through `_start_skill_phases`, flat or phased) builds its
   `CommandResponse` from what the skill's `__result__` returns, called once
   after its last phase with the phases' facts bound by `bound_arguments`,
   by the rules of 3.14 for what `__call__` returns: a `str`, its
   `Signature.Output`, or a `CommandResponse` (3.4). With `__result__`
   defined, every phase is framed as one part of the job (`phase_query`),
   the last included, and the cap note is appended to its text. Keep
   `__result__` out of `phase_methods` and of the helper scan in `skill.py`,
   both of which already skip dunders. Add the load errors of 3.4: a declared
   `Output` without `__result__`, a parameter that names no phase, and a
   `PlanGenerator` that subclasses another command's (2.36). No annotation
   is required. Add the run-time rule of 3.16: a `__result__` that raises or
   returns another form logs a warning, one model call writes the answer,
   and `output` is `None`.
1a. **A skipped phase is `None`** (2.36). `bound_arguments` gives a
   parameter named after a phase that was skipped, filled nothing or is not
   in the call `None`, instead of its default or a `PhaseError`, for phase
   methods and hooks alike.
2. **Static checks.** A producer `from_` field must exist in the target's
   `Output` (2.6); otherwise it is an error.
3. **Runtime warning.** When a command that declares a `Signature.Output`
   returns no `output`, log
   `"<cmd> declares an Output but returned none; phases and from_ references cannot read it"`
   once per command per process (3.14). It covers every command, not only
   those a `from_` names.
3a. **Facts typed by their commands** (3.12). A phase's return annotation
   or `@phase(output=...)` value may be a command's `Signature.Output`, a
   union of `Output`s, or a facts model whose fields are typed with
   commands' `Output`s and `Input`s (or unions of them, or `| None = None`).
   `fill_output` fills each from its command's run, a field typed with an
   `Input` from the run's arguments, and then validates the model. Add the
   load errors of 3.12 (a facts field typed with anything else, except one
   that still carries a copy until Phase 15; a phase whose steps never name
   a command its facts need), and the preview's rendering (3.7).
4. **The registry.** Add `is_planning` to `CommandDirectory` metadata.
   `_skills/` planning commands are registered through `CommandDirectory` under
   their qualified names, alongside `_commands/` planning commands. Add the
   `ast`-based `PlanGenerator` detection (3.4) to `_register_command`, and
   add the `_skills` roots to `_command_source_roots` (3.4, The cache
   fingerprint).
5. **Hidden until Phase 5.** In this phase planning commands are registered and
   routed, but nothing offers them by name:
   - they are left out of the executor's and the planner's command
     catalogs, and out of MCP `list_tools`;
   - they are reached only by `match_skill` at the turn frame, exactly as
     skills are today.
6. **Dispatch.** Add the refusals of 3.4: assistant mode and `/`-prefixed
   commands, `perform_action` and `perform_mcp_tool_call`. In agent mode,
   a step that still names a planning command (for example, a user typing its
   name) is refused in this phase with
   `"<name> is a planning command; it cannot be called as a step yet."`
   Phase 5 replaces that refusal with `run_planning_command`.
7. **Training.** Exclude planning commands at every site listed in 3.4
   (Training).
8. **Tests.** Add `tests/test_planning_commands.py`, covering:
   - a `_commands/Library/book_by_title.py` planning command is matched and run,
     and its `CommandResponse` carries the text and the `Signature.Output`
     its `__result__` built from two phases' facts;
   - the same planning command, on an input where the phase `__result__`
     reads is skipped, receives `None` for it and returns `found=False`, with
     `success=True`;
   - a `__result__` that returns a `str` gives that text and `output=None`; one
     that returns only its `Output` gives the `Output`'s JSON as the response;
     and with `__result__` defined, no phase's agent writes an answer;
   - a `__result__` that raises gives an answer one model call wrote,
     `output=None`, and one warning;
   - assistant mode, `/`-prefixed and `perform_action` calls return the
     refusal text;
   - training on the test workflow ignores the planning command (the trained
     label set and the duplicate check exclude it);
   - adding a file under `_skills/` changes
     `compute_commands_source_fingerprint`;
   - the producer-without-Output error;
   - the `__result__` load errors, and the `from_`-on-an-`Output`-field
     error for a planning command (3.3);
   - inheritance (3.4): a `PlanGenerator` that subclasses another command's
     fails with the message naming both alternatives; one that subclasses a
     base class in a `_` module loads, and a `__result__` it inherits is
     checked as if the file defined it;
   - a `__result__` with no annotation, whose phase parameters have no
     defaults, receives `None` for a skipped phase and builds its `Output`;
   - a phase annotated `-> FindBook.Output` hands on `find_book`'s `Output`
     from its run, a `full_list` step's pages joined, and a fan-out phase
     annotated with `OpenBook.Output` hands on one per item; a phase
     annotated with an `Output` whose command its steps never run is a load
     error;
   - a union annotation hands on the `Output` of whichever member ran; a
     facts model with a field typed with one command's `Output`, one typed
     with another's `Input` and one `| None = None` is filled from the
     runs, the `Input` field from the run's arguments, the optional field
     `None` when its command did not run; a validator that refuses fails the
     phase; a field typed `list[str]` with no copy is a load error;
   - the missing-output warning fires once for an execution command that
     declares an `Output` and returns only text.

**Done when:** `tests/test_planning_commands.py` passes, the tutorials
are unchanged, and the library example's planning commands that this
phase covers (`__result__`, typed facts, a declared `Output`) load and
run. talk_to_ido is not part of this phase.

### Phase 5: nested planning commands

1. **Implement `run_planning_command`** (3.5): cycle guard, alias, push
   and pop, child step numbering and ranges, the nested step budget
   (`on_iteration`), failure outputs, and no hand-off in nested frames.
   Planning command dispatch in agent mode now always goes through it,
   replacing Phase 3's agent-mode refusal. A planning command's arguments
   are checked in the CME's one validation step (3.4, The argument path):
   this phase moves `check_verdicts`, `check_arguments` and the hook there,
   in that order, still implied by type for planning commands until Phase 11
   makes them field options of both kinds (2.46).
1a. **One way to run a planning command** (2.36, 3.5). Every planning
   command runs through `_start_skill_phases`, a template-only one included,
   and the template branch of `_call_agent_for_query` no longer takes a
   planning command. A phase's budget follows how many phases the call
   runs; `state["flat"]` goes, and so does the preview's `Kind:` line.
2. **Nested ask_user** (3.5): the `AskUserSuspend` raise in
   `run_planning_command`, and the unwinding step in `_resume_agent_message`.
3. **Add planning commands to the executor's and the planner's command
   catalogs**, by the same rule as execution commands (3.4). There is no
   switch to turn nesting off (2.23). MCP `list_tools` never lists them.
4. **Callee graph and cycle detection** at load. Add the preview `Calls:`
   and `Depth:` lines, and rename the preview command to `fastworkflow
   command preview`, with no alias (3.7). Regenerate
   `docs/tutorials/skills/previews/`. Say in the release notes that every
   app workflow's pinned previews go stale with this release (talk_to_ido's
   `tests/test_skill_previews.py` is one), and give the regenerate command.
5. **Attribution.** A child contributes exactly one run to its parent
   (3.5).
6. **Tests.** Add `tests/test_nested_planning_commands.py`. Use a test workflow
   modelled on `tests/skill_tutorial_workflow`, with planning command A, whose
   step calls planning command B, which calls execution commands. Verify:
   - A's output is filled from B's typed output;
   - B's internal runs do not satisfy A's facts;
   - step indexes in the turn are unique across A's and B's runs;
   - a step naming B with an argument not written in the step returns
     the `check_arguments` refusal from the CME's validation step, and no
     frame is pushed;
   - B's `validate_extracted_parameters` runs once on the nested path,
     after the guards, with the step text as `command_text`: a correction it
     makes reaches B's plan, a refusal it returns comes back as the failed
     response, and a hook that counts its calls sees one; an `Input` rule
     that reads the request from the validation context refuses on the
     nested path as it does at the turn frame;
   - a `bind=True` fan-out phase of A whose item sub-plan calls B, where
     B opens the item's record, fills that item rather than failing it as
     never opened (3.5, Where a child leaves the workflow);
   - a phase of A calls B, which opens record X, and A's next step acts on
     the current record (talk_to_ido's `propose_fix (on X, the current
     record)` shape): the step acts on X; A's observation of the B step

### Phase 18: a run of its own for a step the agent cannot finish

Phase 18 implements the spawning of 2.55 and the spawned frames of 3.5.
It needs Phases 5 and 6. It is a gate: its branch merges only if step 1's
bar is met.

1. **Build, then measure.** Implement the `spawn` tool and
   `run_spawned` (3.5, Spawned frames) on this phase's branch. Then,

   `spawn`, three runs each, on talk_to_ido's benchmark and its

   reached their step cap in Phase 6's runs.
   - Measure: sub-tasks that fail or reach their step cap; plan success end
     to end; spawns per sub-task, and how many spawned a run for a step the
     agent had not tried; and, per sub-task, model calls, prompt tokens and
     latency.
   - The bar, written into the epic before any run, for example: fewer
     failed or capped sub-tasks, with an interval that excludes no change;
     end-to-end success no lower; and a cost per sub-task within a bound
     the epic states.
   - If the bar is not met, the branch does not merge, the result is

### Settings introduced (summary)

| Setting | Default | Meaning |
|---|---|---|
| `FW_TURN_MAX_STEPS` | 400 (optional) | Executor model iterations per turn, summed over all planning-command frames (depth 1 and below) and, from Phase 18, spawned frames; the turn frame and a fast-path frame are not counted |

This is the only setting the project adds (1.3, 2.23); the fifth, sixth
and seventh amendments add none. These were proposed and dropped:
`FW_COMPOSITE_NESTING`, `FW_SCOPED_LOOKUP`, `FW_COMPOSITE_MAX_DEPTH`,
`FW_SKILL_ASK_MIN_PROBABILITY`, `FW_SKILL_ASK_MAX_GAP` and
`FW_NOT_HERE_SEEDS`.

The seventh amendment stops reading four existing settings, distillation's
planner models: `LLM_TEACHER_PLANNER`, `LLM_STUDENT_PLANNER` and their keys
`LITELLM_API_KEY_TEACHER_PLANNER` and `LITELLM_API_KEY_STUDENT_PLANNER`
(2.54). A workflow that sets them logs once that they are ignored.
`LLM_PLANNER` stays, for the split and the conversation summary.

One existing setting becomes part of what a developer meets, as an option:
`JEV_API_KEY`, which lets Jev choose the planning command the agent sees
first, and lets the `verify` option check. Without it the agent chooses and
adapts planning commands as it plans (2.38, 2.44, 2.52), and `verify`
checks nothing (2.46). It is documented in the example env templates and `AGENTS.md`, and
its absence is an INFO line at load from Phase 6, naming the fields whose
`verify` is inactive (2.31, 3.9).

Constants, which no setting overrides:

- `SKILL_MATCH_THRESHOLD` (0.5, `workflow_agent.py`), `MAX_SUBTASKS`
  (10), the executor's `max_iters` (25) and `MAX_HANDOFFS` (2, turn frame
  only), as today;
- `NOT_HERE_SEEDS` (8; Phase 9, step 1 may lower it): the most
  hand-written seeds taken from each command outside a head for its "not
  here" class (2.15, 3.9); a command with fewer contributes all it has;
- `FULL_LISTING_MAX_CHARS` (Phase 10, step 4 sets it): the size of the full
  command listing below which a sub-task's run is shown it whole (2.30,
  3.10);
- `finish_check.NOTE_MAX_BYTES` (1,024, as today): the most a finish check's
  note holds, and the most the plan checks' notes on one plan hold together
  (2.53);
- `CODE_MAX_PAGES` (20, as today): the most pages a `full_list` step reads
  (3.13);
- from Phase 8, the per-phase step cap (15; inside a planning-command
  frame also capped by the nested budget), the fan-out cap (10, or a
  phase's own `max_items=`) and the facts list cap (100). Today these are
  the settings `FW_SKILL_PHASE_MAX_STEPS`, `FW_SKILL_FANOUT_MAX_ITEMS` and
  `FW_SKILL_FACTS_MAX_LIST_ITEMS`.
