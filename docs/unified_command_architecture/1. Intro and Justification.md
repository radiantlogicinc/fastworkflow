**Vocabulary.** A command is either an *execution command*, which defines
`ResponseGenerator` and runs code, or a *planning command*, which defines
`PlanGenerator` and returns steps. Earlier versions of this document called
them *leaves* and *composites*. Today's code calls planning commands
*skills* (`_skills/`, `fastworkflow.skill`, `match_skill`). This document
keeps those names where it cites today's code, and 3.11 lists what each
becomes. *Coding skills* are something else: the guides for coding agents
in `fastworkflow/skills_for_coding_fastworkflows/`.

## 1. Justification

### 1.1 The pattern that already exists

A user turn is handled the same way at two levels of granularity.

| Step | Skill level (coarse) | Command level (fine) |
|---|---|---|
| 1. Refine | `_run_agent` refines the request with background context | The command metadata extraction (CME) workflow adds the command context and conversation history |
| 2. Split | `split_into_subtasks`, `split_merge.merge_subtasks`, `resolve_referents` | The planner (`build_query_with_next_steps`) writes a plan of command lines |
| 3. Decompose | A skill's phases (`skill_phases.Phase`), each a bounded sub-plan | ReAct agent steps, one per plan line |
| 4. Execute the atomic unit | An executor agent run per phase (`fastWorkflowReAct`) | One formatted command, run by `CommandExecutor._invoke_command_impl` |

The two levels were built separately, so the same ideas are expressed with
different idioms, and some exist at only one level. Each such asymmetry is
something the app developer has to learn twice, and the framework
developer has to maintain twice.

### 1.2 Problems this fixes

The app developer today runs into these problems:

1. **Skills have no contexts.** `_skill_files` (`workflow_agent.py:1119`)
   skips every subfolder of `_skills` with the warning "skill contexts
   (subfolders of _skills) are not loaded yet". Commands are organised by
   `_commands/<Context>/` and `context_inheritance_model.json`; skills are a
   flat global list. A workflow with many skills cannot scope them, and
   every skill competes in every match.
2. **No ask_user while planning a skill.**
   - When `match_skill` is unsure (`SKILL_MATCH_THRESHOLD = 0.5`,
     `workflow_agent.py:1427`), the request silently falls back to the text
     planner.
   - When `plan_skill_call` (`skill_commands.py:2077`) cannot fill a
     required argument after its single retry, it also falls back.
   - At the command level, a missing parameter is asked for. At the skill
     level, the user is never asked.
3. **Three ways to say "this value relates to another command's field".**
   - `available_from` (a command input names its producer command).
   - `fact_from` (a phase facts field copies `<command>.<field>`).
   - A third idiom (`input_from`) was about to be added for skill inputs
     that forward to a callee's input.

   All three are string references stored in `json_schema_extra`. None is
   checked for field-level type compatibility, and all three break silently
   when a command is renamed or moved (Rule 4 of the
   `declare-parameter-producers` coding skill).
4. **`available_from` points at a command, not a field.** It is read by:
   - the planner prompt (`workflow_agent.py:1779`);
   - the ReAct execution agent, through command metadata
     (`command_metadata_api.py:140-155` and `:990-991`);
   - the missing-parameter message (`utils/signatures.py:1260-1267`).

   None of them is told *which output field* supplies the value. That is why
   the coding skill needs prose Rules 2 and 3 ("the producer must emit the
   handle the consumer accepts", "describe the handle at both ends").
5. **Skill arguments are narrower than command arguments.**
   `_spec_from_field` (`skill_commands.py:415`) accepts only str, bool, int,
   Literal and Optional[str]. Authors restate an execution command's description
   and examples by hand on the skill input, and the two copies drift apart.
6. **A skill cannot call a skill.** Composition today is Python
   inheritance only (`class PlanGenerator(BookByTitle)`,
   `docs/tutorials/skills/11-composing-skills.md`). Calling a skill as a step
   is impossible, because `WorkflowExecutionContext` keeps single-instance
   state:
   - `_subtasks`, `_origins`, `_subtask_index`, `_subtask_answers` and
     `_subtask_exhausted`;
   - `_next_step` and `_evidence_floors`;
   - `_phase_run`, `_phase_live` and `_phased_skill_call`;
   - `_initial_plan_text`;
   - `_workflow_tool_agent` (`workflow_execution_context.py:189-212`).

   A nested call would overwrite all of them. Skills are also not commands:
   they are loaded by `_skill_files` / `load_skill_commands`
   (`workflow_agent.py`), never registered in `CommandDirectory`, so no
   step text can name one and `_explicit_agent_command`
   (`workflow_agent.py:295`) cannot dispatch one.
7. **Two folders for one concept.** `_skills/` and `_commands/` hold the same
   kind of thing, a named capability with a `Signature`, at different
   granularities. Each has its own loader, naming rules and preview.
8. **Contexts keep each model's view small only partly.** Contexts exist
   so that the models matching a request choose among few commands,
   because both the BERT classifiers and the LLM agents degrade as that
   number grows (2.14). Today:
   - inherited commands are flattened into the inheriting context's
     classifier, so in talk_to_ido an `Account` head learns 18 commands,
     10 of them `Resource`'s;
   - the reserved `wildcard` ("try my parent") class is trained on every
     ancestor context's utterances and fills half of each record
     context's training rows, and wrong declines are the largest single
     cause of talk_to_ido's misroutes (2.15);
   - the parent hierarchy is declared twice, in
     `context_hierarchy_model.json` and in each context's `get_parent()`,
     and the two drift (2.16);
   - global commands cannot be called by name from inside a context
     (`_explicit_agent_command` refuses them), and a command the climb
     runs on an enclosing record is filed as if it ran on the current one
     (2.17).
9. **A step's wording changes what it does, silently** (2.26). Code reads
   a planning command's steps for their words:
   - only five phrases in a note read every page of a listing, so
     `(all of them)` reads one;
   - a condition inside a note is never read, so
     `renew_loan loan_uid=l1 (only when overdue)` renews unconditionally;
   - `say that ...` is copied into the answer and `say ...` is not;
   - a value equal to one of the field's `examples` hands a step that
     code wrote to the agent.

   talk_to_ido keeps shared phrase constants (`PAGING`, `FIRST_PAGE`) to
   stay consistent.
10. **Each command builds the result clients receive, by hand** (2.29).
    Every one of the 156 command files of the bundled examples, the test
    workflows and talk_to_ido builds
    `CommandOutput(command_response=CommandResponse(...))` itself, and 80 of
    the 132 that declare a `Signature.Output` never return it as `output`.
    `simple_workflow_template`, which developers copy, reports a failed
    create as a successful command. Code-run paging works only for commands
    whose text prints `start=<n>`.
11. **Navigation is declared in two places, and mostly not at all** (2.30).
    A command that enters a context says so with `descends_to` (and
    `descend_parameter`) on its `ResponseGenerator`, or the context says so
    with `enter_command(s)` and its own `<param>` markup, and
    `collect_descend_edges` merges the two by precedence. Outside talk_to_ido
    and the tutorial's sample, no workflow in the repository declares
    either.
12. **Plans are written outside the agent that runs them** (2.51). The
    planner writes each sub-task's plan before the agent starts, and writes
    its replans into the agent's observations, in the place of a command's
    response. A developer reading a trace cannot tell the two apart; a
    check on a plan has nowhere to send its note, so steps a plan leaves
    out are found only when the answer is wrong; and distillation compares
    plans apart from the actions they led to.

### 1.3 What success looks like

The app developer learns eight things, and uses them identically at every
level:

1. One folder tree: `_commands/<Context>/<name>.py`.
2. One `Signature` with an `Input`, an `Output` and a docstring. The
   `Output` is public, typed and built by the author's code. Both kinds
   return their result the same way: a `str`, the `Output`, or a
   `CommandResponse` holding both, an execution command from `__call__`
   (3.14) and a planning command from `__result__` (2.45, 3.16); a planning
   command without `__result__` has its answer written by the agent of its
   last phase. The framework, not the command, builds the result clients
   receive. No `Output` field carries `from_` at either level. An `Input`
   field may have any type the parameter extractor supports, at either
   level; its values arrive by one path for both kinds (2.22, 2.25), and
   are checked by the same field options (`in_request`, `subject`, `strip`,
   `verify`, `means`) for both kinds (2.46).
3. Two kinds of command, told apart by the class name: an execution
   command defines `ResponseGenerator` and runs code; a planning command
   defines `PlanGenerator` and returns steps. Write an execution command
   when code can decide every step, and a planning command when the agent
   should run, judge or recover part of the job (2.48).
4. One cross-reference idiom with one meaning:
   `from_("<Context>/<command>.<field>")`, on a command's `Input` field,
   names the producer whose `Output` field supplies the value (2.27). It
   replaces `available_from` (2.23). A phase's facts need no `from_`: their
   types name the commands that produce them, by the imported `Signature`
   (2.28, 2.33).
5. `ask_user` behaves the same everywhere, a missing argument included: a
   planning command's arguments arrive and are asked for exactly as an
   execution command's are (2.25).
6. Every command, of either kind, leaves the workflow where it ends.
   Nothing restores the caller's context; a step that needs another record
   navigates to it.
7. One scoping rule. A request is matched against the current context's
   own commands, then its bases', then those of each record that encloses
   it, then the global commands; the first scope that recognises it wins
   (3.9). The only hierarchy the developer declares is
   `context_inheritance_model.json`. The enclosing records come from
   `get_parent()`, and `context_hierarchy_model.json` is retired.
8. Every sub-task is planned by the agent that runs it, as the first step
   of its run (2.52, 3.6): from every command while the workflow's full
   listing fits a fixed size, and above it from a shortlist of the commands
   that match it, which the producer `from_` edges and the `descends_to`
   declarations complete (2.30, 3.10). A navigation command that moves the
   workflow without declaring `descends_to` is reported when it runs. Every
   declared planning command on the agent's list comes with its template,
   and for one that matches a sub-task the agent calls it whole, calls it
   with steps before or after it for the parts it does not cover, or adapts
   a copy of its steps (2.44). Called whole, it answers the sub-task with
   its own text, as written (2.43). Code checks the plan against the same
   `from_` and `descends_to` declarations, and the agent reads the notes
   (2.53). No provider key is needed; Jev, when configured, chooses which
   planning command the agent sees first.

The framework developer maintains seven mechanisms:

1. One registry, and one matching contract for both kinds of command
   (2.20). In each scope, matching answers one question over that scope's
   commands of both kinds, and may answer "not here". Which model answers
   in which mode, the classifier heads or Jev, is decided by measurement
   (Phase 10).
2. A `PlanFrame` stack with one per-turn step budget shared by all
   nested frames, and a cycle guard; from Phase 18, if its measurement keeps
   them, spawned frames one level deep (2.55).
3. One output contract: a command returns its `Output` (or text), from
   `__call__` or `__result__`, every frame returns
   `CommandResponse(response, output)`, and the framework builds every
   `CommandOutput` a client receives (3.14).
4. A callee graph, used for cycle detection, the preview and the
   shortlist a sub-task's run is shown.
5. One scoped lookup (3.9). Every matcher sees one scope at a time; each
   classifier head knows one context's own commands and a small "not
   here" label; and a command is bound to the object of the scope that
   recognised it before its parameters are extracted.
6. The plan step (3.6, 3.10): every sub-task's run starts with a plan the
   agent writes, from the full listing while it fits, and above that size
   from a shortlist gathered along the lookup path and into the contexts a
   plan can navigate to, with the template of each planning command that
   matches (2.44, 2.52); code checks the plan, and returns its notes to the
   agent (2.53).
7. One validation step for every command's arguments
   (`validate_parameters`): the parameter screen, the field options'
   checks, `validate_extracted_parameters`, then the `Input`'s validators,
   for both kinds (2.46).

Both developers configure as little as possible (2.23):

- A setting exists only where no single value suits every app.
- Every setting is optional, with a good default wherever one is
  available.
- No setting exists only to be retired later, such as a switch back to
  the old behaviour or an experiment's arm.

This project adds one setting, `FW_TURN_MAX_STEPS` (Settings, at the end
of section 4).

### 1.4 Non-goals

- **Not 100% identical idioms.** The class name stays an explicit switch
  (see 2.2). The target is about 95% shared, with no inferred modes.
  *Amended by 2.32:* the share is measured by what a developer learns, the
  body of a planning command included, and four inferred modes found there
  are removed (2.34, 2.35, 2.36).
- **No layer folders, no layer numbers, no policy based on layers** (see
  2.4).
- **No ordering of matching by size, depth or kind** (see 2.13, 2.20).
  Planning commands may nest to any depth; depth is an execution matter.
- **No delegation lists, and no required `get_parent()` annotations**
  (see 2.16).
- **No planner in assistant mode.** Planning commands run only in agent
  mode. In assistant mode, a request that needs one is refused with a
  pointer to agent mode, as a named planning command already is (3.4). It
  is never handed to the agent silently (2.21).
- **No saved, generated planning commands.** The built-in planning
  command writes a plan for one sub-task and keeps nothing. Every
  planning command is written by a developer (2.21).
- **No change to the type of the result clients receive.** `TurnOutput`
  and each `CommandOutput` in it keep their fields. The framework, not the
  command, builds each `CommandOutput`, and a field leaves the wire only
  through a versioned wire change (2.29).
- **No compatibility names for what never shipped.** Planning commands
  were never released, so their old names get no aliases and no
  deprecation period. What did ship and changes in the next major release
  (`available_from`, `context_hierarchy_model.json` and the trained
  classifier heads) fails visibly, naming what to do instead (2.23).

Four earlier non-goals were dropped after a review on 2026-10-26: keeping
planning commands out of the classifier heads (2.20), keeping the
planner's and the executor's catalogs as they are (2.19, 2.21), keeping
`_spec_from_field` narrow (2.22), and renaming no public APIs (2.23).
