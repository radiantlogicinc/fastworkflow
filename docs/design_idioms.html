For people writing a workflow

The shapes a workflow author writes.

A fastWorkflow app is a tree of commands. A command is one of two kinds, and it lives in a context. An execution command runs your code. A planning command writes the steps of a job the agent runs, with code running every step it can. A context is one kind of object the workflow can stand on, and the commands that act on it.

Each row below is one shape. The example is the smallest one that shows the whole shape. A real command is several of them in a single file. A planning command keeps the execution Signature, with its purpose, seeds, inputs and their options, the producer edge, the hook, and approval, and adds a PlanGenerator.

Execution commands

Code that runs.

One Python file. Signature says what the command is. ResponseGenerator does it. The command runs in agent mode, in assistant mode, and through a direct API or MCP call.

01

One file, two classes

__call__ receives the workflow, the command name, and the filled Input. With no Input, that argument is None.

See also what it returns.

02

The record it acts on

workflow.record is the record the command acts on: the one it was invoked on. That can be an enclosing record, reached through get_parent, so a command in the Item folder can run while the workflow stands on a record inside one. Reading it gives the record; assigning it moves the workflow (see move onto a record).

03

The purpose sentence

The Signature docstring is the command, in the words a person would use. The matcher reads it. When intent detection is unsure, the tie-break shows the first sentence of each candidate, so that sentence is the purpose and any condition follows it.

04

Seed utterances

plain_utterances is the list training expands into the sentences the intent classifier learns. Vary the kind of sentence (an order, a question, a short colloquial line) and aim for about eight. Wording copied from the benchmark teaches the benchmark back to the model, so the seeds stay off intent_benchmark.json.

05

An input

Signature.Input is a pydantic model. The field's description is what the extractor reads, and examples is a value it can copy. A field with no default is required: a missing value is asked for. A default, or Optional[str] = None, means the request may leave it out.

A scope the question can take is an optional field. Its default means the whole set, and the words for "all" map to that default. A scope the user writes is text in the command, so it carries copied_from_command_text (see the user's own words).

A bare value takes the text after the command name in agent mode: one str field marked command_text_after_command_name, at most one per Input, on an execution command, so find_item Alpha binds to it without an extractor.

06

The user's own words

Each option is one key in json_schema_extra. Its value is True, or a dict of that key's own options. Combine keys by adding them; a conflicting pair fails the load.

copied_from_command_text requires a str, int or list[str] to appear in the command text, so a stored note stays the user's sentence. {"ignore": [...]} drops kind-words from either end of a str before the check, so "the Riverside branch" yields Riverside.

record_named_in_command_text is for a str that names a record the command text names. It checks names already written in the command text; it does not interpret the description. The description, plus the sentence the framework appends to it, is what LLM_PARAM_EXTRACTION reads. A model re-picks a record name only with classifier_confirms alongside and JEV_API_KEY set.

converted_from_command_text is for a str or int that the command text is converted into, such as a date. The text check skips it; its placeholder checks still run. Execution commands only.

The classifier keys (classifier_confirms, classifier_decides) are under a flag a classifier decides. A from_command_output key is under a handle's producer.

07

A handle's producer

from_command_output on an Input field names the command that produces an id, uid, or code. The value is "cmd.field", one field of that command's Output (preferred), or a bare "cmd". A list names several producers, and a Context/cmd form names a command of another context. The planner walks these edges to order the commands, and a missing value tells the caller which command supplies it. Name a producer the caller can reach, and match the type: a str may come from one item of a list[str].

See also move onto a record.

08

Correct or refuse

Cross-field rules have one mechanism: a @model_validator(mode="after") on Input. It reads info.context, which holds command_text, workflow (None while a template or preview renders), and command (the qualified name), for either kind of command. Correct a value by assigning self.<field> and returning self. Refuse by raising fastworkflow.Refused(message, field=...); a plain ValueError refuses with no field.

Order: extraction, the option checks, the model validators in declaration order, then the role checks. A name=value binding whose value fails its type or a field validator is dropped, and the extractor runs instead. A field_validator cleans up one field. Neither can replace required or ignore: a missing required value fails before any validator runs, and ignore strips words before the verbatim match.

Known false positive: the library's note_member refuses a note that repeats the member's own name, such as "Mia Chen to call back". That is the request around the note, which is what the validator is for, but a real note with the name in it is refused too.

09

What it returns

__call__ returns one of three things, and the framework wraps it. The Output model is the typed result, and its JSON is the response. A str is the response alone. A CommandResponse carries the sentence a person reads together with the Output a caller reads. To decline, raise Refused.

A planning command's __result__ builds the same Output, so Signature.Output is the command's public result in both kinds. Build one on every path, including the path where nothing was found, so a caller can rely on it.

10

A command that changes data

@writes on an execution command's ResponseGenerator marks a command that changes the application's data, including a change that is easy to undo. Inside a planning phase, such a command runs only when a step of that phase names it. A planning command's PlanGenerator takes no mark: it writes when one of its steps runs a command that declares it.

11

Ask before it runs

@user_approval_for_execution sits on ResponseGenerator, or on PlanGenerator for a planning command. UserApproval.REQUIRED_ALWAYS asks before every run. UserApproval.REQUIRED_UNTIL_DELEGATED asks until a standing approval exists for that user, that workflow, and that command. The reply is yes, no, or always, and always records the delegation. Leave the decorator off and the agent decides.

12

Move onto a record

Assigning workflow.record is the move: from then on the workflow stands on that record, and its commands act on it. Read the record into a local first, then assign to move. @descends_to("Item") declares the destination, so the framework knows the way into Item before the command runs. when_parameter names the input field that chooses the destination, and it is optional. The way in is declared here, on the command.

See also the enclosing record and a node inside the snapshot.

13

The root object

The startup command builds the object the workflow stands on at the beginning and stores it as workflow.root. It is set once per workflow; a second assignment fails. Navigation then moves workflow.record onto a record inside it.

Planning commands

A job written as steps.

Same folder, same Signature. PlanGenerator replaces ResponseGenerator. A method written with no leading underscore is a phase: it returns the steps of one run, and its return annotation is the facts that run fills. A method with one leading underscore is a helper. Phases run in the order the methods are written. A phase that is not needed returns []. __phases__ is documented only under shared phases.

A planning command's Signature docstring is read twice. The matcher reads it with example requests added. The splitter reads it as that command's job_types line, so the docstring shapes how a request is split as well as which command matches (see splitting a request). Write it as a purpose the splitter can judge.

01

A plan in place of a body

The file reads top to bottom: a module docstring, the imports, Signature, then PlanGenerator. A planning Input field is a str, bool, int, Literal of text, or Optional[str] = None. A bool defaults to false, so it turns on when the request asks.

The Signature itself is the execution set: purpose, seeds, input, the user's words, the producer edge, the hook.

02

A step the code runs

run(command, *, named=None, all_pages=False, **inputs) writes a command step. The inputs are the command's own Input field names. Once every required value is known, code runs the step. A value of None is left out of the step, and a keyword the command's Input lacks fails the load. A plain string is a step for the agent.

03

Facts from one command

A phase's return annotation is the facts it hands on. Annotating with a command's Output fills those facts from that command's run in the phase. Later phases receive them as a parameter of the same name. The import is the other command's Signature.

04

Several commands, one phase

When one phase runs two commands, the facts are a model with one field per command, each typed by that command's Output. A value computed from those fields is a property. The model sits just above the method that fills it.

05

Whichever command ran

A phase that runs one of two commands annotates a union of their Outputs. __result__ reads the fields of the one that ran. A Literal input is how the call says which.

06

A phase that does not run

return [] skips the phase. It is decided when the phase is reached, on the facts known then, so a phase gated on a bool input or on a fact is written as an if that returns []. A later method reads a phase that may have been skipped through a parameter default of None.

Use return [] rather than leaving the phase out of __phases__. Both run the same, but the previews differ. Measured on a probe copy of a planning command, with fastworkflow command preview: a phase left out of __phases__ reads "only when loans = true" in the Phases table, and the plan for loans = false has no step for it at all. A phase that returns [] reads "always", and that plan lists the phase with "No steps." and the note that it is skipped when reached.

07

The answer, in code

__result__ runs once, after the last phase, as ordinary code. Its parameters are input and the phases whose facts it reads. It returns the sentence, or a CommandResponse carrying the sentence and the Output (see what it returns). A planning command with no __result__ leaves the answer to the agent.

08

The row a listing named

run(..., named=...) opens one row of a listing this call read. Code chooses the row whose label holds that name, or the only row. The row-id input is the field marked from_command_output, else the command's single required str field, else the load fails. If the phase already holds the id, pass it too: the step is then the command with that id value.

09

Every page

A command whose Input has an integer start is paged, and its Output declares total. The paging parameter is start only. run(..., all_pages=True) reads page after page until the rows reach that total, up to CODE_MAX_PAGES pages (20). Past the cap, the agent reads on. The phase's facts hold every row read. Without all_pages, the same call reads one page.

10

Once per item

@phase(over=...) runs the phase once per item of a list an earlier phase filled. The one parameter that is neither input nor a phase receives the item. In __result__, the phase arrives as the list of those facts, in item order, empty when the list was empty. Each item is opened onto its own record; bind=False is for items that have no record of their own. max_items caps the run, and noun is the word in the note that says so.

11

Calling a planning command

A step that names another planning command runs that command as its own call. The phase hands on the callee's Output, and the workflow is left where the callee left it. The callee's internal steps stay inside the callee. A command that calls itself, even through another command, is reported when the files load. The nested calls of one turn share FW_TURN_MAX_STEPS, 400 unless the workflow sets it.

12

Shared phases

Phases two commands share live on a base class in a _ module. The command subclasses that class, and its __phases__ places the inherited methods where this job needs them, in order. This is the only place __phases__ is needed: a phase that is optional for one call returns [] instead (see a phase that does not run). To reuse a whole command, call it: its PlanGenerator stays its own.

See also helper modules.

13

A flag a classifier decides

classifier_decides on a bool lets a classifier decide the value from the command text alone. The field keeps its default when the classifier is unsure. classifier_confirms asks a classifier to check the value again from the command text. It applies to a bool, to a Literal (its meanings go in {"meanings": {value: text}}), or to a str with record_named_in_command_text alongside. Both use JEV_API_KEY; with no key they do nothing.

14

Splitting a request

On an agent turn the user's message is split into the separate requests it bundles, before any planning command is matched. The splitter sees the new message only; earlier turns go in as a separate conversation input and never become part of a sub-task. A plain "what can you do?" is answered in code and not split. It uses the planner model (LLM_PLANNER) at temperature 0. A reply cut off at LLM_SPLIT_MAX_TOKENS (default 4,700), or visibly broken (two identical sub-tasks, or one that still points at the rest of the request, such as "each of them"), is retried once at 0.7. A failure, or more than 10 sub-tasks, runs the request whole.

The developer's one optional file is _commands/_split.py, at the workflow root only. Every attribute is optional. Its Signature docstring replaces the splitter's instructions wholesale, examples included, with no way to append. Its Signature.Input and Signature.Output may describe only job_types, user_query and subtasks; any other field fails the load, and conversation cannot be changed. identifier_patterns and subject_hints are covered under identifier formats. The file is imported like a command file, so package-relative imports work. It is cached per process, so restart after an edit.

A malformed file fails the load and names the problem: a pattern that does not compile, a raw string where re.compile belongs, a single pattern where a list belongs, a non-string subject_hints, or a Signature that is not a class.

The merge joins a sub-task with no subject of its own to the one before it. With JEV_API_KEY, Jev decides whether two neighbours are one job, and a sub-task is kept apart only when Jev's "one" probability is under 0.2. Without the key those joins are made with no second opinion. The referent step, which writes the record a sub-task means by "it" or "the customer", needs the key (threshold 0.5); without it the sub-tasks pass through unchanged. When the merge leaves one job, the user's own request runs, not the model's rewrite of it.

Levers outside the file: a planning command's docstring (its job_types line), LLM_PLANNER, LLM_SPLIT_MAX_TOKENS, and JEV_API_KEY. The 10-sub-task cap, the 0.2 and 0.5 thresholds and the merge rules are fixed in code.

Next: the sub-task review.

Contexts

Where a command lives, and which object it acts on.

Two declarations decide what a request can reach. base, in context_inheritance_model.json, adds another context's commands to this one. get_parent, on the context class, names the record that encloses this one. The folder holds the commands of the context itself.

Where a request looks. This is not a separate idiom. It follows from four declarations. An exact command name takes the nearest scope that has it, in this order: the current record's own context, that context's base contexts, then each record on the live chain reached through get_parent with its bases, up to the root, and last the global commands. A command file directly in _commands/ is a global command, callable from anywhere by name. The workflow moves into a record only through a command's @descends_to.

01

A folder for one kind of object

The folder name is the context. _commands/Item/show_item.py is the command Item/show_item, and it runs when the workflow stands on an item. _commands/Item/_Item.py is that context's callback class, always named Context.

02

Commands with no object

A command file in _commands/ itself, beside the context folders, is a global command. It is reachable from every context by name.

03

Commands shared through a base

base lists the contexts whose commands this one also has. Item and Member below both gain whatever lives in _commands/Record/. Record can be a base that nothing ever stands on. The file has this one key. A context's own commands come from its folder, so a context is added here to give it a base.

04

The enclosing record

get_parent(cls, record) returns the record that contains this one, read off the live object. An item's parent is the catalog, so the catalog's commands stay reachable while the workflow stands on the item. The walk stops at the root: workflow.get_parent of the root returns the root. The inheritance file holds bases only; the enclosing record comes from here.

05

A record's name and identity

Two declarations on the same context class, and they answer different questions. get_displayname is a display string. instance_label_attr names the attribute whose value is the record's identity. Neither derives from the other.

06

Remember the object

get_state(cls, record) returns a JSON-ready dict, and from_state(state, workflow, *, state_version) builds the object back. state_version is the number that pair understands; a snapshot from another version raises UnsupportedStateVersion. Returning fastworkflow.EPHEMERAL says the context is deliberately kept in memory only. With no get_state, a session that holds the live object stays pinned.

07

A node inside the snapshot

The snapshot is of the root. When the workflow stands on a record inside that root, get_locator(cls, record) returns a path to that record, and find_by_locator(anchor, locator) walks the path on the restored root. An id that is unique only among siblings needs its ancestors in the path.

08

Identifier formats

identifier_patterns in _commands/_split.py is a list of compiled patterns, one per ID format the workflow uses. It is a workflow-wide declaration with four readers:

  • Merge. Each match is a subject, like a quoted name, when the split is merged.
  • Referent step. Which records a sub-task leaves unnamed.
  • Planning-command argument checks. A string argument cut from inside an ID becomes the whole ID: "4421" becomes "acct_4421". Inside several matches, the argument is refused.
  • Policy verifiers. Their ID patterns, when the policy table gives none.

The file and its load errors are under splitting a request.

Plain Python and Pydantic

Ordinary shapes, read by the framework.

These are not framework idioms. They are the ordinary Python and Pydantic forms the framework reads. Each row says what it means in a workflow file.

01

A class

The framework finds Signature (with Input and Output nested in it), and ResponseGenerator or PlanGenerator, by name in each file. Other classes in the file are ordinary Python, such as a BaseModel that a phase annotates with.

02

A docstring

The Signature docstring is the command's purpose: the matcher reads it, and for a planning command the splitter reads it too (see splitting a request). It is one line of the purpose, in the words a person would use.

03

A Field

description, default and examples are what the extractor reads and what the docs show. The framework's options go in json_schema_extra, one key per behaviour (see an input and the user's own words).

04

A return annotation

In an execution command, the return annotation of __call__ is the Output the command returns. In a planning phase, the annotation is the facts that phase hands on (see facts from one command).

05

A union

A phase annotated with a union of two Outputs runs one of two commands, and __result__ reads the fields of the one that ran (see whichever command ran).

06

A property

A value computed from a record, or from a model of facts, is a property. A record's identity is a property too, when it is computed, and instance_label_attr names it (see a record's name and identity).

07

A subclass

A planning command that subclasses a base class inherits its phases, placed by its __phases__ (see shared phases). Its __result__ can extend the shared answer with super().

Helper modules and step helpers.

Not idioms: the modules and helper functions the shapes above use.

Helper modules

A file whose name starts with an underscore is a module the commands import: shared wording, tables, facts models. It is never matched as a command. The one exception is the context callback, the file named after its folder: _Item.py in Item/.

# _commands/Item/_wording.py
from fastworkflow.planning import count

def copies(n: int) -> str:
    return count(n, "copy", "copies")

# _commands/Item/show_item.py
from ._wording import copies
