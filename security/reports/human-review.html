Unsafe pickle deserialization in DiskCache

ID: CVE-2025-69872 / GHSA-w8v5-vhqr-4h9v / PYSEC-2026-2447
Component: diskcache 5.6.3 (transitive via dspy)

Why a code / process change (not pyproject alone)

No patched PyPI release exists (latest still 5.6.3 as of 2026-09-03 23:24 UTC). A pyproject.toml bump cannot remediate. Mitigation would require application changes (disable DSPy disk cache, relocate/harden cache dir permissions, or wait for upstream non-pickle default).

Rationale

Documented in security/vex/fastworkflow.openvex.json (version 7) as not_affected with justification vulnerable_code_cannot_be_controlled_by_adversary. Exploitation requires write access to the process-local DSPy cache directory; remote API/MCP clients cannot write that path. An adversary who can write as the service user already has equivalent privilege to pickle RCE. Re-evaluate if cache directory is shared across trust boundaries or world-writable. When upstream ships a fix, add a floor constraint in pyproject.toml. Recommendation remains IGNORE (accepted risk / VEX) rather than FIX because no actionable code path is reachable by remote clients in supported deployments.

FIX

Optional: harden DSPy disk-cache deployment guidance

ID: Process follow-up related to CVE-2025-69872
Component: docs / operator guidance (not a dependency bump)

Why a code / process change (not pyproject alone)

While the vulnerability is not remotely reachable in supported deployments, operators who mount ~/.dspy_cache (or equivalent) as a shared/world-writable volume could change the threat model. That is a documentation / deployment-checklist change, not a version pin.

Rationale

Recommend a small docs note (or runbook checklist item) stating: do not share the DSPy disk-cache directory across trust boundaries; keep it mode 0700 and owned by the service user. This does not change runtime code. Marked FIX as a low-cost process improvement; deferrable if docs bandwidth is constrained. Not blocking for this PR.
