IGNORE

diskcache 5.6.3 — pickle RCE (GHSA-w8v5-vhqr-4h9v / CVE-2025-69872 / PYSEC-2026-2447)

Severity: Medium (CVSS ~5.2) · Ecosystem: PyPI · Fixed version: none on PyPI (latest still 5.6.3) · OpenVEX v9: not_affected

Why this needs human judgment

No patched release exists. Clearing the alert would require replacing DSPy’s on-disk cache backend, vendoring a fork, or disabling disk cache — all application/process changes, not a pyproject.toml bump.

Recommendation rationale — IGNORE

  • fastWorkflow does not import diskcache directly; it arrives transitively via dspy for LM response caching (dspy.configure_cache).
  • Exploitation needs write access to the process-local cache directory (e.g. ~/.dspy_cache) plus subsequent deserialization. Remote MCP/API clients cannot write that path in supported deployments.
  • An attacker who can already write arbitrary files as the service user already has equivalent-or-greater privilege than pickle RCE would grant (vulnerable_code_cannot_be_controlled_by_adversary).
  • Documented in security/vex/fastworkflow.openvex.json; Trivy suppresses with --vex.

Re-evaluate when

  • PyPI publishes a fixed diskcache (or DSPy switches cache backends).
  • A deployment mounts the DSPy cache as world-writable or shared across trust boundaries.

Why this needs human judgment

Debian bookworm packages in the public Python slim image often lack fixed versions in-distro (affected / fix_deferred). Addressing them requires maintaining a custom hardened image or switching bases — outside pyproject scope.

Recommendation rationale — IGNORE

  • fastWorkflow ships as a PyPI library/CLI, not a container product; no Dockerfile is owned in-tree.
  • Findings characterize a third-party reference image used only for Dockle/Dive/Trivy completeness in this automation.
  • Consumers who containerize should choose and patch their own base images (or rebuild when Debian publishes fixes).
